# v0.3 — specification

**Status:** DRAFT for review. Three items. Two are operator-requested features; one is the
structural work deferred from v0.2.

## A note on the promotion rule

v0.2 shipped under *"anything that cannot name the artifact it retires does not get scheduled"*,
and I used it to argue against the refactor. **That was too narrow and the operator was right to
push back:** a refactor's artifact is *future* debugging cost, which is diffuse but real. The
evidence is already paid — two doc line-citations drifted, a cold-start fix referenced an
out-of-scope variable, and agents demonstrably struggle to navigate a 23k-line file.

So the rule stands for *bug* work, and structural work is judged on a different axis: does it make
the next fix cheaper and safer? WS-1 is scheduled on that basis, not on a retired artifact.

## WS-1 — Extract the reconcilers

`service/routers/api_v2.py` is **23,323 lines**. The reconcilers are a well-defined seam inside it:

| | |
|---|---|
| reconciler functions | **43** |
| lines they occupy | **3,530 (15% of the file)** |
| imported by `main.py`'s sweep | **28** |

The sweep's import list is effectively the extraction manifest — a boundary the code already
declares rather than one we invent. Largest: `_reconcile_managed_worker_hygiene` (242),
`_repair_terminal_session_consistency` (232), `_close_orphaned_managed_runs` (212),
`_reconcile_dead_session_status` (210).

This is also where **two of v0.2's bugs lived** (`_close_reconcilable_delivered_runs`'s
`finished_at` guard, hidden two months; `_finalize_spawns_with_dead_terminals`'s absence), which is
the concrete case that they are hard to reason about in place.

**Target:** `service/reconcilers/`, one module per responsibility, imported by `api_v2.py` and
`main.py` unchanged from the callers' perspective.

### Per-slice gates (set by `comms-senior-dev`)

*"The safety net is 'running service behaves the same', not 'pytest saw the same functions'."*

- [ ] **Pure moves only.** No behaviour change in the same commit as a move.
- [ ] Container rebuilt, `aify-doctor` green.
- [ ] **Pre/post route inventory diff** — the router must expose exactly the same routes.
- [ ] **Import-identity check**: no second `_LIVE_STATE_CACHE` / `_LIVE_SCREENS` instance. The
      single-worker invariant is untouchable; a duplicated module-global silently forks state.
- [ ] **One live smoke replay through the moved seam** against the running service.
- [ ] Before/after API responses for representative endpoints from a seeded DB.

### Non-goals

Rewriting logic while moving it. If a move surfaces a defect, card it and move on. Empty behaviour
changelog is the point — if something breaks during v0.3, there must be exactly one candidate cause.

## WS-2 — Desktop notifications (operator-requested)

*"i want dashboard to use notices system … so i would hear when i would get message from agent."*

**The plumbing already exists.** The dashboard holds a `/ws` WebSocket with backoff, and the
service already broadcasts `message_sent` with `{id, from, to, subject}` (`api_v2.py:17040`) plus
`channel_message`. Nothing new is needed server-side.

- [ ] New module `service/new_dashboard/notify.mjs` — pure, with its own `notify.test.mjs`, per the
      repo rule that `app.js` (~4.9k lines) is only reachable by source-regex tests.
- [ ] Permission requested on an explicit user gesture, never on load.
- [ ] Fires only for messages addressed to `dashboard` — the operator's inbox, not all fleet chatter.
      Getting this wrong turns 3,800 messages/14d into 3,800 notifications.
- [ ] Suppressed while the tab is focused; a visible dashboard does not need a popup.
- [ ] Off by default, with a persisted opt-in toggle.

**No TLS work needed.** `localhost` is a secure context, so opening the dashboard at
`http://localhost:8801` on the machine itself gives full `Notification` support with zero
infrastructure. This is the correction to my earlier claim that HTTPS was required — that applies
only to phones.

## WS-3 — Mobile alerts via ntfy (operator-requested)

Web Push was the wrong tool here: it needs a service worker, therefore a secure context, therefore
TLS on a LAN address — for a service the operator explicitly runs **locally, in a container**.

**ntfy** is one outbound HTTP POST. No PWA, no service worker, no VAPID keys, no subscription
table, no TLS on our side. The container already reaches the internet for the OpenAI quota check.

- [ ] Setting: `notify_ntfy_url` (empty = disabled). Default OFF.
- [ ] POST title/body/priority when a message lands for `dashboard`.
- [ ] **Fire-and-forget with a bounded timeout.** A notification failure must never fail or delay
      the message it is reporting — this hooks the send path, which is the fleet's hot path.
- [ ] Rate-limit or coalesce. See WS-2: the volume here is large enough to make a phone unusable.
- [ ] The URL is a secret (anyone with the topic can read the notifications). It goes in `.env`,
      never `config/service.json`, and must not appear in logs or `/settings` responses.

Self-hostable later if the public topic is unwanted; a Telegram bot is an equivalent-effort
alternative if preferred.
