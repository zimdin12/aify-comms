# v0.2 — what shipped, and the ledger behind it

**Status:** SHIPPED. Written 2026-08-07 as a draft ranked by evidence, then rewritten
after every candidate was scanned for proof and after `comms-senior-dev` reviewed the
plan. `V0.2_ROADMAP.md` and `V0.2_PLAN.md` remain the raw finding backlog; this is the
release record.

## The rule this release is built on

> **Anything that cannot name the artifact it retires does not get scheduled.**

`comms-senior-dev` arrived at the same rule independently — *"I would not promote any
scan item unless it attaches to a live failure or blocks diagnosis of one"* — and asked
for it to be mandatory per work item, so v0.2 *"stays evidence-ranked instead of
becoming another checklist backlog."*

Applying it cost the draft four items, including one of my own confident diagnoses.
That is the rule working, not the rule being expensive. The backlog holds ~113 open
findings against 3 closed; more findings was never the constraint.

### Why #5 was dropped — a retraction

I predicted that leaked `bridge_instances` rows would make `_requeue_orphaned_claimed_runs`
read a dead claim bridge as fresh. **It does not.** That reconciler keys on
`bi.id = r.claim_bridge_id` — one specific bridge row — so sibling rows for the same
agent cannot make the claim bridge look alive.

The accumulation is also *deliberate*: `_record_bridge_registration` carves out
same-terminal wrapper-child siblings so bridge-spawned PTY siblings cannot kill each
other, and the rows age out after 5 minutes without a heartbeat. Measured live: 26 rows
total, max 4 per agent, all superseded on schedule.

Real, bounded, by design, no consequence found → no artifact → dropped. This is the
third time I have been wrong about a bridge-lifecycle mechanism in this project; the
pattern is that these mechanisms look leaky from the outside and are load-bearing on
the inside.

### Why #9 is gated

WS-3 in the draft. It is real, but I have now published two wrong diagnoses of the
restart bug and shipped-then-reverted one fix (`0b948d2` → `70e03aa`). It stays blocked
on one question, which must be **answered with evidence before any code is written**:
why does the sidecar report *"Delivered to Claude **resident** session"* for a MANAGED
agent? If managed work takes the resident path, that path plausibly never opens a turn
against the claimed run — which is the observed shape. Guessing again is how this
becomes slop.

### Why #10 is reframed

Not "split 23,023 lines" — that is a project with real regression risk and nothing
user-visible to show for it. The justified slice is **extract the reconcilers**: one
bounded seam, pure-ish, individually testable, and where *two* of this session's bugs
lived (the `finished_at` guard that excluded its own target rows for two months, and
finding #2 above). Everything else gets split opportunistically, when something is
already being changed there.

`comms-senior-dev` agreed it needs its own release with an empty behaviour changelog,
"probably v0.3", because interleaving it with behaviour fixes makes regression triage
ambiguous.

## What shipped

### 1. An agent can read why its own worker died

The operator's ask, verbatim: *"it would have been nice if sc-manager would have seen
what hermes responded… then he could have fixed it and tried again. Agents should know
what is going on."*

- **`service/terminal_diagnostics.py`** (new, pure): `meaningful_failure_line()` picks
  the ONE line that explains a death — the FIRST line carrying a fatal marker, because
  in the captured incident three consecutive lines were fatal and the third literally
  says *"see the error above"*. First-fatal is the cause; last-fatal is the symptom.
  Falls back to the last meaningful line; returns `""` when only harness scaffolding was
  recorded, so `""` means "no diagnosis" and can never be rendered as one. Bounded to
  240 chars — a truncated fatal line is useful, a 4KB ANSI dump in every failure message
  is the over-messaging problem this project already has.
- **`GET /agents/{agent_id}/console`** now falls back to the most recent terminal's
  RECORDED output when there is no live console, returning
  `live:false, historical:true` with `failureLine`, `status`, `stoppedAt`. Side-effect
  free — it never starts a worker.
- **`comms_console_tail`** renders that case as `NOT LIVE — … This worker is gone; the
  output below is history.`, leading with `Cause: <line>`. The tool description now says
  it works on a dead worker, because an agent will not reach for a tool whose
  description says "live console".

**Tested against the REAL captured frame** — the 459 bytes read verbatim out of the live
DB, ANSI and CRLF intact, not a hand-written approximation. The compaction bug shipped
because its fixtures were authored from documentation.

**Retires:** the 2026-08-07 relay-through-human. **Verified by:** the acceptance test
named in the draft — the incident's output must yield the `hermes dashboard … did not
become ready` line.

### 2. A dead worker no longer suppresses its own respawn

`_finalize_spawns_with_dead_terminals()` — deliberately **state-based, not event-based**.

Two existing reapers missed the incident for one structural reason each:

- `_fail_orphaned_running_spawn_requests` skips any spawn whose claiming bridge is a
  currently-ONLINE env bridge. The env bridge stayed online — only the worker died — so
  that reaper is *correct* to skip it and can never cover this shape.
- `report_terminal_dead` **does** finalize the spawn, and its comment explains exactly
  why that matters. But it is one of ~26 `UPDATE terminal_sessions` sites, and it was
  never called here: the row carries no `console_dead_reported` event and an empty
  `error`. Finalization was bolted onto a single death path out of many.

Keying on the terminal's own recorded status means a new way for a terminal to die
cannot defeat it — the property the event-based version lacked.

Guards, all tested: only `starting`/`running` with empty `finished_at`; requires a
session-bound terminal in `_TERMINAL_END_STATUSES`; **leaves the spawn alone if any
terminal on the same session is still live** (rebind race); requires the death to be
older than `SPAWN_DEAD_TERMINAL_GRACE_SECONDS` (45s) with an undeterminable death time
treated as too fresh; never overwrites an existing error.

**Retires:** the 5-minute window in which a dead worker's own respawn is refused with
"a spawn for this agent is ALREADY IN FLIGHT". **Verified by:**
`test_the_next_coldstart_is_no_longer_suppressed`, which asserts the operator-visible
outcome — `_has_pending_or_booting_spawn_request` True before, False after — rather than
the mechanism.

### 3. The cheap half of the duplication findings

For N12 (8 implementations of "is this terminal active"), N1 (40 inline `status IN (…)`
literals) and H3, the expensive remedy is consolidating every copy. The cheap one is a
test that the copies **agree** — which catches the actual failure mode, divergence, at
near-zero risk.

`_TERMINAL_END_STATUSES_ORDERED` is the deterministic SQL-binding form of
`_TERMINAL_END_STATUSES`, and `test_terminal_status_sets_agree` fails the suite if they
ever drift. Consolidation happens opportunistically from here, not as a project.

### 4. Dead code deleted, coverage kept

`_is_turn_busy_fresh` had zero production call sites. Its only test was retargeted at
`_turn_busy_state` — the layer every live caller actually reaches — so the freshness
semantics stay pinned while the dead wrapper goes. Deleting both would have been a net
loss of coverage.

## Non-goals for v0.2

- **A broad code scan.** The six fixes in v0.1.3 and all four here came from live
  failures with traces; none came from reading code speculatively.
- **The remaining backlog.** Pull one forward only when a live failure points at it.
- **Dashboard feature work.** This is a reliability and observability release.

## Carried in, not scheduled

- **Hermes moved 0.15.1 → 0.20.0.** The debug reference material describes 0.15.1, and
  0.20.0 already broke managed spawn once (missing web UI build). Prove one real
  managed-hermes send after any hermes update.
- **`bridge-running` / `agent-identity` skip on Windows.** After `install.sh` nothing
  verifies a RUNNING wrapper executes the new bridge code on this host. Item B1 (bridges
  report their build stamp on heartbeat) makes it platform-independent and is cheap; it
  is not here only because nothing has yet failed because of it.
- **Wrapper-child bridges mint a fresh UUID per re-registration** while the
  channel-sidecar uses a stable derived id. A stable id would make the row a no-op
  UPSERT instead of a new row. No symptom found, so not scheduled — recorded because it
  is the reason #5 *looked* like a leak.
