# v0.2 — specification

**Status:** draft for operator review. Written 2026-08-07, after a session that shipped six fixes
to v0.1.3. Supersedes nothing; `V0.2_ROADMAP.md` and `V0.2_PLAN.md` remain the finding backlog and
this is the *release plan* drawn from them.

## The shape of this release

**Ranked by evidence, not by scan.** Every item below was surfaced by something that actually
broke on the operator's machine, with a trace. That is deliberate:

- The backlog holds **119 open findings** (26 in `V0.2_PLAN.md`, 93 in `V0.2_ROADMAP.md`) against
  **3 closed**. More findings is not the constraint.
- The six fixes that shipped in v0.1.3 all came from live failures — a restart that produced no
  worker, nine orphaned processes, a reconciler that excluded its own target rows, 4,391 leaked
  directories, a broken hermes install, a refusal that named the wrong cause. None came from
  reading code speculatively.
- The scan-derived items (N1–N13) are, with the exception of the ones hotfixed into v0.1.x, still
  open. They were not wrong — they were unranked, and unranked findings do not get done.

**So: no broad audit for v0.2.** One structural item is included because it has become a
first-order cost, not because it is tidy.

## WS-1 — An agent must be able to diagnose its own failure

**Why first.** This is the highest-value item in the release and it comes directly from the
operator: *"it would have been nice if sc-manager would have seen what hermes responded… then he
could have fixed it and tried again. Agents should know what is going on."*

On 2026-08-07 a managed hermes worker died 65s after spawn. The cause was recorded, verbatim, in
`terminal_events`:

```
[hermes-managed-host] fatal: hermes dashboard at http://127.0.0.1:9147/
                      did not become ready within 60000ms: fetch failed
```

The requesting agent was shown *"No online environment can host managed hermes for this agent"* —
which was false. The real diagnosis existed the whole time and nobody could see it. The operator
had to bring it to a human, who found the actual cause (a hermes install with no built web UI) in
minutes once the terminal output was read.

N8 (shipped in v0.1.3) fixed the *category* of the refusal. It did not surface the evidence.

- [ ] When a managed spawn or dispatch fails because its terminal died, attach that terminal's
      **last meaningful output** to the run's `error_text` / the failure the requester receives.
      "Meaningful" needs a definition, not a tail: prefer a line matching a fatal/error marker,
      else the last non-ANSI-noise line. The 13:36 case must yield the `hermes dashboard … did not
      become ready` line, and that is the acceptance test.
- [ ] Bound it. A truncated fatal line is useful; a 4KB ANSI dump in every failure message is the
      over-messaging problem this project already has.
- [ ] Make it reachable *after* the fact too. `comms_console_tail` only works while a console is
      live, so a dead worker's output — the case that matters most — is unreachable by the agent
      that needs it. Either extend it to read the recorded output for a stopped terminal, or say
      plainly in the tool description that it cannot, and name what can.
- [ ] Test with a REAL captured frame, not a synthesized one. The compaction bug shipped because
      fixtures were hand-written from documentation.

**Done means:** an agent whose worker dies can read why, without the operator relaying it.

## WS-2 — A dead worker must not poison every later send

**Trace, same incident.** The 13:36 spawn request stayed `status='running'` indefinitely after its
terminal died. A claimable spawn request makes cold-start refuse, so *every subsequent send* to
that agent was refused. One runtime failure became a total delivery outage for that agent, and the
message blamed the environment.

- [ ] Reconcile a `running`/`starting` spawn request whose terminal is stopped/failed and whose
      owning bridge is not live. `_fail_orphaned_running_spawn_requests` exists — establish
      whether it does not cover this shape or was not reached, **before** writing anything.
- [ ] Bound the gate the same way the delivery gates are bounded (see DECISIONS.md, "Delivery
      gates read raw `turn_busy`, bounded by exactly one ceiling"). An unbounded "a spawn is in
      flight" gate is the same strand class.
- [ ] Regression test asserts the operator-visible outcome: after a worker dies, the NEXT send
      must not be refused with a stale-spawn reason.

## WS-3 — Close the restart bug's second path

Documented in KNOWN_ISSUES.md with its trace. `claimed_at` distinguishes it from the path fixed in
v0.1.3: the brief is CLAIMED by the dying channel sidecar, which takes it to the grave, and it
fails at a 120s/300s backstop.

- [ ] Make the failing paths PREFER RECOVERY for a run that is `claimed` with no `delivered`
      event — requeue via `_requeue_orphaned_claimed_runs`, which already exists and is tested,
      instead of failing. Bound the retries so a genuinely undeliverable run still terminates.
- [ ] **Do not re-attempt the shape that was reverted** (`0b948d2` → `70e03aa`): superseding the
      sidecar at PTY death is one second too late to prevent the claim, and
      `_discard_superseded_active_run` then fails the run instantly with no grace, deleting the
      rescue window. Read that entry before starting.
- [ ] Answer first, with evidence: why does the sidecar report *"Delivered to Claude **resident**
      session"* for a MANAGED agent? If managed work takes the resident path, that path plausibly
      never opens a turn against the claimed run — which is the observed shape.

## WS-4 — Runtime leaks with no reaper

Two confirmed, both found by looking rather than by report.

- [ ] **`aify-gwport-*`** — 980 directories in `%TEMP%`, created at RUNTIME (the test-side leaks
      were fixed in v0.1.3 and verified at zero). Trace the writer first; a reaper written against
      a guessed writer is how the restart bug got two wrong fixes.
- [ ] **`bridge_instances` accumulation** — one agent held three non-superseded rows at once. Same
      shape as the hermes instance leak (#186) but on claude-code. This is also the most likely
      reason `_requeue_orphaned_claimed_runs` did not rescue the 22:31 run: its condition requires
      the claim bridge to be non-fresh, and a leaked row keeps reading fresh.
- [ ] **Unexplained:** the env bridge stopped after its `2026-08-06T06:45:38Z` heartbeat, and the
      boot sweep that should have reaped three orphaned gateway triads did not. Cannot currently
      distinguish "ran and failed to match" from "never reached". Capture the bridge's startup
      output on the next launch — that single artifact settles it, and no fix should be written
      before it exists.

## WS-5 — Split `api_v2.py`

**23,023 lines in one file.** This is the only item here not driven by a user-visible failure, and
it is included because it has become a first-order cost rather than an aesthetic one. Against the
project's own 500-line rule it is ~46× over.

Concrete costs paid in one session:
- Two documented line citations had silently drifted and had to be corrected; any doc that cites
  `api_v2.py:NNNN` is decaying continuously.
- A cold-start fix referenced a variable that existed in one caller's scope and not another's,
  because the callers are ~300 lines apart in a function too large to hold in view. It parsed,
  the suite passed, and it would have raised only on the failure path.
- The reconciler and its callers could not be read together, which is exactly how the
  `finished_at` guard excluded its own target rows for two months without anyone seeing it.

**Constraints — these are what make the split safe:**
- [ ] **Pure moves only, in reviewable slices.** No behaviour change in the same commit as a move.
      One slice = one seam, tests green, committed.
- [ ] **The single-worker invariant is untouchable.** `_LIVE_STATE_CACHE` / `_LIVE_SCREENS` are
      process-global; splitting must not introduce a second import path that creates a second
      cache. Assert one instance in a test.
- [ ] **Every slice ends with the container rebuilt and `aify-doctor` green.** A refactor that
      passes tests but breaks the deployed service is the failure mode this repo is built around.
- [ ] Proposed seams, by responsibility rather than by size: dispatch/run lifecycle; terminals and
      console; spawn/session lifecycle; status derivation and gathering; environments/bridges;
      messages/channels; reconcilers and reapers.
- [ ] Reconcilers are the highest-value seam to extract FIRST — they are pure-ish, individually
      testable, and are where two of this session's bugs lived.

**Explicit non-goal:** rewriting logic while moving it. If a move surfaces a defect, card it and
move on.

## Non-goals for v0.2

- **A broad code scan.** Stated above with reasons. If a specific subsystem earns suspicion from a
  live failure, audit that subsystem.
- **The remaining ~113 backlog findings.** They stay in the backlog. Pull one forward only when a
  live failure points at it — which is what promoted N7, N9–N13 and N8 into v0.1.x.
- **Dashboard feature work.** Nothing in this release is user-facing by design; it is a
  reliability and observability release.

## Watch-items carried in, not scheduled

- **Hermes moved 0.15.1 → 0.20.0.** The debug reference material describes 0.15.1 behaviour, and
  0.20.0 already broke managed spawn once (missing web UI build). Prove one real managed-hermes
  send after any hermes update; do not trust the fleet on a version bump.
- **`bridge-running` and `agent-identity` skip on Windows.** After `install.sh`, nothing verifies a
  RUNNING wrapper executes the new bridge code on this host. v0.2 item B1 (have each bridge report
  its build stamp on heartbeat) makes it platform-independent and is cheap; it is not in this
  release only because nothing has yet failed because of it.

## Open decisions — operator's call

1. **Scope.** WS-1 + WS-2 alone is a tight, high-value release that fixes the outage class seen
   this week. WS-3 and WS-4 add reliability but no new capability. WS-5 is the largest by effort
   and returns nothing user-visible. Which of the five ship in v0.2?
2. **Does WS-5 go in this release or its own?** A 23k-line split interleaved with behaviour fixes
   makes every regression ambiguous. My recommendation: WS-1/2/3/4 as v0.2, WS-5 as v0.3 with an
   empty behaviour changelog, so any breakage during the split has exactly one candidate cause.
3. **Skills as a plugin.** Raised on 2026-08-03. Skills already reach all three runtimes via
   `install.sh`, now with a `skills-installed` verifier. Shipping them *inside* the plugin needs a
   third copy of the tree (plugin roots read `skills/`, not `.claude/skills/`), and two copies
   already cost a byte-identical-mirror test. Worth doing only as "one source generates the
   others" — a real refactor, not a bolt-on. In or out?
