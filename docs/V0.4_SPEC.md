# v0.4 — Mobile alerts via ntfy

**Status: design, awaiting review.** Nothing is implemented. `V0.3_SPEC.md` says this is *"not
started until the queue contract above is written as a design and reviewed"* — this is that
document.

## What this is for

> *"i want dashboard to use notices system. so i can allow notices on desktop and mobile and then i
> would hear when i would get message from agent."*

v0.3 shipped the desktop half: a browser Notification raised from the dashboard's existing `/ws`
socket, with no server change at all. It only works while a tab is open. This is the other half —
the operator's phone, with no tab, no browser, and no laptop awake.

Web Push is the wrong tool for it: service worker → secure context → TLS on a LAN address, for a
service explicitly run locally in a container. **ntfy is one outbound POST.** No PWA, no VAPID, no
subscription table, no service worker.

## The delivery contract

This is the part that has to be right, and the reason there is a spec at all. The reviewer refused
my first phrasing — *"fire-and-forget with a bounded timeout"* — because that sentence permits
awaiting an HTTP call on the message-send path. It hooks the fleet's hot path: 3,883 messages in
14 days. An external network dependency there can delay or fail the very message it is reporting.

### C1 — enqueue after commit, never before

The enqueue point is fixed by code that already exists. Both send handlers already do their work,
`await db.commit()`, and *then* broadcast:

| path | line | what it already broadcasts |
|---|---|---|
| direct message | `api_v2.py:17147` | `message_sent {id, from, to, subject}` |
| channel message | `api_v2.py:22326` | `channel_message {channel, from, body}` |

The ntfy enqueue goes beside those broadcasts, post-commit. A notification is therefore never
raised for a message that did not persist, and the enqueue cannot roll back a transaction.

### C2 — the enqueue itself cannot fail the send

`queue.put_nowait()` on a **bounded** `asyncio.Queue`, wrapped so a full queue drops the
notification and logs a counter rather than raising into the send handler. Dropping an alert is
correct; failing a message because an alert could not be queued is not.

**Bound: 256.** At the measured cadence (~277 messages/day fleet-wide, of which operator-addressed
is a small fraction) a queue that reaches 256 pending means the worker is wedged, and the right
behaviour then is to shed, not to grow.

### C3 — the worker owns the network, and the timeout

One `asyncio.Task` started at app startup, cancelled at shutdown. It drains the queue and performs
the POST with `timeout=5s` **in the worker**. Nothing on a request path ever awaits ntfy.

Single-worker uvicorn is already a hard constraint (`_LIVE_STATE_CACHE`), so one in-process task is
correct and needs no coordination. Recorded here because it is one more thing that breaks under
`--workers > 1`.

### C4 — failure is logged and dropped, and the relay's own health is observable

No retry, no backoff queue, no dead-letter table. A failed alert is a missed alert. Retrying a
notification about a message that is already delivered and visible in the dashboard buys nothing
and risks a storm against a third-party host while the fleet is busy.

**A failure counter alone does not retire "a wedged worker is visible" — review caught that.** A
worker that stops draining produces *no* POST failures at all; the queue simply fills until C2
starts shedding, and the counter stays at zero throughout. So `/health` (today just
`{"status": "healthy"}`, `health.py:94`) gains an ntfy block:

| field | the question it answers |
|---|---|
| `enabled` | is the feature even on |
| `workerAlive` | is the drain task running, or did it die/never start |
| `queueDepth` | is it draining, or filling |
| `droppedFull` | how many alerts were shed — a silent drop is not acceptable |
| `sendFailures` | is the URL/host broken |
| `lastSuccessAt` / `lastFailureAt` | when it last worked, which a counter cannot say |

The block carries **no URL**, redacted or otherwise, and a test asserts the raw value appears
nowhere in it. Same rule as everywhere else in this repo: a check that cannot detect the failure it
exists for is not a check.

### C4b — the enqueue function must not be `async`

Review's point, and it is about people rather than code: if the public entry point is `async def`,
someone eventually writes `await` in front of it and reintroduces exactly the bug this contract
exists to prevent — silently, because it will still work. A plain `def` cannot be awaited by
accident. Pinned by a test that asserts the function is not a coroutine function.

### C5 — coalescing, on the same measurements as v0.3, and it happens BEFORE the queue

Same 90-second window, same key (`sender + subject`, not message id — keying on the id coalesces
nothing during exactly the ping-pong burst this exists to collapse). Volume is the failure mode
that kills a notification feature; the desktop side is already shaped around it and the phone has
less tolerance, not more.

**The location matters and the first draft left it open.** Coalescing must happen in the
synchronous enqueue path, *before* `put_nowait` — not in the worker. Worker-side coalescing still
lets a ping-pong burst consume queue slots and push the bound toward shedding real alerts, so the
collapse would happen after the damage. A duplicate inside the window returns without queueing at
all; a distinct key updates the map and then attempts `put_nowait`. Pruning happens in that same
path. None of this touches the network or awaits anything, so C1–C3 still hold.

### C5b — disabled means no state churn

With no URL configured the enqueue returns before the coalesce map or the queue is touched, so an
off feature leaves no trace to reason about. Tested, because "off" that still mutates state is how
a feature that is supposedly disabled ends up in a bug report.

### C6 — the URL is a secret

`AIFY_NTFY_URL` in `.env` **only**. Never `config/service.json` (which is generated and not
gitignored in the same way), never a settings row, never a log line, never a `/settings` response.
Anyone holding an ntfy topic URL can read every notification sent to it, and can publish to it.

- absent or empty ⇒ the feature is **off**, and off is the default;
- redacted to `ntfy:<host>/<topic-sha8>` anywhere it is displayed;
- a test asserts the raw value appears in no response body and no log record;
- **never log an exception object from the HTTP client.** Review's catch: client libraries put the
  request URL in `str(exc)`, so `logger.warning("ntfy failed: %s", exc)` leaks the credential into
  a log file precisely when something is going wrong. Log the exception *class* and status code
  plus the redacted identity, never the object.

### C7 — what qualifies (and the duplication it forces)

Only what the operator was actually sent:

- `message_sent` where `dashboard` is among the recipients;
- `channel_message` for a channel `dashboard` has actually joined — checked against
  `channel_members`, which the server can answer exactly.

**This duplicates `notify.mjs`'s `isForOperator` in Python, and that is a known cost, not an
oversight.** Audit finding 2 was precisely this: `comms_search` existed in two languages, I fixed
one and believed I was done. The mitigation that worked three times is an agreement test, not
consolidation — a table of `(event, payload) → should_notify` cases asserted against BOTH the
Python predicate and the JS one, failing when they diverge.

One deliberate asymmetry, with the reason recorded: the browser **fails closed** on channel
membership because its channel list loads asynchronously and is unknown early in a session. The
server has no such gap — it reads `channel_members` directly. So the server may notify for a joined
channel in a case where the browser would have stayed quiet. That is not drift; it is the server
knowing something the client does not, and the agreement test must encode it as an allowed
difference rather than assert identical outputs.

### C8 — no new surface for the operator to manage

No settings UI, no per-agent rules, no quiet hours. `.env` var set = on, unset = off. If it turns
out to need tuning, that is evidence for a later release, not a guess now.

## Testing

| test | what would otherwise ship broken |
|---|---|
| enqueue is post-commit | a notification for a message that rolled back |
| the enqueue function is not a coroutine function | someone `await`s it later and the bug returns |
| full queue drops, does not raise | ntfy outage failing fleet messages |
| coalescing happens before `put_nowait` | a burst eats queue slots and sheds real alerts |
| disabled ⇒ no coalesce-map or queue mutation | an "off" feature that still accumulates state |
| health reports queue depth and worker liveness | a wedged worker with a zero failure counter |
| health block contains no URL | the credential leaking through the diagnostic surface |
| worker owns the timeout | an `await` on the send path — the exact bug the reviewer caught |
| failure is logged, never retried | a retry storm during a busy fleet |
| coalescing window + key | the volume failure that switches the feature off |
| URL absent ⇒ disabled | accidental on-by-default |
| URL never in a response or log | leaking a credential that grants read AND write |
| agreement with `notify.mjs` | audit finding 2, one language fixed and believed done |
| channel gate uses real membership | notifying on channels the operator never joined |

## What this release is NOT

No PWA, no service worker, no VAPID, no push subscription table, no per-agent notification rules,
no quiet hours, no retry queue, no notification history. Every one of those is a plausible next
step and none of them is needed to hear a phone buzz when an agent messages you.
