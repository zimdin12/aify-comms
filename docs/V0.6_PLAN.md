# v0.6 plan — what v0.5.x deliberately did not do

v0.5.x was the refactor line: every non-test source file under 1000 lines, the reconcilers off the carrier,
and the verification gaps that decomposition exposed. That work is done and measured (see the bottom of this
file). This file is the queue of things that were **found** during it and are **out of scope for a refactor
line** — each one needs a decision before it becomes work.

Nothing here is started. Where a section says what exists today, it was measured on 2026-08-17, not recalled.

---

## 1. Separate the harness wrappers into a standalone dependency (operator ask)

**The ask.** `claude-aify`, `hermes-aify`, `codex-aify` become a standardized harness wrapper that
aify-comms *depends on* rather than *contains* — installable on its own, and usable by **other services**
so they can send data and read status through the same surface.

**What exists today, measured:**

- The wrappers are **generated text**, not a package. `install.sh` (4,370 lines) emits them from 14
  heredocs — a bash script per POSIX runtime, a `.ps1` for hermes, plus `.cmd` shims on Windows. They are
  written into `~/.local/bin` (or the Windows equivalent) at install time.
- There is **one** npm package: `mcp/stdio/package.json` is `aify-comms-mcp` v0.5.4, `bin:
  aify-comms-mcp → ./server.js`. The MCP server, the runtime adapters, the delivery loops and everything a
  wrapper needs all ship inside it.
- `install.sh` copies `mcp/stdio` + `node_modules` into `~/.aify-comms` and points every wrapper and MCP
  config at that native copy (the 9p/WSL2 load-time fix). So a wrapper's "dependency" is already a
  *directory copy*, which is the closest thing to separation that exists.
- No `wrappers/` or `packages/` directory. No design doc. The term "standardized wrapper" does not appear
  anywhere in the repo.
- **The one precedent worth copying:** `integrations/hermes-aify-plugin/` is a real, separable Python
  package with its own `sitecustomize.py` and `gateway_patch.py`. It shows the shape — an integration that
  a host installs and aify-comms merely expects to be present.

**Verdict: not done, not started, not specified.** It is a genuine v0.6 item.

**What has to be decided before it is work** (these are the questions, not answers):

1. **What is the wrapper's contract to a NON-aify-comms host?** Today a wrapper does four things: resolves
   the runtime CLI, exports the agent identity env (`AIFY_AGENT_ID`, `AIFY_RUNTIME`, …), points the MCP
   config at the bridge, and launches the runtime. Only the first is service-agnostic. "Send data and get
   status" means the wrapper needs a declared endpoint/key/identity contract that does not assume
   aify-comms is the consumer — i.e. the bridge's registration + heartbeat + status surface becomes a
   *published protocol*, not an internal one.
2. **Where does the line fall — wrapper, or bridge?** The wrapper is ~100 lines of shell; the value is in
   `mcp/stdio` (the bridge). If other services want status and data, they want the BRIDGE, and the wrapper
   is just the launcher. Splitting the launcher alone would be cosmetic. This is the central question.
3. **Versioning.** `VERSION` is single-source today and a test enforces it across five files. A separately
   installable wrapper introduces a second release cadence and a compatibility matrix — the thing the
   single-source rule exists to prevent. Needs an explicit compat policy (wrapper N works with bridge
   N±k).
4. **Distribution.** npm package, or a copied dotfolder as now? `install.sh` currently guarantees the
   wrapper and the bridge are the same build; a standalone install breaks that guarantee, and
   `aify-comms doctor`'s `bridge-installed` / `bridge-current` checks exist precisely because that
   guarantee kept being violated silently.

**Suggested first step, if approved:** write the wrapper↔host contract as a spec before moving any file —
what a host provides (endpoint, key, identity, cwd), what it gets (registration, heartbeat, status, dispatch
delivery), and what is explicitly NOT part of it. The refactor is easy once the contract is named; doing it
in the other order produces a wrapper still shaped like aify-comms.

## 2. Make the delivery loops testable (structural, found by measurement)

A V8-coverage census over `mcp/stdio` (run the bridge suite under `NODE_V8_COVERAGE`, merge the per-process
JSONs, report named functions whose first range has `count: 0`) went **192 → 122** during v0.5.4 as the gaps
were closed. What remains is not neglect:

| Where | Functions | Why unreachable |
|---|---|---|
| `server.js` | 27 | Loop starters, heartbeats, detector stoppers, `cleanupOnExit` — reachable only by BOOTING the bridge, which registers agents and supersedes the live environment bridge |
| `hermes-delivery-loop.mjs` | 11 | Closures inside `runDeliveryLoop`; needs a live gateway + service |
| `claude-channel.js` | 11 | The channel sidecar's poll loop internals |
| `dispatch-loop.mjs` | 10 | Closures inside `runDispatchLoop` |
| `hermes-managed-gateway-session.js` | 9 | The socket half — `ensureStarted` spawns `hermes dashboard` |
| `terminal-runtime.js` | 9 | Real node-pty PTYs |
| `hermes-channel.js` | 7 | Same shape as claude-channel |
| callbacks handed into the above | ~20 | `terminal-manager`, `virtual-terminals`, `spawn-triggered-agent`, per-controller `onPoolEvent` |
| reapers | 5 | Declined on safety: reaching them needs `AIFY_ENVIRONMENT_BRIDGE` set (which once reaped seven live gateway hosts) or real killers on the operator's machine |
| POSIX-only | 4 | `killPid`, `pidIsAlive`, `descendantPids`, `findOnProcessPath` — covered on Linux, unreachable on win32 |

**The finding:** these are closures created inside functions that never return. They are **untestable by
construction, not by neglect** — the same shape as the original v0.5 finding that logic inside a 20k-line
module can only fail in production. The delivery loops are the heart of the product and are verified today
only by a manual two-session live round-trip.

**The work, if approved:** extract each loop BODY (one tick) behind an injectable seam, the way the
reconcilers were extracted from the carrier — `runOneDeliveryTick({ deps })` with the loop reduced to a
scheduler around it. Standard as before: byte-identical bodies, the module exports what it extracts, real
unit tests that call it. This is a v0.6-scale decomposition, not a test-writing task.

**Also measured, for the same reason:** the dashboard's own census is **78 never-called of 492** (84%), and
unlike the bridge's remainder, much of it IS reachable — `shared-files` delete/attach/paste, the notify
gating predicates, `realtime-socket`'s message handler. That is ordinary test work, not a v0.6 item.

## 3. Two pinned findings awaiting a ruling

Both are recorded in the tests that found them, deliberately unfixed, because each changes behaviour on a
delivery path.

**A. The hermes ACP sub-mode declares a steer it rejects.** `hermes-managed-controller.js` documents
"ACP-backed (default): interrupt supported, steer rejected" and its constructor reads like a ternary
enforcing that — but `adapters/hermes.js` declares `supportsSteering => true` unconditionally, so both
branches evaluate to the same object and the ternary changes nothing. The ACP path reports `steer: true`
while its own `steer()` throws.

*Reach, measured:* the `capabilities` key of the legacy `start()` shape has **no reader** — `dispatch-loop`
consumes `.promise` alone — and what the control plane acts on comes from `defaultCapabilitiesForRuntime` at
registration plus the service-side strip of managed-hermes `steer` (`af9e937`, which fixed the real
incident). So it costs nothing today. It is a field that reads as authoritative and is not.

*Why not fixed:* narrowing a declared capability touches steer-vs-queue routing for every hermes agent and
overlaps the open WS-3 steer-vs-queue decision. Pinned in `tests/hermes-controller-routing.test.js`.

**B. A codex routing term that cannot change the route.** `codex-controller.js` computes
`hasWsAppServer = (resident || channel) && hasCodexLiveAppServer(cfg)` and uses it only in
`executionMode === "managed" && !hasWsAppServer` — where the mode test has already excluded resident and
channel, so the term is always true. `getRuntimeConfig` and `hasCodexLiveAppServer` cannot affect which
controller is picked. The decision that matters is made inside `CodexLegacyController.start()` on the same
config (`codex-legacy-controller.js:92`).

*Why not fixed:* deleting it is behaviour-preserving, but it is a reviewer's edit rather than something that
should arrive inside a test slice. Equivalence pinned in `tests/codex-controller-routing.test.js`.

## Where v0.5.x actually ended (measured 2026-08-17, not recalled)

- **Zero** non-test source files at or over 1000 lines. `oversized-allowlist.json` is EMPTY and both gates
  (Python + JS) treat an empty list as exempting nothing.
- `control_plane.py` 6.7k → **894**; `app.js` 5,081 → **987**; `server.js` 6.3k → **920**.
- Reconciler → carrier imports: **0**, enforced by `test_leaves_do_not_import_the_carrier.py` with a
  ceiling of 0 that fails if left slack.
- Suites: python **3988** (+7834 subtests) · bridge **316** suites · dashboard **1020**.
- Bridge coverage census: 192 → **122** never-called; dashboard census established at **78/492**.
- Four real defects found and fixed because something was flagged as untested: `disposeAll` disposed
  nothing; codex `thread/list` answered under `data` and one reader saw only `threads`; a contention
  predicate matched `"locked"` inside `"blocked"`; `Number(x||0)` let a non-numeric token count become NaN
  and poison a session total. Two dead functions removed.
- **Not deployed.** At the time of writing the container still serves pre-v0.5.4 code and the branch is 578
  commits ahead of `origin/main`, so none of those fixes is live.
