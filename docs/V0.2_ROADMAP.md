**Status:** proposed. Written 2026-07-26, after v0.1 shipped at `59db55b`.

**PARTLY SHIPPED as v0.1.1 (2026-07-29).** Deployed and tagged, so this file is no longer
all-future. Done since it was written:
- **N7** (degraded-environment stop) — the hotfix this file recommended taking ahead of the release.
- **C8's honesty half + the real input-path defects behind it** — the dashboard wheel handler was
  bypassing the serialized input queue AND firing on hover, injecting synthetic arrows into whichever
  agent's PTY the pointer was over. That, not the console-input endpoint, was corrupting drafts.
- **C9's actionable half** — mouse traffic no longer reaches the PTY from a wheel gesture.
- **Wrapper symmetry** — `codex-aify` now recovers its agent id from a bare `--resume`, the gap
  `hermes-aify`'s own comment had admitted; plus a `comms_register` warning for identity-less
  residents, which is the runtime half of the same problem.
- A round of operator-reported chat/session UX defects (sticky queue mode, subject echo, composer

Still open and unchanged: **WS-1** (the `api_v2.py` carve and its duplicate-rule guard), **WS-3**
(Windows-real deploy verification / bridge build stamp on heartbeat), **WS-9** (`aify-comms` as a

This is the *plan*. The *findings ledger* is [V0.2_PLAN.md](V0.2_PLAN.md) — every item there was

referenced by their ledger id (A1b, B1, C6 …) rather than restated.

## What v0.2 is for

v0.1 was a **stability** release: a safe revert point, service-breaking defects only. It took
**five review rounds**, and the shape of those rounds is the argument for this release:

| Observation from the v0.1 series | What it says |
|---|---|
| Every one of the 14 defects passed a green suite (958–986 tests) | Green is not evidence in this repo |
| Two defects were *inside fixes I had just written and verified* | The risk is in the contract around a change, not the change |
| One rule (`terminal is not active`) was implemented **twice**, and the first fix landed in only one copy — changing nothing | Duplicate rules are undetectable by review at this file size |
| `api_v2.py` is **22,889 lines** — 44× the repo's own 500-line guidance | Nobody, human or agent, holds it in context |

So v0.2 is a **structural and observability** release. Not a feature release, and deliberately not
"the v0.1 nits." Four things earn the version bump:

1. **Close the honesty gaps that cost real operator time** — the console submit that reports success
   on input the TUI never acts on (WS-2), and the fact that on the primary dev host *nothing* verifies
   a running bridge is the installed bridge (WS-3).
2. **Give the operator somewhere to look.** There is no live terminal view of the fleet, and the
   container layer reports a heartbeat and almost nothing else. Every incident this month was
   diagnosed by hand-writing SQL against the container. WS-9 turns `aify-comms` itself from a rolling
   log into a live status screen, and WS-10 makes the container layer diagnosable; both also answer
   "what do agents read?" — same derivation, two renderings.
3. **Pay down the file that caused the defect run** (WS-1). Every recurring defect class here — a
   rule implemented twice, a named set reused for the wrong purpose, a picker that shadows a live row
   with a dead one — is a symptom of a module too large to reason about. Three of this round's own
   findings (N1, N2, N3) are that class.
4. **Port what an upstream with the same problem already solved** (WS-4), from a direct read of
   hermes' dashboard-embedded terminal.

See "Release sequencing" for what actually ships in v0.2.0 — WS-1's carve is deliberately *not* the
gate, and the reasoning for that changed after the first draft.

## Ground rules (carried from v0.1, non-negotiable)

- **Never state a deployed build sha in a commit, tag or doc.** `service/_build_stamp.json` is
  gitignored and untracked, so `GET /version`'s sha is host-local state. Three review rounds were
  burned arguing `f291161` vs `5885eef`; both were right about their own machine.
- **Single-worker uvicorn.** `_LIVE_STATE_CACHE` and `_LIVE_SCREENS` are process-global. WS-1 must
  not change that, and must keep cache ownership in exactly one module.
- `bash scripts/stamp.sh` **before** `docker compose up -d --build`.
- Bridge changes need `install.sh` **and** a wrapper relaunch. On Windows nothing proves the
  relaunch worked — that is WS-3.
- Skill mirrors `.claude/skills/` and `.agents/skills/` stay byte-identical.
- **The suite must be green on Windows**, not only on Linux (E2). The installer-contract test was
  red on the primary dev host for the entire v0.1 series.

## New findings from this round

Eight. N1–N3 are session/console state, N4–N6 are containers, **N7 was a live defect found by
review — FIXED and shipped in v0.1.1**, and **N8 is a live defect found by a teammate on 2026-07-31**.

Two are bugs I did **not** file — N2, and the container restart-loop at the end of N6 — because the
code contradicted a plausible reading. And **N4 is a finding a reviewer corrected**: I asserted it
from a truncated read of the very function I was citing. Both directions are recorded rather than
tidied away, because the failure mode of this document is confident prose over unverified claims.

### N1. The session-status vocabulary is aspirational, not actual — and it has already caused two defects

Measured against the live DB (read-only, 149 `agent_sessions` rows of real history):

```
agent_sessions.status    → ended 82 | stopped 51 | running 10 | lost 4 | failed 2
agent_sessions.terminal_status → '' 134 | attached 9 | stopped 6
```

**Five values.** But the file defines three overlapping sets naming eleven:

- `_LIVE_SESSION_STATUSES = {starting, running, recovering, restarting, cli-takeover}` (`api_v2.py:379`)
- `LIVE_SESSION_STATUSES = {running, attached, active, idle, starting, recovering}` (`:394`), whose
  docstring claims it is "the FULL set of `agent_sessions.status` values that count as live"
- `ENDED_AGENT_SESSION_STATUSES` (added in v0.1 as the documented complement of the above)

`attached`, `active` and `idle` **never appear in that column** — `attached` is written to
`terminal_status` (`:3472`), a different column. So `LIVE_SESSION_STATUSES`' docstring is wrong
about its own subject, and every `status IN (...)` list built from it carries dead branches.

This is not cosmetic. It has produced two shipped defects already:
- **slip 6:** `_SESSION_DELETE_ALLOWED_STATUSES` (a deletion allowlist) reused as a hide-from-list
  set, breaking `comms_restart` / `comms_compact` / Restart / Reset / Compact;
- **R2c:** `_current_agent_session_row` promoting only four statuses in its `ORDER BY`, so a live
  session lost the `last_seen` tiebreak to a fresher corpse.

Both are the same failure: reasoning about a vocabulary nobody had measured.

- [ ] Pin the ACTUAL vocabulary with a test that asserts the set of values any writer can produce,
      derived from the writers, not from the constants.
- [ ] Delete phantom members, or — if a writer is *supposed* to produce them and doesn't — file that
      as the real bug. Decide by reading the writers, one at a time.
- [ ] Only then simplify the three sets. Not before: a set's name encodes its purpose and collapsing
      them is exactly the move that broke `comms_restart`.

### N2. `assign_agent_environment` marks the wrong set 'lost' — LATENT, not live. Filed as a trap, not a bug.

`POST /agents/{agent_id}/environment` (`api_v2.py:14286`) rewrites `environment_id` for **every**
session row of the agent (`WHERE agent_id = ?`, no id filter), but only marks 'lost' those whose
status is in `{starting, running, recovering, restarting}` (`:14415-14416`) — the narrow
`_LIVE_SESSION_STATUSES` minus `cli-takeover`, not `LIVE_SESSION_STATUSES`.

I was about to file this as a live defect: a session with status `attached`/`active`/`idle` would
survive with a live status while its `environment_id` now points at an environment it never ran on,
and `_current_agent_session_row` accepts exactly those statuses as current — so the picker would
answer with a session claiming to live on a bridge that does not own its PTY.

**N1's measurement says that cannot currently happen.** The only live value the column takes is
`running`, which *is* in the narrow set, so live rows do get marked lost. The defect is unreachable
today and the code is correct in practice.

It stays on the list as a **trap**: the moment any writer starts producing `attached`/`active`/`idle`
in that column — which `LIVE_SESSION_STATUSES` actively invites — this UPDATE silently stops marking
them lost, and the failure is a session pointing at the wrong bridge. Recording it so the next
reader does not have to re-derive it, and so N1 has a concrete consequence attached.

- [ ] No code change until N1 settles the vocabulary. Then either widen this set or delete the
      phantom statuses that make it wrong.
- [ ] Note the adjacent `SELECT id FROM agent_sessions WHERE agent_id = ? ORDER BY last_seen DESC
      LIMIT 1` a few lines below (`:14423`) — newest-by-`last_seen`, **no status filter**. Same
      shadowing shape as R2c. Harmless only because of what N1 measured.

### N7. **FIXED** (hotfix) — a `stop` in a DEGRADED environment was still cancelled, permitting a duplicate worker

Reviewer finding, independently verified, **now fixed** — see DECISIONS.md,
*"This environment's bridge can act" has ONE definition*. This was the same worker-duplication chain
v0.1 claimed to fix **at the root**, still open for degraded environments — the third consecutive
round in which my fix covered the narrow case.

**Reachability, measured before fixing** (the discipline the last three rounds cost me): the live
fleet's `environments.status` holds only `{online, offline, forgotten}`, and **no bridge reports
`degraded`** — it arrives only from an explicit registration or a status write, and nothing derives
it. So this was latent-but-reachable rather than firing today, which is why it shipped as a normal
reviewed hotfix rather than an emergency. It was fixed anyway: eleven gates accept `degraded` and the
sweeps did not, and a disagreement that wide gets reached eventually and silently.

**Two divergences closed, not one.** Raw `status = 'online'` also never *ages*, so a silent ONLINE
bridge kept its controls pending indefinitely while `api_v2` already treated that environment as
offline. The tests pin both — and the stale-online subtest failed before the fix, which is how that
second divergence was found rather than assumed.

**Scope held deliberately.** While verifying I found `api_v2.py:15436` — an environment-inference
fallback whose `ORDER BY CASE WHEN status = 'online' THEN 0 ELSE 1 END` puts `degraded` in the same
tier as `offline`, so a fresher offline env outranks a degraded one on the `last_seen` tiebreak. Same
tiered-ORDER-BY shape as R2c and N2. **Not touched:** it is an inference heuristic I have not traced,
its blast radius is which `environmentId` gets guessed when nothing else is known, and bundling an
untraced behaviour change into a hotfix is how the last three rounds went wrong.
- [ ] Trace `api_v2.py:15436`'s five-ish callers, then decide whether `degraded` belongs in tier 0.

The asymmetry, both halves confirmed in code:

- **Reachability accepts degraded.** Eleven gates in `api_v2.py` test
  `env_status in {"online", "degraded"}` (`:1032`, `:2159`, `:3033`, `:4182`, `:5046`, `:5063`,
  `:5121`, `:7604`, `:7764`, `:8709`), and `_ENVIRONMENT_HEARTBEAT_STATUSES = {"online","degraded"}`
  (`:4075`). So a degraded environment keeps heartbeating and its bridge stays **live and working**.
- **Both reconcile sweeps require `online`.** In `db.py` (the stop re-target and the env-currency
  failure sweep, ~`:782-823`) every `environments` subquery carries `AND environments.status = 'online'`.

So for a degraded environment: the re-target finds no online row and **cannot rescue** the stop, and
the failure sweep's `NOT EXISTS (… status='online')` is satisfied and **fails** it. The full chain:

```
Stop worker → terminal 'stopping', stop queued
  → env is degraded (still heartbeating, bridge still working)
  → re-target finds no ONLINE row, does not fire
  → failure sweep fails the stop      ← the PTY is never killed
  → session written 'ended'
  → Start is permitted → SECOND worker, old PTY alive
```

Identical to the chain fixed in v0.1, reached through `degraded` instead of through a changed
`bridge_id`. And it is worse than a plain strand: the bridge in a degraded environment is alive and
*could* have executed the stop.

- [ ] Make the two sweeps agree with the reachability gates: use `{online, degraded}` where the
      question is "can a bridge act on this?". Do **not** narrow the eleven gates instead — that would
      make degraded environments undeliverable, and a too-strict gate is what made the whole `ef-`
      team unstartable in v0.1.
- [ ] Fix in **both** implementations. The `api_v2` / `db.py` duplication is a recorded invariant
      (DECISIONS.md), and landing a terminal-control fix in only one of them is precisely the slip
      from the last round.
- [ ] Test the degraded case explicitly, per environment status, including that a stop in an `offline`
      environment still fails (the accumulation bound must survive).
- [ ] **Candidate for a v0.1.x hotfix rather than v0.2.0.** It is the same class as what v0.1 shipped
      to fix, the fleet runs degraded environments in practice, and the failure mode is a leaked PTY
      plus a duplicate worker. Operator's call on timing; my recommendation is hotfix.

### N8. **NEW** — the cold-start refusal names a cause it never checked

Reported live 2026-07-31 by graph-tech-lead after double-restarting ef-manager: the bridge said
*"no online environment can host managed claude-code for this agent"*, while the Windows environment
was online and advertising claude-code. They checked, concluded the message was wrong, and were
right.

**Verified against the live DB:** `windows:StevenZ-L:default` is `online`, `last_seen` fresh, and its
`runtimes` array contains `{"runtime": "claude-code", "modes": ["managed-warm"], "available": true,
"unavailableReason": ""}`. The message's claim was false.

**Mechanism.** `api_v2.py:16267` calls `_coldstart_spawn_request_for_dispatch(...)` and renders ONE
message for a bare `False`:

```python
coldstarted = await _coldstart_spawn_request_for_dispatch(...)
if not coldstarted and not await _has_claimable_spawn_request(db, recipient_id):
    not_started.append(... f"No online environment can host managed {runtime} for this agent ...")
```

But that function returns `False` from at least FOUR distinct causes, and its own docstring says so:
- the runtime is not in `{claude-code, codex, hermes, opencode, pi}`;
- **the agent is `session_mode='resident'`** — a deliberate resident-safety refusal, added 2026-07-06
  precisely so an auto-cold-start cannot fork a managed twin beside a resident;
- a claimable spawn request already exists;
- no environment can actually be resolved — the ONLY case the message describes.

So the operator is told to go fix their environments no matter which of the four fired. In this
incident the environments were healthy; the refusal came from transitional session state during the
double restart. The message sent a competent agent to investigate the one thing that was fine.

This is the same class as the v0.1 fixes and as C8: **a report asserting a cause it did not verify.**
It is cheap to fix and it directly cost an agent time today.

- [ ] Return a REASON (small enum), not a bare bool, from `_coldstart_spawn_request_for_dispatch`.
- [ ] Render the actual reason: "this agent is resident — switch it to managed first", "a spawn is
      already in flight", "runtime X is not cold-startable", "no online environment advertises X".
- [ ] Test each branch produces its own message. The bug is that four causes share one sentence, so
      a test that only covers the environment case would not have caught it.
- [ ] Check the sibling call site (`api_v2.py:16401`) — same sentence, same conflation.

### N3. `_resolve_live_console_terminal`'s two branches disagree about `stopping`

`api_v2.py:13931`. The pointer branch accepts any terminal whose status is not in
`_TERMINAL_END_STATUSES` (a complement), so it accepts `'stopping'`. The fallback branch uses an
explicit allowlist `('starting','attached','running','active','idle','recovering')`, which excludes
it. So `comms_console_input` / `comms_console_tail` can resolve onto a terminal that is being killed,
but only via the pointer.

Low blast radius, and it matters more after v0.1 than before: `'stopping'` rows now legitimately
persist while a queued stop is outstanding (R2a), so this is a live window rather than a
theoretical one. Writing input into a PTY being torn down is never right.

- [ ] Make both branches use the same allowlist. One-line change; needs a test that the pointer
      branch declines a `'stopping'` terminal, because the SQL alone will not express it.

### N4. Container state is partly discarded at the API boundary — **CORRECTED, was overstated**

**The first version of this entry was factually wrong and a reviewer caught it.** I claimed
`list_containers()` returns *none* of the diagnostic fields, including `error_message`. It does
surface it: `if state.error_message: entry["error"] = state.error_message` (`manager.py:353-354`).
I read `list_containers` from `:331` to the `idle_seconds` line, took that for the end of the dict
build, and asserted from the truncation. It was three lines further down. Same slip as concluding
from one table — **partial evidence read as complete evidence** — and it is why the entry is left
here corrected rather than quietly edited.

What is actually true, and it is narrower but still real:

- **The health-monitor path produces a reasonless `FAILED`.** `_health_loop` sets
  `state.status = ContainerStatus.FAILED` (`:443`) **without** setting `error_message`. Every *start*
  failure path does set it (`:228` health-check timeout, `:238` image-not-found with the exact
  `docker pull`, `:248` start-cancelled, `:261` generic), so the gap is specific to a container that
  was healthy and then failed its checks — which is the common runtime case rather than the boot case.
- **`consecutive_health_failures`, `started_at`, `last_request_at` and `container_id` are still not
  exposed.** So a container failing **2 of 3** health checks remains byte-for-byte identical, to every
  reader, to a healthy one. That half of the finding stands and is the substance of N5.

- [ ] Set `error_message` on the health-monitor transition, so a `FAILED` container always carries a
      reason no matter which path failed it.
- [ ] Expose `consecutive_health_failures`, `started_at`, `last_request_at`, `container_id`. No new
      state and no new computation — stop discarding what is already known.

### N5. There is no DEGRADED container state, so the signal is binary and late

The health loop keeps a container at `RUNNING` until `consecutive_health_failures >= retries`, then
jumps straight to `FAILED` and restarts (`manager.py:441-446`). `ContainerStatus` has six values and
none of them means "up but failing checks". So the observable story is *fine → dead*, with the
interesting interval invisible. This is the operator's "they just roll some heartbeat", precisely.

- [ ] Add a derived DEGRADED reading (`RUNNING` **and** `consecutive_health_failures > 0`). Derive
      it — do not add a seventh stored status. The status column is written from several paths and a
      new writable value is how the session-status vocabulary got into the N1 mess.
- [ ] Keep a small in-memory ring buffer of container transitions. A crash-restart cycle currently
      leaves **no trace at all** once the counter resets on the next good check, so "restarted 3× in
      the last hour" — the single most useful container fact — is unavailable everywhere. Process-global
      and single-worker, consistent with `_LIVE_STATE_CACHE`.

### N6. Per-container `health_check.interval_seconds` is configured and then ignored

`_health_loop` sleeps a hardcoded `await asyncio.sleep(10)` (`manager.py:420`). The configured
`interval_seconds` is honoured **only** during startup, by `_wait_for_health` (`:218`). So a
definition that sets a 60s interval is checked every 10s, and one that wants 5s cannot get it.

- [ ] Honour the per-container interval, or delete the field. A knob that silently does nothing is
      worse than no knob.

**Checked and NOT a defect** (recording it so nobody re-derives it): I expected a 10s restart loop —
the health loop sets `FAILED` and calls `restart_container` without resetting
`consecutive_health_failures`, so if the restart returned early the next tick would restart again
immediately, forever. It cannot: `restart_container` → `start_container` blocks on `_wait_for_health`
up to `startup_timeout_seconds` and sets the counter to `0` on success (`:225`), and raises on
failure. Slow-booting containers (vLLM, LocalAI) are safe.

## What the hermes study found

Read directly from the hermes 0.19.0 editable checkout on this host
(`~/AppData/Local/hermes/hermes-agent`), which embeds `hermes --tui` in its own dashboard over a
PTY — the same problem as our Session Console. Their path is
`web/src/pages/ChatPage.tsx` → `WebSocket /api/pty` → PTY → `ui-tui/dist/entry.js` + `tui_gateway`.

**Already ported** (the 2026-07-02 upstream study, task #237 — our code carries `hermes parity`
comments and matches): wedged-`CONNECTING` force-close on a budget, resume-signal reconnect throttled
across `visibilitychange`/`pageshow`/`focus`/`online`, capped exponential backoff, emit-resize-only-on-change,
double-rAF authoritative fit, Unicode11 + `allowProposedApi`, OSC 52 clipboard, `scrollback: 5000`.
Not re-litigating those.

**Worth taking** (verified deltas, four items — see WS-4):

1. **The burst-then-Return write discipline.** This is the big one and it lands on C8, not on the
   dashboard. `ChatPage.tsx:445-454` sends a slash command as text, waits **100 ms**, and *then*
   sends `\r` as its own frame. The comment states the reason: 100 ms is "safely past Node's default
   stdin coalescing window", so Ink's tokenizer "emit[s] a keypress event for each character (not
   coalesce them into a paste)". They do the same again for `/image` (`:587-591`) and for the
   `?learn=` seed (`:985`). It is a deliberate, load-bearing, thrice-repeated discipline.
2. **WebGL gated on width.** `const useWebgl = terminalTierWidthPx(host) >= 768` (`:772`), because
   the WebGL glyph atlas is sized in *device* pixels and renders visually much larger cells than
   `fontSize` implies on phones and in DevTools device mode. Ours loads WebGL unconditionally
   (`app.js:1888`).
3. **A close-code contract with UI for each outcome.** `4410` = the agent process exited → write
   `[session ended]` and render an explicit "Start new session" affordance; `4409` = superseded by a
   newer tab → stay quiet; `4401/4403/4404/4408` each get a specific banner, and *every* close logs
   `code` + server-supplied `reason` so a "chat won't connect" report is diagnosable without server
   access (`:1001-1069`). Our main dashboard socket's `onclose` (`app.js:535`) takes no argument at
   all; only the codex *synthetic* console prints a code (`app.js:2398`).
4. **Lifecycle predicates as pure, separately-tested modules.** `lib/pty-reconnect.ts` +
   `pty-reconnect.test.ts`, `lib/pty-mobile-input.ts` + test, `lib/chat-activation.ts` + test. Our
   equivalent logic is correct but inline in a 4,864-line `app.js`. This is precisely the structural
   fix that made doctor's false-green testable in v0.1 (B2) — and that extraction immediately caught
   a real bug (the `filter` arity trap) the moment it became testable.

**Deliberately NOT porting:**
- *The localStorage attach-token reattach* (`:67-88`). Our terminal identity is already server-side
  (`terminal_sessions` rows + `runtime_state.consoleTerminal`), which is strictly better — it
  survives a different browser. Nothing to take.
- *Mouse-report filtering.* Withdrawn under review in C9 and it stays withdrawn: the dashboard
  console is a real terminal emulator and `server.js` states the raw-passthrough contract
  explicitly. Note hermes agrees — they do **not** filter mouse reports; they add
  `macOptionClickForcesSelection` so the *user* can bypass tracking. That is the right shape if we
  ever want it.
- *Their `\x1b[RESIZE:cols;rows]` in-band resize escape.* We have a typed control action; an in-band
  escape in a byte-transparent channel is a hazard we do not need.

### WS-2 — Console input: find the submit mechanism, stop the dead noise (C8, C9, N3)

v0.1 fixed the **honesty** half — the endpoint and the MCP tool now say QUEUED, not sent. This is
the **mechanism** half. It cost an operator's manager agent ~15 minutes of critical-path idle across
five stalls, and the console tail was the only arbiter throughout while status read `online`.

**Root-cause hypothesis, now with upstream corroboration.** `api_v2.py:14110` builds
`body = text + ("\r" if enter else "")` — **one control, one write, text and CR together**. That is
exactly the pattern hermes deliberately avoids (three separate call sites, 100 ms apart, with the
reason in the comment). And we already have the discipline in this repo:
`terminal-runtime.js:582 _sendAnswer` sends keystrokes as a **spaced sequence** with
`autoAnswerKeyDelayMs = 150` precisely so a menu move re-renders before the next key. The console
path skips a discipline the repo already proved it needs.

That yields a chain which explains the *whole* report, including the part that previously looked
contradictory:

1. one write containing text **and** CR → Ink's tokenizer coalesces it into a **paste**, not
   keypresses;
2. a paste with a trailing newline in claude's composer **inserts a newline** instead of submitting;
3. the draft is now **multi-line**, so every subsequent bare `\r` inserts another newline;
4. each retry looks identical and does nothing — "worked twice, then silently stopped submitting".

This is why the ledger's warning ("do NOT reach for write-splitting first — three bare-CR writes
also failed, and a lone CR cannot lose to state batching") is **still correct and not a
contradiction**: splitting prevents *entering* the poisoned state; it cannot *recover* from a draft
already made multi-line. Both halves are needed.

- [ ] **DISCRIMINATING TEST — REPLACED; the previous one was not discriminating.** I had specified
      "send a bare `\r` to a stuck draft and read the tail by eye". A reviewer pointed out that proves
      almost nothing: on an **already-poisoned** draft a newline appearing confirms only that the
      composer is currently multi-line, which is the *symptom*, and says nothing about whether the
      combined write caused it. It cannot distinguish the hypothesis from its negation.

      The test must run on a **FRESH** draft and compare the two writes directly:
      1. Fresh composer. Send `"hello" + "\r"` as **one** control (today's behaviour). Record the tail.
      2. Fresh composer. Send `"hello"`, wait ~150 ms, send `"\r"` as a **separate** control. Record.
      3. **Prove submission end-to-end**, not from the tail: the message must appear as a real turn —
         a reply, a run transition, a transcript entry. A tail is the thing that has already fooled us
         once (`consoleBytesBefore` was removed for exactly this), and a repainting spinner means the
         bytes changing proves nothing.

      Only if (2) submits and (1) does not is the paste-coalescing chain confirmed. If **both**
      submit, the chain is wrong and the poisoning has another cause — in which case do not ship the
      split as a fix, because it would be a coincidence dressed as a cure.
- [ ] Then: send text and CR as **separate** writes with a delay, via a shared helper rather than a
      fourth open-coded copy (see WS-4.4). Reuse `_sendAnswer`'s discipline; do not re-derive it.
- [ ] Then: a **recovery** lever for an already-poisoned draft, since splitting does not help there.
      Needs the runtime's real submit sequence — claude-TUI behaviour this repo cannot verify from
      outside, so this step is gated on the test above, not on reasoning.
- [ ] C9: **do not enqueue a control for a terminal that is already not active.** 158 rows of
      guaranteed-dead work buried C8's two real writes when reading the table. Pure win, no contract
      change, and it makes the table readable during the next incident.

### WS-9 — `aify-comms` becomes a live status screen instead of a rolling log · **the highest-value new surface**

**Operator ask, 2026-07-26, verbatim intent:** typing `aify-comms` should give "some TUI dashboard
kind of thing" showing state and connections — not a scrolling log.

**What `aify-comms` is today.** The wrapper (`install.sh:2555`) prints three lines and then
`exec node …/server.js --environment-bridge`. So it is a **long-lived foreground supervisor** the
operator leaves running in a terminal: it owns this host's PTYs, polls
`/terminals/controls/claim` (800 ms, long-polled), claims dispatches, heartbeats the environment, and
emits ~78 `console.*` call sites as it goes. It already holds, in-process and first-hand:
`MACHINE_ID`, `BRIDGE_INSTANCE_ID`, `BRIDGE_VERSION`, `BRIDGE_STARTED_AT`, and
`computeBridgeBuildTag()` (`server.js:177-224`).

**This is a better home for the TUI than a separate tool, and it supersedes an earlier draft of this
item.** I had specified a standalone `aify-top` that would re-derive fleet state over HTTP. That was
aimed at the wrong thing. The bridge *already is* the process that knows which terminals are alive,
which claims are in flight, and whether its last heartbeat succeeded — locally, without asking
anyone. A second process polling the API to guess at what this one observes directly is strictly
worse: more code, more latency, and a second opinion about liveness, which is the exact shape of
doctor's false green. **`aify-top` is dropped.** Two surfaces, not three: `aify-comms` = live, this
host; `aify-doctor` = one-shot proof, whole system.

**The actual defect in a rolling log**, and therefore the design principle: **errors scroll away.**
Steady-state heartbeat and claim chatter pushes the one line that mattered off the screen, so the
operator is left scrolling for something that already left the buffer. So: **state is sticky, noise
is bounded.**

Panes (this host's bridge, not the fleet — the dashboard covers the fleet):
1. **Header** — server URL, machine/env id, bridge instance id, **build tag**, uptime, and the age of
   the last successful heartbeat. Connection to the service as a state with an age, never a bare dot.
2. **Terminals this bridge owns** — agent, runtime, session mode, terminal id, PID, and whether the
   PTY is actually alive. Observed locally, so it is the one place this fact is authoritative.
3. **Work** — claims in flight, last claim outcome, queued/failed counts.
4. **Errors — sticky.** The last N failures with count and age, which do **not** scroll. This is the
   pane that fixes the actual complaint.
5. **Recent activity** — the log, bounded to a pane instead of the whole scrollback.

Non-negotiables, each earned by a specific past failure:
- [ ] **TTY → status screen; non-TTY → today's line log, byte-identical.** Piped, `nohup`'d,
      service-managed and CI invocations must not change at all. `--log` forces line mode in a TTY.
      This is the compatibility contract and it is what makes the change safe to ship.
- [ ] **PREREQUISITE, not an existing property: the bridge must write a logfile.** I stated that the
      full stream "still" goes to one, citing `LOG_ROOT` (`install.sh:713`). A reviewer checked:
      `~/.local/state/aify-comms/` exists but holds only `codex-aify` app-server logs, and `server.js`
      has no `createWriteStream` / `appendFile` / LOG_ROOT write at all. **The environment bridge does
      not write a logfile today** — its diagnostics live only in the terminal scrollback. So bounding
      what is on screen would genuinely *destroy* evidence, which makes this a blocking prerequisite:
      land the logfile first, verify it captures a full session, and only then bound the screen.
      Rendering selectively must never mean recording selectively.
- [ ] **Label locally-observed vs server-derived facts, and never blend them.** PTY liveness is ours;
      an agent's status is the server's `derive()`. Showing them in one row without saying which is
      which is how a surface starts lying. Server-derived values carry an age.
- [ ] **Read-only.** No kill/restart keybindings. On 2026-07-02 a sweep of a live ops UI fired real
      Stop controls and killed three workers plus the operating session — in a screen you stare at
      *during* an incident, a stray keypress is that same hazard with a shorter fuse. Actions stay in
      the dashboard and the MCP tools, where they are single-target and confirmed.
- [ ] **NO `--json --once`. WITHDRAWN — it would have killed the operator's live bridge.** I specified
      it for agent/human symmetry without tracing what a second invocation does. A reviewer did:
      `aify-comms` *is* the environment bridge, so a second process **registers the environment,
      becomes the current bridge, and the server supersedes the incumbent** — which then exits by
      design (`server.js:2643-2649`: on a `server:superseded-bridge` control whose `bridgeId` is not
      its own, the older bridge logs and exits). A diagnostic invocation would therefore terminate the
      running bridge and every PTY it owns. That is the "a tool used during an incident must not make
      it worse" rule violated by the very flag added to satisfy a symmetry principle.

      Rejected the alternative too: owner-process IPC to read the incumbent's state is new machinery
      in the highest-consequence process on the host, for a need that is **already served** —
      `aify-doctor --json`, `comms_agents` and `comms_envs` all answer this without owning a bridge.
      So the screen is a *rendering of the process that is already running*, and there is no second
      invocation. Symmetry is satisfied by doctor, not by making the supervisor dual-mode.
- [ ] Add a test that no code path can start a bridge registration in a render-only mode. The failure
      mode here is silent and destructive, so it needs a pin, not a comment.
- [ ] **Shared predicates.** Anything about environment liveness comes from `doctor-predicates.js`,
      not a fresh copy.

Implementation: **plain ANSI, no TUI framework.** Adding a React runtime to a supervisor that must
keep working when things are broken is the wrong trade, and hermes maintaining an entire *fork* of Ink
is that dependency's cost made visible. Install stays symmetric and unchanged in shape — same
dotfolder copy, no new native module, nothing new for `bridge-terminal` to fail on, and no new
command to learn: the thing the operator already types just gets useful.

Note this makes **WS-3 nearly free**: the build tag the header displays is the same value the
heartbeat needs to send. Same field, two consumers.

## Decisions

### DECIDED (operator delegated these on 2026-07-26: "do as you think is right")

**A2 — managed codex auto-approve → make it an explicit named setting; behaviour unchanged.**

The auto-approve itself is not the problem and should not change: a managed worker has no operator to
answer a prompt, so without it the run deadlocks. That is a requirement, not a preference. The problem
is **asymmetry**, and symmetry across harnesses is a stated goal of this project. Today hermes'
permissive posture is an explicit, greppable env flag (`HERMES_YOLO_MODE=1`) while codex's is an
emergent property of three RPC handlers (`codex-session.js:202`,
`controllers/codex-legacy-controller.js:218`, `:228`). An operator reading the config cannot discover
that codex is more permissive than hermes. That is the defect — not the permission.

So: one named setting, resolved the same way for every runtime, documented in DECISIONS.md as a stated
property, which makes "managed codex is YOLO" answerable by reading instead of by tracing three call
sites.

**CORRECTED after review — my first version of this decision was self-contradictory.** I wrote
"default ON for managed and **OFF for resident** … zero behaviour change" two paragraphs after
establishing that the handler **is** wired into the resident path. Both cannot be true: resident codex
auto-approves *today*, so defaulting resident to OFF is a real, unflagged behaviour change to tested
behaviour — the "a default change is not a migration" slip, in the same entry that documents it.

The decision, restated honestly:
- [ ] The setting's default **reproduces current behaviour exactly**: auto-approve where it happens
      today, including resident. That is what makes it a naming change with no fleet risk.
- [ ] Pin current behaviour per path with tests **first** — including that resident does get the
      handler — so the baseline is recorded rather than assumed. The ledger's old claim that resident
      never did was false; do not now assume the opposite without a test either.
- [ ] **Whether resident codex SHOULD auto-approve is a separate operator decision**, made
      deliberately and shipped as its own change with its own review. It is a security posture
      question, it belongs with the standing "security fail-open defaults" decision from the
      2026-06-28 audit, and it must not ride along inside a refactor labelled behaviour-neutral.

**C6 — `delivered` is NOT terminal. Every finished run must reach a terminal status.**

Two reasons, and the second is the decisive one:

1. *It is nearly free.* Every consumer already gates on `result_message_id`, not on `status`, so
   advancing the status changes no delivery behaviour whatsoever. This is pure bookkeeping repair —
   the lowest-risk shape a fix can have in this repo.
2. *The alternative is bad for agents, which is who this is for.* "Document `delivered` + `finished_at`
   as terminal and fix the readers" pushes a **two-field rule** onto every future reader, and the
   primary readers are agents. An agent asking "is this run still open?" should get its answer from one
   field in one read. A rule requiring it to correlate `status` with `finished_at` will be got wrong —
   by agents, by the dashboard, and by me.

So `delivered` keeps its honest meaning — *handed to the target, outcome unknown* — and a reconcile
rule advances a run that has `finished_at` to a terminal status. The 13 existing rows get a one-shot
backfill in the same commit, with the count verified before and after (not assumed: reading back an
artefact I produced is slip 5).

### RECOMMENDED — the one call with a real cost attached

**Do the carve, but ship it as v0.2.x rather than gating v0.2.0 on it.** Rationale in
"Release sequencing" above. The reason to still do it: at 22,889 lines this file is where the defect
