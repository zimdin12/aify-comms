# Finishing 0.9: separation, the state switch, and multiple environments (2026-10-14)

The operator set 0.9 as the separation-of-concerns release on 2026-10-02: "aify-comms should keep what
makes sense to keep in comms side, env is environment, that handles agents and processes. Plugins are
ok." Tags 0.9.0 to 0.9.6 shipped fixes and partial moves, but this goal was never checked as done. On
2026-10-14 three read-only audits measured what is left against `docs/TARGET_ARCHITECTURE.md`, the 0.9
agent-state plan and the code. This page is the plan to finish it. The audits' evidence is cited by
file:line in the commits that act on it.

## What is not done

- **Host work still in aify-comms:**
  - the hermes gateway host: about 6,000 bridge lines that start, kill and reap processes;
  - kill and reap helpers called by launchers;
  - a resident bridge killing its own parent tree on Stop;
  - latent runtime spawners: about 7,200 lines;
  - six host checks in the comms doctor;
  - the `aify-comms` verifier on PATH.
- **Install does other repos' work.** `install.sh` (2,172 lines):
  - renders the launchers;
  - configures and patches hermes;
  - installs the hermes plugin;
  - installs the turn hooks;
  - copies service code onto agent hosts.

  The launchers also find aify-wrapper's own bins inside the comms install, and call comms bridge files
  by path.
- **aify-env core names a comms route.** It builds `/api/v1/environments/heartbeat` itself
  (`lib/advertise.mjs:386`), outside the plugin.
- **The status switch (P7) and the deletions (P8) have not started.** aify-env cannot see a single
  resident. All 16 resident records are scoped to instance `default`, and that process (pid 71956) is
  dead. The only live aify-env is `herdr-78cfcc61` (verified 2026-10-14). Switching today would show
  every resident offline.
- **Multiple environments: the service side is built and has never run.**
  - Environments register, heartbeat and are chosen at spawn.
  - A defined agent cannot move between machines: the dashboard offers it and the service answers 409.
  - Environment ids ignore `AIFY_MACHINE_ID`.
  - An undefined agent can cold-start on any machine.
  - No second aify-env, WSL or another PC, has ever run.

## Releases

Each release gets one dev review of its exact objects, all five suites, and a deploy. The doctors
must be green before the tag.

**0.9.7: install separation and the resident fix.** Every change here is in the launchers, so the
operator relaunches once.
1. aify-wrapper installs itself, and its launchers find their own bins in their own package.
2. aify-wrapper's installer renders the launchers and owns harness setup: the hermes plugin, the
   `web_dist` prebuild and patch, hermes session servers, and turn hooks pointing at aify-env.
3. Launchers take comms' MCP commands from `~/.aify/services.json` instead of calling bridge paths.
4. Residents report to the live aify-env instance (B1): herdr-aify exports its instance scope, and
   the lifetime script resolves a live descriptor instead of a blind `default`.
5. aify-env core stops naming the comms heartbeat route; the plugin owns it.
6. The six host checks move to `aify-env doctor`.
7. The claude reaper and resident Stop move to aify-env and aify-wrapper.
8. `install.sh` shrinks to comms' own job: the backend, comms' registry entry, skills, the MCP server
   registration and the unread-notice hook. It then calls the other installers in order: aify-env,
   aify-wrapper, comms, re-render.

**0.9.8: aify-env's word becomes the status (P6 to P8).**
- **First the missing pieces:**
  - stops recorded only in comms move into aify-env's journal (B2);
  - the two agents whose mode disagrees are corrected (B3);
  - screen, background-shell and starting inputs reach aify-env (B4);
  - a publication on every turn event, and the mirror reloaded after a service restart (B5);
  - `turn.ageMs`, build versions, and the busy, queue and claim decisions instrumented (B6).
- **The gate:** the fleet comparison shows zero disagreements outside the approved classes below.
- **Then the switch (P7):**
  1. Write the witness tests first.
  2. One pure comms view.
  3. Delivery hold rebased onto aify-env's busy flag.
  4. Add `unknown`.
  5. Launchers report only to aify-env.
- **Then the deletions (P8):** the status engine, detectors, three tables, the shadow recorder and
  the latent spawners, after proving that no live route reaches them. pi and opencode stay as
  deprecated and kept (operator, 2026-09-18).

**0.9.9: hermes leaves comms; agent hosts carry no comms code.**
- The gateway host and its delivery loop move to aify-env. The WebSocket submit stays comms code,
  running as an aify-env comms-plugin capability.
- The verifier and the doctor move into the container.
- Client installs stop copying service code onto the host, through SSE transport parity.
- The usage readers move to an aify-env plugin.

**0.9.10: multiple environments, proven live.**
- Environment ids come from the machine id.
- Undefined agents cold-start only on their own machine.
- A move verb: `aify-env agents move <id> <environment>`, and the dashboard uses it.
- A second aify-env is brought up in WSL and proven end to end: register, define, spawn, message,
  stop.

## Decided here, each reversible

- **Status policy changes the plan held for approval, at their plan defaults:**
  - an agent with no reporting environment reads `unknown` (grey), not offline;
  - events from launchers older than 0.9 are refused as `unbound` after the relaunch;
  - push and poll serve one view.

  The operator can veto any one; each is a single commit.
- **Not doing: several aify-comms services in one registry.** No operator text asks for it; the
  multi-service design is about different services (comms, dashboard, project-graph), which works today.
- **Usage readers:** to an aify-env plugin, because they read host credentials.
