# v0.6 Phase 7 — aify-env: implementation plan

> **For agentic workers:** implement task-by-task. Each task ends with an independently testable
> deliverable and a commit. Steps use `- [ ]` for tracking.

**Goal.** A host service that owns processes and PTYs, so more than one aify service can start agents
on one machine without two spawners fighting over the same terminals.

**Architecture.** New repo, `~/projects/aify-env`. It reads the same `~/.aify/services.json` that
aify-wrapper reads. It runs what it is told, from a derived allowlist. It knows nothing about
messaging, dispatch or agent status — `alive` is not `working`, and deriving status in two places is
how two answers start disagreeing.

**Tech stack.** Node, `node --test`, `node-pty` for terminals with a piped-stdio fallback. No web
framework beyond what a local HTTP listener needs.

**Read first:** [AIFY_ENV_BOUNDARY.md](../../AIFY_ENV_BOUNDARY.md) — what moves, what stays, the
derived allowlist, and why doctor asks rather than inspects.

## Global constraints

- **Never execute a file to decide whether to execute it.** The allowlist reads
  `HARNESS_WRAPPER_VERSION` out of the file, exactly as doctor does, because asking a pre-contract
  wrapper `--check` would launch the runtime.
- **Never run a bare `aify-comms`** — it starts the environment bridge and reaps the managed fleet.
- **Nothing in this phase may touch the operator's live fleet.** aify-env is new; until Phase 8 wires
  aify-comms to it, nothing routes through it.
- **Tests seal PATH, HOME, TMP/TEMP and the registry path.** Hostile means `http://127.0.0.2:1`.
- **`alive` is never reported as `working`.** aify-env has no opinion about agent state.
- **No secrets in commits**; report env-name and key-presence only.

## File structure

| Path | Responsibility |
|---|---|
| `lib/allowlist.mjs` | Pure. Given a file's text, may it be executed? Derived from the contract marker. |
| `lib/process-registry.mjs` | Pure. The set of owned processes and the transitions over it. |
| `lib/runner.mjs` | Spawns under a PTY, falls back to piped stdio, streams output, reaps. |
| `lib/health.mjs` | Pure. This environment's own checks, and the `passed/failed/unanswered` shape. |
| `lib/services.mjs` | Reads `~/.aify/services.json`; asks each service for its self-report. |
| `bin/aify-env.mjs` | The daemon: listener + loops. |
| `bin/aify-doctor.mjs` | Collect and display. Asks; never inspects another component's internals. |
| `tui/` | The terminal view: services, owned processes, its own I/O. |

### Task 1: The repo, and the allowlist that makes it safe to run anything

**Files:** Create the repo, `lib/allowlist.mjs`, `tests/allowlist.test.js`, `README.md`.

A host service that runs commands for any registered service is remote code execution by design.
Today's constraint — the environment bridge only launches wrappers — is incidental, not enforced.

**Interfaces — Produces:** `mayExecute(fileText) -> {ok, reason}` and
`markerOf(fileText) -> string|null`.

- [ ] **Step 1: Write the failing tests.** A file carrying `HARNESS_WRAPPER_VERSION="0.5.7"` is
      allowed and its marker is read. A file without it is refused, naming the reason. An empty file,
      a binary blob, and a file whose marker is commented out are all refused. The marker is read from
      the file **only** — a test asserts nothing is executed, by pointing at a file that would create a
      sentinel if run.
- [ ] **Step 2: Run. Expected: FAIL.**
- [ ] **Step 3: Implement.** Fails closed on anything it cannot read.
- [ ] **Step 4: Run. Expected: PASS.**
- [ ] **Step 5: Commit.**

### Task 2: Owning a process

**Files:** `lib/process-registry.mjs`, `lib/runner.mjs`, tests for both.

**Interfaces — Consumes:** an allowlist verdict. **Produces:** `start(spec) -> handle`,
`stop(id)`, `list()`, and an output stream per handle.

- [ ] **Step 1: Write the failing tests.** A started process appears in `list()` with a pid; its
      output streams; it leaves `list()` when it exits; `stop()` is idempotent. A spec whose file is
      refused by the allowlist never reaches spawn.
- [ ] **Step 2: Run. Expected: FAIL.**
- [ ] **Step 3: Implement**, PTY first with a piped fallback when `node-pty` will not load.
- [ ] **Step 4: Run. Expected: PASS**, and the PTY path must be exercised, not skipped — a skipped
      assertion reports as a pass, and this is the path the dashboard console depends on.
- [ ] **Step 5: Commit.**

### Task 3: Reaping, keyed on STATE

- [ ] **Step 1: Write the failing tests.** A process that dies without anyone calling `stop()` is
      still removed. A process whose owner disappeared is still removed. Cleanup keys on the observed
      state, never on an event having fired.
- [ ] **Step 2-5:** as above.

This is the rule this project paid for: a spawn sat `running` for 97 minutes because the one function
that marks a terminal dead is one of about 26 writers and was simply never called. Cleanup that must
hold for all paths keys on the state.

### Task 4: `aify-env doctor` — passed / failed / **unanswered**

**Files:** `lib/health.mjs`, `bin/aify-doctor.mjs`, tests.

- [ ] **Step 1: Write the failing tests.** A registered service that does not answer reads
      `unanswered`, never `ok`, and `--strict` does not exit 0 on it. A check that could not gather
      evidence is `unanswered`, not `skipped`-as-pass. `--json` carries the three states distinctly.
- [ ] **Step 2-5:** as above.

`skip()` in the existing doctor pushes `ok: true`, so on Windows a green `--strict` means ten verified
and two unanswerable. That is survivable at twelve checks on one host and not across four components
where "not installed" and "silent" are ordinary.

### Task 5: The TUI

- [ ] Registered services from the registry, each reachable or silent, plus whatever they self-report.
- [ ] Processes aify-env owns — pid, wrapper, cwd, uptime. Ground truth, because it started them.
- [ ] Its own I/O, which is what an activity indicator may be driven by.
- [ ] **A test asserting the TUI reports no agent status of its own.** aify-env knows processes.

### Task 6: The request contract

**Files:** `bin/aify-env.mjs` listener, `docs/PROTOCOL.md`, tests.

- [ ] Start / stop / list / attach, over a local listener, with the caller naming the service it is
      acting for.
- [ ] **Every request is allowlist-checked**, including ones from a registered service. Registration
      is not authorisation.
- [ ] Document it, because Phase 8 is written against it.

## Phase gate

Green by measurement:

1. A process started through aify-env runs under a PTY, streams to a consumer, and is reaped when it
   dies — including when nobody called `stop()`.
2. A file without the contract marker is refused, and the refusal names why.
3. `aify-env doctor` reports three states, and a silent registered service reads `unanswered`.
4. The TUI shows services, owned processes and its own I/O, and claims no agent status.
5. Nothing in the operator's live fleet has been started, stopped or routed through aify-env.

## Deliberately not in this phase

- **Moving the harness semantics.** Turn detection, stop gating and steering stay in aify-comms. The
  risk this phase carries is those ~16.9k lines following `terminal-runtime.js` into the new repo,
  at which point aify-env is the bridge with a new name in a new place.
- **Wiring aify-comms to it.** Phase 8, behind a flag, on an idle fleet.
