# 0.9.10: the hermes gateway host moves to aify-env

**Why.** The operator, 2026-10-02: aify-comms becomes a pure comms service. TARGET_ARCHITECTURE "What is left"
item 4 names what is still host work in comms: the hermes gateway host (starting it, killing a prior one,
reaping orphans, resume markers). Putting a message into a runtime session stays comms' delivery. Task #4.

**Done in 0.9.10 already.** Hermes turns reach aify-env (ef466e1c). The dead transcript readers are deleted
(d3b13b93).

## Today, read from the code (2026-10-26)

`hermes-aify` (aify-wrapper) runs one launch as four steps, three of them comms code on the host:

1. **Kill prior.** It runs aify-wrapper's `bin/aify-hermes-reap-prior.mjs` (the prior delivery loop), and then
   comms' `hermes-daemon-cli.js stop <agent>` (gateway hosts, by their port and pid markers).
2. **Gateway host.** comms' `hermes-managed-host.js ensure-host <agent>` (`hermes-gateway.mjs` `ensureGatewayHost`)
   spawns a hidden `hermes dashboard --tui --port <agentPort>`, scrapes its session token, and writes the
   port, url and key markers into TEMP (`hermes-endpoint.js`).
3. **Delivery loop.** comms' `hermes-managed-host.js run <agent>` connects to that gateway, submits prompts and
   runs the turn detector. It calls `ensureGatewayHost` again to recover a dead gateway.
4. **Visible TUI.** It attaches to the same gateway (pc-manager's lane).

comms' doctor `gateway-orphans` reports leftover gateway hosts. Hermes code in the comms bridge: about 7,660
lines in 28 files. `hermes-aify.sh.in` is already 1,162 lines, over the 1,000-line limit.

## Target

- **aify-env owns the gateway process.** The launcher, managed or hand-launched, asks
  `POST /agents/<id>/gateway` with its lifetime; aify-env starts or reuses that agent's gateway and answers
  `{wsUrl, token}`, and `GET` answers the same to the delivery loop. Admission is `turn-event`'s: loopback,
  descriptor-only routing, the lifetime current for the agent, `residents` only while this process holds the
  role. The gateway stays **detached and tied to the agent's launcher pid** (`HERMES_PARENT_PID`, hermes'
  parent-death watchdog), not to aify-env: an aify-env restart must not end a resident's gateway, as it does
  not today. aify-env records `{port, pid, lifetime}`, re-adopts a live gateway after its own restart by
  probing its port, and reaps one whose lifetime has ended. Markers become that record, not TEMP files.
- **comms keeps delivery.** The loop asks aify-env for the gateway, and on a dead gateway it asks aify-env to
  replace it. It never spawns or kills one. `hermes-daemon.js`, `hermes-prior-reap.mjs`, the spawn half of
  `hermes-gateway.mjs` and the port/key markers in `hermes-endpoint.js` are deleted. `gateway-orphans` moves
  to `aify-env doctor`.
- **aify-wrapper** drops steps 1 and 2 from the launcher, which also brings `hermes-aify.sh.in` back under its
  size limit.

## Found while building (2026-10-26): the gateway's environment is the agent's

Hermes runs the agent's tools inside the gateway process, and the gateway spawns the agent's MCP children, comms'
bridge among them, which reads its identity from `AIFY_AGENT_ID` in that environment (`hermes-gateway-config.mjs`).
So the gateway must start with the launcher's environment and folder. Started by aify-env, it would carry aify-env's:
the comms bridge inside hermes would have no agent id, and tools would run in the wrong folder.

Recommended, pending the operator because TARGET_ARCHITECTURE names aify-env: **the spawn moves from comms to the
launcher (aify-wrapper)**, which has the agent's environment. aify-env keeps the port, the record, replacing an
older lifetime's gateway, `GET` for the delivery loop, and the doctor row. The launcher asks aify-env for the port,
starts the gateway, and registers its pid. Built so far in aify-env: the port rule, the start module (moves to
aify-wrapper under this), the book and the route (`ensure` becomes `prepare` + `register`).

## Slices (built together, switched together, as the operator ruled for 0.9.8)

1. aify-env: the gateway host module (spawn, token, readiness, the per-agent port), owned by the lifetime; the
   route; doctor `gateway-orphans`. Tested against a fake `hermes` binary, as `ensureGatewayHost` is today.
2. comms: the loop's gateway source is aify-env; the hosting code, its tests and the doctor row are deleted.
3. aify-wrapper: the launcher asks aify-env; kill-prior and ensure-host are gone.
4. Switch: aify-env restart (the operator's), install, then relaunch the hermes agents. Prove it live: a
   managed hermes started from the dashboard answers a message, its gateway dies with it, and no orphan is
   left behind.

## Decision for the operator

**A resident hermes (launched by hand) would need aify-env running.** Today it works without one, because
comms' bridge starts the gateway. After the move, a hand launch with no aify-env would fail loudly, as a
managed spawn already does. My recommendation is to accept this: aify-env is the only spawner. The
alternative is to keep a comms fallback for residents, which keeps the host code this release exists to
remove.

## Risks

- Nine hermes agents rely on this path. Every launch shape changes at once, so the switch is one restart plus
  relaunches, with rollback images for comms and the previous commits of aify-env and aify-wrapper.
- The visible TUI attaches to the same gateway. pc-manager's paged-history TUI work touches step 4, so it is
  coordinated before slice 3.
