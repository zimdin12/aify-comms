# v0.6 — Separate the core, polish what is left

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended)
> or superpowers:executing-plans to implement each PHASE plan task-by-task. Steps use checkbox (`- [ ]`)
> syntax for tracking.

**Goal:** Split the reusable core out of aify-comms — testable delivery loops and independently
installable harness wrappers — then hold everything that remains to a hard standard, with end-to-end
proof at both ends of the release.

**Architecture:** Five phases in a fixed order, each ending in working software and a gate that must be
green before the next begins. Phase 0 and Phase 5 are the same end-to-end suite: the first run is the
baseline that says what works today, the last run is the proof that a release's worth of restructuring
did not break it. Everything between is decomposition (Phases 1–2) followed by quality (Phases 3–4).

**Tech Stack:** Python 3.12+/FastAPI/SQLite (service), Node 20+/ESM (bridge + dashboard), Docker
Compose, pytest + `node --test`.

**Spec:** [docs/V0.6_PLAN.md](../../V0.6_PLAN.md) — the queue this plan schedules. Every item there is
assigned to a phase below or explicitly deferred with a reason.

## Global Constraints

Copied verbatim from the standing rules; every task inherits them.

- **No product source file may reach 1000 lines.** `oversized-allowlist.json` is EMPTY and that is the
  end state — adding an entry to make a red gate green is a reviewer decision, never a fix.
- **The service must stay single-worker uvicorn.** `_LIVE_STATE_CACHE` is a process-global dict.
- **One version, in the repo-root `VERSION`.** Five surfaces move together: `VERSION`,
  `mcp/stdio/version.js`, `mcp/stdio/package.json`, `mcp/stdio/package-lock.json` (both self-entries),
  `.claude-plugin/plugin.json`.
- **No secrets in commits.** `.env` is gitignored; the ntfy topic URL and `OPERATOR_KEY` are
  credentials — `.env` only, never `config/service.json`, never logged, never in a response body.
- **Skill mirrors byte-identical** between `.claude/skills/` and `.agents/skills/`.
- **`bash scripts/stamp.sh` before `docker compose up -d --build`.** Bridge changes need `install.sh`
  **and** a wrapper relaunch; run `install.sh` sequentially, never in parallel.
- **Never run a bare `aify-comms`** — it starts the environment bridge and reaps managed workers. Use
  `aify-comms --check`.
- **Never set ACTION env vars in a test run** (`AIFY_ENVIRONMENT_BRIDGE=1` once reaped seven live
  gateway hosts). Hostile-env means SET but pointing NOWHERE (`127.0.0.2:1`), never at the live service.
- **Never blind-kill processes by heuristic** (Windows PID reuse).
- **Live-UI testing is read-only**, allowlist never blocklist.
- **Every fix is proven by mutation** — mutate the product, require the test to go red, restore the
  source byte-identically and assert it.
- **Deploy-coupled auth changes get an explicit release step.** comms-senior-dev, 2026-08-18: "doctor
  red + relaunch instruction is not itself a deployment gate."

## Why this order

Each phase removes a reason the next one would be guesswork.

1. **You cannot safely restructure what you cannot observe.** The delivery loops are the product's heart
   and are verified today only by a manual two-session round-trip. Phase 0 makes that repeatable before
   anything moves.
2. **You cannot extract a wrapper contract you have not named.** Phase 1's seams force the delivery
   path's real interface into the open; Phase 2 then splits along a line that exists rather than a line
   someone drew.
3. **You cannot judge the dashboard while its backend is moving.** Phase 3 runs after the core settles.
4. **A bughunt is only as good as the coverage underneath it.** Phase 4 runs last so it hunts through
   instrumented code, not through the blind spots Phases 1–3 removed.

```python
"""Start a real service against a scratch database, and stop it.

A REAL PROCESS, not TestClient. The e2e suite exists to catch what in-process tests cannot: startup
ordering, the reconcile sweep running on its own timer, and a bridge talking over HTTP. TestClient
shares the interpreter and would hide all three.

NEVER POINTS AT THE OPERATOR'S SERVICE. The port is ephemeral and the database is a tmp_path — the
recorded incident is a hostile-env run that pointed at 127.0.0.1:8800 and registered six agents into
the live registry.
"""
from __future__ import annotations

import os
import socket
import subprocess
import sys
import time
from pathlib import Path

import urllib.error
import urllib.request
import json


def _free_port() -> int:
    with socket.socket() as s:
        s.bind(("127.0.0.1", 0))
        return s.getsockname()[1]


class E2EStack:
    def __init__(self, db_path: Path, boot_timeout: float = 30.0):
        self.db_path = Path(db_path)
        self.port = _free_port()
        self.base_url = f"http://127.0.0.1:{self.port}"
        self._boot_timeout = boot_timeout
        self._proc: subprocess.Popen | None = None

    def __enter__(self) -> "E2EStack":
        env = dict(os.environ)
        env.update({
            "DATA_DIR": str(self.db_path.parent),
            "DB_PATH": str(self.db_path),
            "API_KEY": "",
            "OPERATOR_KEY": "e2e-operator-key",
            "AIFY_SERVER_URL": self.base_url,
        })
        self._proc = subprocess.Popen(
            [sys.executable, "-m", "uvicorn", "service.main:app",
             "--host", "127.0.0.1", "--port", str(self.port), "--no-access-log"],
            env=env, stdout=subprocess.PIPE, stderr=subprocess.STDOUT,
        )
        deadline = time.time() + self._boot_timeout
        while time.time() < deadline:
            if self._proc.poll() is not None:
                out = (self._proc.stdout.read() or b"").decode("utf-8", "replace")
                raise RuntimeError(f"the service exited during boot:\n{out[-2000:]}")
            try:
                if self.api("GET", "/health").get("status") == "healthy":
                    return self
            except (urllib.error.URLError, ConnectionError, OSError):
                time.sleep(0.2)
        raise TimeoutError(f"the service did not become healthy within {self._boot_timeout}s")

    def api(self, method: str, path: str, body: dict | None = None) -> dict:
        url = f"{self.base_url}{path}"
        data = json.dumps(body).encode() if body is not None else None
        request = urllib.request.Request(url, data=data, method=method)
        if data is not None:
            request.add_header("Content-Type", "application/json")
        with urllib.request.urlopen(request, timeout=10) as response:
            text = response.read().decode("utf-8", "replace")
        return json.loads(text) if text else {}

    def stop(self) -> None:
        if self._proc and self._proc.poll() is None:
            self._proc.terminate()
            try:
                self._proc.wait(timeout=10)
            except subprocess.TimeoutExpired:
                self._proc.kill()
                self._proc.wait(timeout=10)
        self._proc = None

    def __exit__(self, *_exc) -> None:
        self.stop()
```

```python
"""send -> stored -> dispatch run -> delivered -> reply threaded back.

THE FOUR LOAD-BEARING PROPERTIES of that path, asserted as one flow because they only mean anything
together (docs/ARCHITECTURE.md, "How a message becomes work"):
  1. storage precedes delivery — the message exists even when nothing can run it;
  2. a dispatch run is created and reaches a terminal state;
  3. the reply is THREADED to the original message, not merely present;
  4. the run closes because the reply arrived, not because something timed out.
"""
from service.tests.e2e.harness import E2EStack


def _register(stack, agent_id, **over):
    body = {"agentId": agent_id, "role": "coder", "runtime": "claude-code",
            "sessionMode": "resident", "cwd": "/w"}
    body.update(over)
    return stack.api("POST", "/api/v1/agents/register", body)


def test_a_message_becomes_a_run_and_the_reply_closes_it(tmp_path):
    with E2EStack(db_path=tmp_path / "e2e.db") as stack:
        _register(stack, "e2e-sender")
        _register(stack, "e2e-target")

        sent = stack.api("POST", "/api/v1/messages/send", {
            "from_agent": "e2e-sender", "to": "e2e-target", "type": "request",
            "subject": "do the thing", "body": "please do it", "trigger": False,
        })
        assert sent["ok"], sent
        message_id = sent["messageId"]

        inbox = stack.api("GET", "/api/v1/messages?agentId=e2e-target&filter=all")
        assert any(m["id"] == message_id for m in inbox.get("messages", [])), (
            "the message was not stored. Storage precedes delivery: a message that cannot be "
            "delivered is still a message."
        )

        reply = stack.api("POST", "/api/v1/messages/send", {
            "from_agent": "e2e-target", "to": "e2e-sender", "type": "response",
            "subject": "Re: do the thing", "body": "done", "inReplyTo": message_id,
            "trigger": False,
        })
        assert reply["ok"], reply

        thread = stack.api("GET", f"/api/v1/messages/{message_id}/thread")
        assert reply["messageId"] in [m["id"] for m in thread.get("messages", [])], (
            "the reply is not threaded to the original. A reply that exists but is not threaded "
            "leaves the contract open and the sender re-asking."
        )
```

## Phase 1 — Make the delivery loops testable

**The finding, measured.** A V8-coverage census over `mcp/stdio` went 192 → 122 never-called functions
during v0.5.4. What remains is untestable *by construction*: closures created inside functions that
never return. `server.js` 27, `hermes-delivery-loop.mjs` 11, `claude-channel.js` 11,
`dispatch-loop.mjs` 10, plus ~20 callbacks handed into them.

**The work.** Extract each loop BODY behind an injectable seam — `runOneDeliveryTick({ deps })` — with
the loop reduced to a scheduler around it. Same standard as the reconciler extraction: byte-identical
bodies, the module exports what it extracts, real unit tests that CALL it.

**Order:** `dispatch-loop.mjs` first (smallest, and Phase 0 exercises it), then
`hermes-delivery-loop.mjs`, then `claude-channel.js`, then `server.js`'s loop starters.

**Folded in from the v0.6 queue:** §2 in full. The `pi-session.js` (993 lines) and `server.js` (933)
structural watch-items are addressed here or explicitly deferred — a seam extraction is the natural
moment to take 993 down, and doing it any other time is a refactor with no test behind it.

**Phase gate:** every extracted tick has unit tests that call it; census materially below 122; the
Phase 0 e2e suite still green; `node tests/run-all.mjs` green.

**Needs a decision before starting:** none. This phase is unblocked.

## Phase 2 — Separate the wrappers into their own repo(s)

**The ask.** `claude-aify`, `hermes-aify`, `codex-aify` become a standardized harness wrapper that
aify-comms *depends on*, installable on its own and usable by other services.

**What exists, measured.** The wrappers are **generated text, not a package** — `install.sh` (4,370
lines) emits them from 14 heredocs. There is one npm package (`mcp/stdio`, `aify-comms-mcp`). No
`wrappers/` directory, no design doc.

**SCOPE DECIDED 2026-08-19 (operator): the WRAPPERS are the published thing; the bridge stays here.**
Written up in [docs/superpowers/specs/2026-08-19-harness-wrapper-contract.md](../specs/2026-08-19-harness-wrapper-contract.md),
which supersedes the paragraph below and corrects it on two points of fact:

- **The wrapper generators are SMALL**, and my earlier "correction" of the plan's "~100 lines of shell"
  was wrong. Re-measured: claude 128, codex 10, pi 222, hermes 251 — **611 lines, ~14% of install.sh**.
  The 3,943/2,847 figures I published came from a span bug (each generator terminated at the next
  WRAPPER installer, so hermes — the last one — ran to end-of-file). Hermes' real heft is elsewhere:
  ~1,145 lines across `install_hermes_windows_tui_shim` (503), `aify_hermes_kill_prior` (277) and config
  patching, i.e. the Windows visible-TUI requirement, not the launcher.
- **The split is step one of a three-tier target** the operator stated the same day — client /
  environment / server, where the server contains an environment and a client so a single box works,
  while external environments and clients connect to the same surfaces. That reframes the wrapper split
  from "extract the launcher" to "name the client↔environment edge for the first time", which is why
  the contract's `HARNESS_MCP_COMMAND` matters more than any file move.

**The central question, ANSWERED above; kept for its reasoning.** The wrapper is ~100 lines of
shell; the value is in the bridge. If other services want status and data, they want the BRIDGE — and
splitting the launcher alone is cosmetic. **Task 2.1 is a written contract, not code:** what a host
provides (endpoint, key, identity, cwd), what it gets (registration, heartbeat, status, dispatch
delivery), and what is explicitly NOT part of it.

**Three things this phase must not break, each already paid for:**
1. `install.sh` currently guarantees wrapper and bridge are the same build. A standalone install breaks
   that guarantee — and `doctor`'s `bridge-installed` / `bridge-current` checks exist *because* it kept
   being violated silently. The contract must say how version skew is detected.
2. The native-copy load-time fix: the repo often sits on a slow 9p/WSL2 mount where the bridge takes
   ~5s to load, which blows hermes' hardcoded 0.75s MCP-discovery window.
3. **Deploy coupling needs an explicit release step** — the v0.5.6 precedent.

**Folded in:** v0.6 queue §1 in full, plus the `API_KEY` / per-agent-identity decision from
DECISIONS.md (2026-08-18) — the wrapper contract is exactly where "what credential does a host present"
gets answered, and answering it twice in two phases would fork it.

**Phase gate:** `aify-comms doctor` green from a clean install that consumes the wrapper as a
dependency; version-skew detection demonstrated by deliberately installing mismatched versions.

**Needs a decision before starting:** the contract (Task 2.1) is itself the decision, and it needs the
operator's sign-off on scope — wrapper only, or wrapper + bridge as the published surface.

## Phase 4 — Deep bughunt across all layers

**Runs last on purpose.** It hunts through instrumented code, so a finding means a defect rather than a
blind spot.

**Layers, each with a named entry point:** service routers and `api_core` leaves · reconcilers and the
sweep ordering · the bridge and its runtime adapters · the dashboard · the MCP tool surface · schema and
migrations · the installer.

**Carried in from the v0.6 queue, each already traced:**
- §4b's five Lows, each with the packet it belongs to.
- §4c's three deliberate fail-opens — this phase is where a **specimen hunt** happens: a real carrier
  row is the bar the ruling set, and a bughunt across live data is where one would turn up.
- §4d's latent 429/529 false positive — same, needs an observed error string.
- §4a provider-refusal classification — build ONLY if this phase produces the retained-frame evidence
  its entry bar requires.
- §4g's three items needing an OPERATOR ruling: #10b (a system-authored notice refreshes a dead agent's
  last-produced), the rename that strands terminals, and the managed-register guard that fails toward
  resident. **These block work and should be ruled before Phase 4 starts, not during it.**

**Method, non-negotiable:** every finding gets a failing test before a fix; every fix is mutation-proven;
findings are ranked by whether a reader could act on the wrong belief, not by how clever the bug is.

**Phase gate:** a committed findings ledger where every row is FIXED, DEFERRED (with the reason and the
bar for revisiting), or NEEDS-RULING with the question stated.
