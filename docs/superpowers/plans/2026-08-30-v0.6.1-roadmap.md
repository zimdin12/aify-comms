## Row 5 — SoC: aify-env and aify-wrapper as a base for an unrelated project

**Measured 2026-08-30**, with the search instrument positive-controlled (4 and 8 hits on
strings known to be present, 0 on one known absent) so the zeros below are real.

**aify-env is clean.** 25 source mentions of aify-comms, every one a COMMENT citing the
sibling's incident history. Naming a consumer in a comment is documentation; it is not
coupling. A new project can take aify-env as it stands.

**aify-wrapper is clean by NAME and coupled by SHAPE.** Zero literal `aify-comms` in
non-comment template code: the service name is fully parameterised, the channel server
included, as `@@SERVICE_NAME@@-channel`. But `wrappers/claude-aify.sh.in` hardcodes FOUR
paths into aify-comms' internal directory layout:

| line | hardcoded | should be |
|---|---|---|
| 427 | `${AIFY_SCRIPT_DIR_FWD}/mcp/stdio/server.js` | a placeholder |
| 456 | `${HARNESS_ENDPOINT}/mcp/sse` | a placeholder |
| 466 | `${AIFY_SCRIPT_DIR_FWD}/mcp/stdio/claude-channel.js` | a placeholder |
| 503, 506 | `${AIFY_SCRIPT_DIR_FWD}/mcp/stdio/claude-session-hook.js` | a placeholder |

The other three launchers (codex, hermes, pi) hardcode NOTHING — so the right pattern
already exists in the repo and only the claude launcher departs from it. `@@BRIDGE_DIR@@`
is already declared and is used at exactly ONE of the five sites (line 529).

**Consequence, stated concretely:** a new service built on aify-wrapper's claude launcher
must reproduce aify-comms' layout — an MCP bridge at `mcp/stdio/server.js`, a channel
server at `mcp/stdio/claude-channel.js`, a session hook at
`mcp/stdio/claude-session-hook.js`, and SSE served at `/mcp/sse`. That is not fatal, but it
is the answer to "are they really SoC'd": by name yes, by layout not yet.

**Fix shape:** extend the placeholder set the way the other three launchers already work.
Small, mechanical, gated by the existing render tests.

## Row 6 — aify-env TUI: what is there, and what the upgrade costs

- `lib/tui.mjs` (328 lines) is a PURE renderer: `renderDashboard(snapshot, {columns, color})`
  returns a string. `paint()` is the single place an escape is written, `width()`/`clip()`/
  `table()` handle measurement. Colour is already meaning-bearing by policy, never decorative.
- `lib/dashboard.mjs` (171 lines) is the loop: full screen CLEAR (`ESC[2J ESC[H`) then redraw
  on `setInterval`.

**The purity is the asset.** Panes can be pure functions over the same snapshot, which keeps
the architecture the operator asked for. Three things the upgrade actually needs:

1. **Stop the full clear.** Clear-and-redraw flickers and makes a right-hand pane unreadable.
   Needs differential rendering, or at minimum cursor-home + per-line erase.
2. **A focus model and raw-mode input.** The operator's idea (a right-side per-terminal view
   with an input option) means keyboard routing: some keys drive the dashboard, some go to the
   selected PTY. aify-env already has PTY custody, so writing input to a process is in reach.
3. **Colour and indicators with meaning.** The existing policy is right and should hold: every
   colour carries state. More indicators, not more decoration.

## Row 7 — Anthropic's cross-session messaging: what to take, what to leave

Researched 2026-08-30 from Anthropic's own docs and changelog. Two separate features:

- **Cross-session `SendMessage` + `ListAgents`** — GA, shipped v2.1.224 (2026-08-07), macOS
  and Linux first. Same-machine transport is a per-session UNIX socket / named pipe
  (`CLAUDE_CODE_MESSAGING_SOCKET` + a per-session token), never through Anthropic's servers;
  cross-machine goes through their servers over Remote Control.
  <https://code.claude.com/docs/en/cross-session-messaging>
- **Agent teams** — EXPERIMENTAL, off unless `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`.
  Different transport: a JSON-file mailbox per agent. `TeamCreate`/`TeamDelete` shipped and
  were then REMOVED in v2.1.178. <https://code.claude.com/docs/en/agent-teams>

They solved a NARROWER problem: one operator's own sessions, mostly one machine. No server,
no database, no dashboard, no dispatch queue, no durable identity, no channels, no file
sharing. aify-comms carries all of that because it targets heterogeneous runtimes and a fleet
that outlives any session. So this is a source of ideas, not a design to converge on.

### Worth adopting, ranked

1. **The anti-polling contract.** `notify_when_idle` is one-shot, opt-in, costs the WATCHED
   session nothing (it subscribes without starting a turn), and auto-expires at 12h — paired
   with an explicit instruction never to poll or send "are you done?". aify-comms has
   `comms_listen` and `comms_run_status`; a zero-cost expiring one-shot beats both.
2. **Every drop is reported to the SENDER, by name.** Roughly 15 changelog entries in the 21
   days after launch are this one lesson relearned: sent-but-dropped, held-with-no-notice,
   a malformed inbox blocking delivery. Given this repo's own favourite failure — a step that
   reports success and changes nothing — those entries are a ready-made defect checklist.
3. **Tell the model WHY the first line matters** rather than giving it a length rule: the
   human sees only the first line as a preview until they expand it. Cheaper and more
   effective than the subject-length rule aify-comms uses. (Feeds row 3.)
4. **Loop safety as THREE bounded mechanisms**, not one: per-sender rate limit, identical-
   repeat drop, hard queue cap (50 accepted / 100 held), bursts refused AT THE SENDER. The
   documented consequence is that a two-session message loop stops on its own.
5. **The permission-laundering prohibition, close to verbatim.** Never ask a peer to do what
   your own permission settings blocked — a peer doing it for you bypasses the user's
   decision. SHARPER here than there, because aify-comms spans runtimes with different
   permission postures.
6. **Inbound consent derived from BOTH sides' permission class**, not a flag on one side.

### Deliberately not adopting

- **Name-as-address with no durable id.** Affordable only because their sessions are
  ephemeral and machine-local. A fleet that survives restarts cannot.
- **JSON-file mailboxes.** One malformed entry blocked a mailbox in a per-second error loop
  until v2.1.207.
- **No broadcast and no channels.** That is a solo-use scope choice, not a simplification to
  copy; aify-comms' channels are a real capability.
- **Auto-approving a teammate's plan in the lead's session** — an explicit hole in their own
  permission model.

### One thing to verify before quoting

The changelog and the docs DISAGREE on which version brought Windows support (v2.1.240 vs
v2.1.234). Do not cite either number without re-reading the source.

## Row 4 — SECURITY: independently audited, and the claim was too strong

Audited 2026-08-30 by a reader who did not write the code. Several findings were
MUTATION-PROVEN (a line deleted, the suite re-run, named tests going red), which is the
standard this repo holds. **Three of the six items are genuinely wired in and live. The
half that distributes the key is broken, and the docs describing it are false.**

What IS proven live: the cross-site guard returns 403 on the running container on both
:8800 and :8443; deleting `service/main.py:456` reddens two named tests; deleting the
websocket check at `:471-475` reddens another; aify-env's `browserOriginatedRequest` sits
at a single call site before routing and its deletion takes a suite from 7/0 to 4/3.

### The fix list, all of it v0.6 (defects in shipped work, not new features)

**F1 — Enabling the API key today would BREAK the fleet, and nothing says so.**
This is the most serious item because it inverts the operator's requirement that safety be
painless. `install.sh:2633-2635`: the hermes arm calls `install_hermes_config` and RETURNS
before the `mcp add` lines that pass the key. Measured: `API_KEY` appears **0** times in the
hermes env block (`install.sh:1838-1955`) against a control of **5** for `SERVER_URL` — a
positive-controlled zero, so it is a real absence. Hermes filters env to its stdio MCP
children, so nothing else can supply it. Same for the environment-bridge launcher: 0
occurrences in the generated block (`install.sh:1378-1560`, control 4) AND 0 in the installed
copy at `~/.local/bin/aify-comms` (control 3). So the moment `API_KEY` is set, hermes and the
bridge that owns spawning both 401 on every call, permanently.

**F2 — `README.md:99-101` is false.** It says the installer "passes the same value into every
wrapper and MCP config it writes". False on both halves: `API_KEY` count in the wrapper
templates is 0/0/0 for claude/codex/hermes (control `SERVER_URL`: 2/8/5). `install.hermes.md`
never mentions the key at all. A doc that overstates a security property is worse than one
that omits it.

**F3 — The guard does not stop the threat it cites.** `CrossSiteBrowserMiddleware` refuses
only `sec-fetch-site: cross-site`. `same-site` and `same-origin` pass — measured live: 200
with `Origin: https://evil.example`. That is precisely the shape a DNS-rebound page sends,
and DNS rebinding is the threat the commit message and the test docstring both quote. There
is no `TrustedHostMiddleware` and no Host check anywhere. **The fix is a Host allowlist, not
a cleverer Sec-Fetch rule.** The guard is still worth having — it closes ordinary drive-by
CSRF — but it must stop being described as closing rebinding.

**F4 — What is open right now.** `API_KEY` is unset (`.env:58`), so `APIKeyMiddleware` never
installs and all 75 mutating routes are open to anything that can reach the port; 8800, 8801
and 8443 are all published on 0.0.0.0. `GET /api/v1/agents` unauthenticated returns 47 rows,
14 carrying live gateway tokens. `console.py:281-283` gates keystroke injection only on the
caller being a registered agent id — and ids come free from that same unauthenticated
listing. Two requests to type into a live agent's terminal. NOT demonstrated by execution;
this is code-reading plus the live unauthenticated listing.

**F5 — aify-env has no authentication of any kind.** Loopback IS genuinely enforced
(`bin/aify-env.mjs:80`, hardcoded, no `--host` flag, used at both listens). But a grep for
`authorization|bearer|api.key|secret` across `lib/` and `bin/` returns zero against a working
control. Any local process can spawn, kill, resize and write keystrokes into a live coding
agent's PTY. Loopback is the entire model.

**F6 — `keyEnv` binds nothing today.** aify-wrapper's `lib/registry.mjs:192` is reached only
by `strictMcpEntriesFor` (`:222`), which filters on `strictMcp === true`; the live
`~/.aify/services.json` entry has `keyEnv` and **no** `strictMcp`. This is exactly the
"a declared field with no reader changes nothing" shape from my own memory rule — hit again,
in the same week I wrote the rule down.

**F7 — A test that would pass on an unrelated failure.** The websocket call-site test catches
bare `(WebSocketDisconnect, Exception)` and never asserts close code 1008.

### What the auditor explicitly could NOT verify

No write path was exercised against the live service. Whether codex's `mcp add --env`
survives the later `install_codex_mcp_env_vars` pass is untested. Whether an aify-env
delegated spawn inherits a key: no evidence either way. The "old browser sends neither
header" bypass is reasoned from the guards' design, not driven with a real browser.

## Row 5 — a SECOND defect found while measuring the coupling

`claude-aify.sh.in` resolves the session hook from `@@SCRIPT_DIR@@` (the repo checkout) while
the bridge, channel and reaper all resolve from the native copy. Confirmed on the INSTALLED
launcher: hook at `/c/Docker/aify-comms/...`, everything else at `~/.aify-comms/...`. Both
copies are byte-identical today (md5 8caff1b8), so it is latent, not biting.

Why it matters: the hook is then the one bridge file whose edits go live with NO install
step, while `doctor`'s `bridge-installed` would still be telling you to re-run the installer.
Nothing pins the directory in any test — the only assertion is that both hook entries name
the same filename.

Root cause is three placeholders for one concept, all of them only in this launcher:
`@@BRIDGE_DIR@@` (reaper), `@@NATIVE_BASE@@` (bridge, channel), `@@SCRIPT_DIR@@` (hook).
**Fix: collapse to `@@BRIDGE_DIR@@` everywhere.** That also deletes the `/mcp/stdio/` path
segments, which is three of row 5's four layout couplings — one change, both problems.

## Rows 1+2 — DASHBOARD: the console pipeline, measured, and hermes' compared

Audited 2026-08-30 from source on this machine. The auditor reported TWO false findings of
its own that dissolved under positive control, so every file:line here is a pointer to check.

### What the console actually is

Better than expected: real **xterm.js 5.5.0** with fit, unicode11, web-links and **WebGL**
addons, `scrollback: 5000`, OSC-52 clipboard, alt-screen wheel translation
(`service/new_dashboard/xterm-mount.mjs`). Not a naive `<pre>`. Output is **WebSocket-pushed,
not polled**. The pipeline is seven hops: bridge PTY coalesces (16ms/33ms/16KB,
`mcp/stdio/terminal-runtime.js:77-79`) → HTTP POST to `/terminals/{id}/output` → service
re-coalesces (`service/terminal_write_queue.py:41-44`) → **one global `_write_lock`** (`:68`,
module singleton `:283`) → server-side **pyte** VT emulation + full-blob rewrite
(`service/api_core/terminal_output.py:64-90`) → fleet-wide broadcast (`service/ws.py:29`) →
`term.write()` (`realtime-socket.mjs:141-168`).

### Ranked performance findings

1. **Input is one HTTP POST per keystroke, strictly serialised** (`terminal-input.mjs:1-12`).
   Each character pays a round trip AND waits for the previous one. The code already names
   the gap: *"Hermes uses one ordered WebSocket. We still cross the service API"*
   (`xterm-mount.mjs:144`). **The socket to fix it is already open and bidirectional** — the
   server explicitly throws client frames away: `await ws.receive_text()  # Keep alive, ignore
   client messages` (`service/main.py:483`).
2. **Attach/Refresh costs seconds and megabytes.** Two resizes, each confirmed by polling up
   to 30x100ms (`terminal-input.mjs:51-58`), each poll a full `GET /terminals/{id}` that
   flushes, `SELECT *`s a 64KB blob and fetches ~201 event rows, plus a hard 700ms sleep.
   Worst case ≈ **6.7s and ~4MB per Refresh click**, with no spinner and no disabled state.
3. **Every flush rewrites the whole 64KB buffer to SQLite** (`terminal_output.py:29-30,86-90`)
   on a database this repo documents as single-writer. Live reading: `outputSeq` 3586 and 3024
   on two terminals — thousands of full-blob UPDATEs already.
4. **Bytes are VT-emulated twice** — pyte server-side under the global lock (~0.9 MB/s per
   `terminal_snapshot.py:210`), then xterm in the browser. The server copy is also LOSSY
   (private CSI stripped, `terminal_snapshot.py:105`), so the attach snapshot is an
   approximation while the live stream is exact.
5. **Every tab receives every terminal's output** (`ws.py:29` broadcasts to all; the client
   filters). N x M by construction.
6. **Only one console can be open at a time, fleet-wide** — `state.activeXterm` is a single
   slot (`state.mjs:47`) and every mount disposes the previous. With 47 agents you cannot
   watch two.

### Hermes' dashboard, found and read

`C:\Users\Administrator\AppData\Local\hermes\hermes-agent\web\` + `hermes_cli/web_server.py`.
What it does better, concretely: **one bidirectional binary WebSocket for everything**
(`WS /api/pty`, output as raw `send_bytes` 1:1, keystrokes back over the same socket to
`bridge.write(raw)`); **resize in-band** via `\x1b[RESIZE:cols;rows]` — no POST, no
confirmation polling, no 700ms sleep; **no database and no server-side VT emulation** (an
in-memory 1 MiB ring per session, 16 sessions, 30-min TTL); **per-session socket** rather than
a fleet broadcast; newer xterm (6.0.0 vs our 5.5.0); and client polish we lack — a resume-burst
sanitiser that collapses Ink's erase floods, scroll-follow gated on xterm's write callback,
IME composition forwarding, ticket-based WS auth with distinct close codes.

7. Analytics fetch failure renders as "no data" — the error branch is unreachable.
8. **Spawn and Upload double-submit freely** — zero `disabled` guards. A double-click spawns

Then: a toggle labelled with its current state so it always promises the opposite; destructive

### Rows 1+2 — WHAT LANDED, 2026-08-31: relative times stop freezing

**First, a correction to the audit above.** Its headline UI/UX finding — `_agentSig` is `[id, status]`
and `_envSig` omits six rendered fields — is **already fixed** and was when the audit was written.
`_agentSig` carries twelve fields including `statusNote`, `runtime` and `poolSeverity`; `_envSig`
carries `bridgeBuild`, `unknownProcesses`, `terminalReason`, `manual`, `manualRoots`, `runtimes` and
`cwdRoots`. Read `render-memo.mjs` before re-reporting it. The count was wrong too: **14 `relTime`
call sites across 9 modules**, not 33 across 11.

**The half that was real is the half `render-memo.mjs` had already named**, in its own words: relative
times "must change as the clock advances even when no datum does. No signature can express that ...
Left as v0.6.1 work rather than half-done here." A memoised section repaints when a FIELD moves, so
"last seen 1m ago" beside an agent that died an hour ago is the display asserting the opposite of the
truth. That is not cosmetic: it is the field an operator reads to decide whether an agent is alive,
and this session spent a tick on 2026-08-31 chasing a live-looking `lastSeen` on a dead agent row.

**Shipped:**

| piece | where |
|---|---|
| `relTimeAt(value, nowMs)` — the clock as an argument, so a moment has one answer | `util.js` |
| `relTimeHtml(value, nowMs)` — the label plus the PARSED instant in `data-rel-ts` | `util.js` |
| `refreshRelTimes(elements, nowMs)` — re-derive labels at one clock reading | `rel-time-ticker.mjs` |
| `startRelTimeTicker({queryAll, ...})` — re-queries every tick, injectable timers | `rel-time-ticker.mjs` |
| started once at boot beside every other load-time listener | `boot-wiring.mjs` |

No section is re-rendered: only `textContent` is rewritten, and only on nodes whose label actually
changed, so an operator mid-selection is left alone. That restraint is the point — repainting on a
timer is the cure that was worse than the disease.

**Proven by mutation, not by a green run.** Three mutations, each with an assert that the mutation
APPLIED before the suite ran: dropping the "only write when it differs" guard reddened 2; capturing
the node list once instead of re-querying reddened 3; emitting a span for empty input reddened 1.

## B3 FIXED — advertising is judged on ACCEPTED beats, per service

**The reviewer's core safety invariant.** `/health.advertising` was `enabled && targets.length > 0`
and consulted no POST result at all, so a service answering 401, 404, 500 or nothing still reported

`advertiseTo` has always returned per-target `{ok, status}`, used only to print failures.

### aify-env

- `advertisementTargets` keeps the registry NAME with the endpoint. Without it, "am I advertising?"
  is only answerable for the daemon as a whole, so a success to service B counted as advertising to
  service A and stood A's bridge down for a beat it never received.

  A FUTURE stamp does not count, closing the same skew asymmetry the delivery ceiling had to.
- The staleness window is DERIVED (`MISSED_BEATS_BEFORE_STALE * intervalMs`), not a second constant
  that would drift the moment somebody tuned the interval.
- `/health` reports `advertisingTo`, keyed by registry name, alongside the scalar.

### aify-comms

- The bridge asks about ITSELF: `advertisingTo[SERVICE_NAME].fresh === true`. Every other shape —
  an older daemon with no such field, a name we do not appear under, an unreadable body, and now

  advertising. Absence is not evidence that we were told.
- `SERVICE_NAME` moved to `service-registry.mjs`, which owns the registry concept. It was a bare
