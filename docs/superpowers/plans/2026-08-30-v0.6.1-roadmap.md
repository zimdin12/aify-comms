# Findings

## Row 5 — SoC: aify-env and aify-wrapper as a base for an unrelated project

**Measured 2026-08-30**, with the search instrument positive-controlled (4 and 8 hits on
strings known to be present, 0 on one known absent) so the zeros below are real.

**aify-env is clean.** 25 source mentions of aify-comms, every one a COMMENT citing the
sibling's incident history. Naming a consumer in a comment is documentation; it is not
coupling. A new project can take aify-env as it stands.

**aify-wrapper is clean by NAME and coupled by SHAPE.** Zero literal `aify-comms` in
non-comment template code: the service name is fully parameterised, the channel server
included, as `@@SERVICE_NAME@@-channel`. But `wrappers/claude-aify.sh.in` hardcodes FOUR
paths into aify-comms' internal directory layout:

| line | hardcoded | should be |
|---|---|---|
| 427 | `${AIFY_SCRIPT_DIR_FWD}/mcp/stdio/server.js` | a placeholder |
| 456 | `${HARNESS_ENDPOINT}/mcp/sse` | a placeholder |
| 466 | `${AIFY_SCRIPT_DIR_FWD}/mcp/stdio/claude-channel.js` | a placeholder |
| 503, 506 | `${AIFY_SCRIPT_DIR_FWD}/mcp/stdio/claude-session-hook.js` | a placeholder |

The other three launchers (codex, hermes, pi) hardcode NOTHING — so the right pattern
already exists in the repo and only the claude launcher departs from it. `@@BRIDGE_DIR@@`
is already declared and is used at exactly ONE of the five sites (line 529).

**Consequence, stated concretely:** a new service built on aify-wrapper's claude launcher
must reproduce aify-comms' layout — an MCP bridge at `mcp/stdio/server.js`, a channel
server at `mcp/stdio/claude-channel.js`, a session hook at
`mcp/stdio/claude-session-hook.js`, and SSE served at `/mcp/sse`. That is not fatal, but it
is the answer to "are they really SoC'd": by name yes, by layout not yet.

**Fix shape:** extend the placeholder set the way the other three launchers already work.
Small, mechanical, gated by the existing render tests.

## Row 6 — aify-env TUI: what is there, and what the upgrade costs

- `lib/tui.mjs` (328 lines) is a PURE renderer: `renderDashboard(snapshot, {columns, color})`
  returns a string. `paint()` is the single place an escape is written, `width()`/`clip()`/
  `table()` handle measurement. Colour is already meaning-bearing by policy, never decorative.
- `lib/dashboard.mjs` (171 lines) is the loop: full screen CLEAR (`ESC[2J ESC[H`) then redraw
  on `setInterval`.

**The purity is the asset.** Panes can be pure functions over the same snapshot, which keeps
the architecture the operator asked for. Three things the upgrade actually needs:

1. **Stop the full clear.** Clear-and-redraw flickers and makes a right-hand pane unreadable.
   Needs differential rendering, or at minimum cursor-home + per-line erase.
2. **A focus model and raw-mode input.** The operator's idea (a right-side per-terminal view
   with an input option) means keyboard routing: some keys drive the dashboard, some go to the
   selected PTY. aify-env already has PTY custody, so writing input to a process is in reach.
3. **Colour and indicators with meaning.** The existing policy is right and should hold: every
   colour carries state. More indicators, not more decoration.

## Row 7 — Anthropic's cross-session messaging: what to take, what to leave

Researched 2026-08-30 from Anthropic's own docs and changelog. Two separate features:

- **Cross-session `SendMessage` + `ListAgents`** — GA, shipped v2.1.224 (2026-08-07), macOS
  and Linux first. Same-machine transport is a per-session UNIX socket / named pipe
  (`CLAUDE_CODE_MESSAGING_SOCKET` + a per-session token), never through Anthropic's servers;
  cross-machine goes through their servers over Remote Control.
  <https://code.claude.com/docs/en/cross-session-messaging>
- **Agent teams** — EXPERIMENTAL, off unless `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`.
  Different transport: a JSON-file mailbox per agent. `TeamCreate`/`TeamDelete` shipped and
  were then REMOVED in v2.1.178. <https://code.claude.com/docs/en/agent-teams>

They solved a NARROWER problem: one operator's own sessions, mostly one machine. No server,
no database, no dashboard, no dispatch queue, no durable identity, no channels, no file
sharing. aify-comms carries all of that because it targets heterogeneous runtimes and a fleet
that outlives any session. So this is a source of ideas, not a design to converge on.

### Worth adopting, ranked

1. **The anti-polling contract.** `notify_when_idle` is one-shot, opt-in, costs the WATCHED
   session nothing (it subscribes without starting a turn), and auto-expires at 12h — paired
   with an explicit instruction never to poll or send "are you done?". aify-comms has
   `comms_listen` and `comms_run_status`; a zero-cost expiring one-shot beats both.
2. **Every drop is reported to the SENDER, by name.** Roughly 15 changelog entries in the 21
   days after launch are this one lesson relearned: sent-but-dropped, held-with-no-notice,
   a malformed inbox blocking delivery. Given this repo's own favourite failure — a step that
   reports success and changes nothing — those entries are a ready-made defect checklist.
3. **Tell the model WHY the first line matters** rather than giving it a length rule: the
   human sees only the first line as a preview until they expand it. Cheaper and more
   effective than the subject-length rule aify-comms uses. (Feeds row 3.)
4. **Loop safety as THREE bounded mechanisms**, not one: per-sender rate limit, identical-
   repeat drop, hard queue cap (50 accepted / 100 held), bursts refused AT THE SENDER. The
   documented consequence is that a two-session message loop stops on its own.
5. **The permission-laundering prohibition, close to verbatim.** Never ask a peer to do what
   your own permission settings blocked — a peer doing it for you bypasses the user's
   decision. SHARPER here than there, because aify-comms spans runtimes with different
   permission postures.
6. **Inbound consent derived from BOTH sides' permission class**, not a flag on one side.

### Deliberately not adopting

- **Name-as-address with no durable id.** Affordable only because their sessions are
  ephemeral and machine-local. A fleet that survives restarts cannot.
- **JSON-file mailboxes.** One malformed entry blocked a mailbox in a per-second error loop
  until v2.1.207.
- **No broadcast and no channels.** That is a solo-use scope choice, not a simplification to
  copy; aify-comms' channels are a real capability.
- **Auto-approving a teammate's plan in the lead's session** — an explicit hole in their own
  permission model.

### One thing to verify before quoting

The changelog and the docs DISAGREE on which version brought Windows support (v2.1.240 vs
v2.1.234). Do not cite either number without re-reading the source.
