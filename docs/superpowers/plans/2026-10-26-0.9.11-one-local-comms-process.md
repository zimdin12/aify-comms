# 0.9.11: one small local comms process per Claude agent, the tools served by the service

**Why.** The operator, 2026-10-26: the stack must not cost performance or put excess context in front of
agents. Measured on this host with 4 Claude agents (private memory, Windows): each agent runs three comms
processes, about 200 MB per agent (the tool server `server.js` ~94 MB, the plugin channel ~79 MB, an idle
second channel ~30 MB). An empty Node process is 15 MB. A comms call through one extra local hop costs
0.17-0.18 ms and an idle connection about 8.8 KB, so the cost is the processes, not the networking. The
tools describe themselves in 24,485 bytes (34 tools, about 6,100 tokens).

**The constraint.** Claude's channel must be local: "A channel is an MCP server that runs on the same
machine as Claude Code. Claude Code spawns it as a subprocess and communicates over stdio" (Claude Code
channels reference). A channel server may also serve tools. HTTP is Claude's recommended remote transport
and SSE is deprecated; `headers` take `${VAR}` (Claude Code MCP docs). Hermes reads per-server `headers`
(hermes-agent `tools/mcp_tool_transport.py`); Codex already runs `url` servers here, and its binary carries
`http_headers` (behaviour unchecked).

## Target

- **The service serves the comms tools over Streamable HTTP**, one implementation, in place of today's two
  (the JS bridge tools and the Python copy in `service/sse/` behind the deprecated `/mcp/sse`). The caller's
  identity comes from a header the launcher writes per session with the API key, so no tool takes the
  agent id as an argument the model types. This reverses the recommendation recorded in
  `mcp/stdio/tests/transport-parity.test.js` (keep both copies, test their agreement): its reason, tools
  that needed a local process, is gone, and two copies drifted twice; the operator ruled for one.
- **The only local comms process is the channel**, for Claude only, holding the few tools that touch this
  machine. Hermes and Codex get a `url` entry and run no local comms tool process.
- **Expected:** about 200 MB to 25-30 MB per Claude agent (estimate from the 15 MB empty Node and the 30 MB
  idle channel), about 3.5 GB at 20 agents. Pre-registered: above 40 MB per Claude agent after the switch,
  stop and re-plan.

## Slice 1 findings (2026-10-26, read at comms 37d0ee78 and the live service)

**Tools.** 34 in JS, in 14 modules under `mcp/stdio/*-tool(s).mjs`. In service mode (`IS_REMOTE`), four read or
write this machine (corrected in review; a first pass found three):
- `comms_share` with a `filePath` reads it, binary or text.
- `comms_read` of a binary artifact writes it to TEMP.
- `comms_agents` reads the pid binding (`bound-agent-id.mjs`) and prefers it over `AIFY_AGENT_ID` to mark the
  caller's row.
- `comms_register` writes the pid binding, writes the hermes session marker, moves a captured Claude session to
  the agent's key, and reads and prunes runtime markers. Start-up registration must keep or deliberately replace
  each of these, and the runtime, session and config capture.

Other local inputs besides `AIFY_AGENT_ID`: `comms_agent_info` falls back to this machine's id
(`agent-summary.mjs`) when the service row has none. So an identity header alone does not replace the local
process; each local input needs a named replacement.

The Python copy (`service/sse/`) serves 21 comms tools, all also in JS (its transport has 28 names; seven are
service and container tools). The 13 it lacks: agent_info, compact, contracts, delete_session, describe, envs,
interrupt, remove_agent, restart, spawn, status, unsend, usage. Each calls service routes. Name parity is not
behaviour parity: the port keeps each tool's requester apart from its target or member ids.

**Who delivers**, from `dispatch-execution.js` and the live settings (`managed_via_wrapper` = codex, hermes; 18
Claude, 9 hermes and 2 Codex agents):

| duty | Claude | hermes | Codex |
|---|---|---|---|
| claims and delivers runs | the channel (`claude-channel.js`) | the delivery loop (`hermes-managed-host.js run`) | **the tool bridge inside codex-aify** (`AIFY_MANAGED_VIA_WRAPPER=1`), through the app-server |
| liveness beat | bridge **and** channel | bridge **and** loop | bridge |
| gateway probe, turn detector | none | bridge **and** loop, both armed by the gateway URL | none |
| runtime marker | channel (`claude-channel.js` writes and removes it; the bridge only reads and selects Claude markers when registering) | bridge | bridge |
| session handle | bridge (adapter heartbeat) | bridge (adapter heartbeat) **and** loop (`startResumeSync`: the durable resume marker, and a handle PATCH on change) | bridge |
| resident-lost at exit | bridge | **managed host**: the launcher exports `AIFY_RESIDENT_LIFECYCLE_OWNER=managed-host`, and `resident-lost.mjs` declines the MCP child's report | bridge |
| auto-registration, binding file | bridge | bridge | bridge |

So:
- The Claude and hermes tool bridges deliver nothing. Their beats and hermes probes repeat the channel's and the loop's. Proposed: the channel and the loop take auto-registration and the adapter's session-handle beat. Each contract stays as it is, so hermes' exit stays the managed host's report, and the loop's resume sync stays separate from the handle beat.
- The two hermes turn detectors were a race, not only a cost (review of bd829e7b, which claimed otherwise). Each stamps its edge after an awaited gateway read. So a delayed idle from the bridge's detector reached aify-env with a newer time than the loop's working edge, and closed a working turn. Removed from the bridge in 0.9.10 (`tests/one-hermes-turn-detector-per-agent.test.js`). The service ignores `/turn-start` and `/turn-end`, so only the aify-env edge mattered. Limit: the launcher proves it requested the loop wherever it exports the gateway URL, not that the loop runs healthy (no health gate since wrapper ≈969-976), so a hermes agent whose loop failed has no detector-derived live turn observation. Its exit still posts a turn-end to aify-env through the launcher's exit trap (`bin/aify-runtime-exited.sh`).
- **Codex cannot simply lose its local process:** its bridge is its delivery. Proposed: a Codex delivery loop beside the launcher, the shape hermes already has, holding the app-server controller. Deferred to `docs/CODEX_CATCHUP.md` (operator, 2026-10-27).
- The native `managed` path (`launchRuntimeRun` → codex-session, hermes-session) runs only for a runtime missing from `managed_via_wrapper`. Both are listed, so nothing on this host reaches it. It is a deletion candidate for slice 5.
- File upload and download for hermes and Codex: proposed in the loop beside each (a local tool would bring back the process). Undecided.

## Decided

**Local mode goes** (operator, 2026-10-26: each concern belongs to the part assigned it, and comms is not the
service's backup or a spawner). With no service URL, the bridge is its own backend: messages as files
(`local-store.mjs`) and a runtime launcher (`spawn-triggered-agent.mjs`) that starts agents without
aify-env, the only spawner. It is a second copy of the service. Every install sets a service URL, so
nothing should use it (assumed; slice 1 checks).

**The one tool set is the Python copy inside the service** (operator, 2026-10-27, option A): port the 13 tools
it lacks and match the replies agents see today; header identity is read in the service. The JS tools are not
moved into the container.

**Codex keeps its local process this round** (operator, 2026-10-27): it catches up once Claude and hermes are
proven on 0.9.11. Its delivery loop, its `url` entry and the deletion of the JS tool modules move to
`docs/CODEX_CATCHUP.md`, so slices 3-5 below cover Claude and hermes only, and slice 5 keeps the JS tool modules. Until then the
two tool copies both serve agents (Python for Claude and hermes, JS for Codex), so
`mcp/stdio/tests/transport-parity.test.js` stays and must cover the 13 ported tools too.

## Slices

1. Verify the inventory per tool; diff the JS and Python tool sets. Map every duty the bridge process holds
   (above) to its owner per runtime, and name the replacement before anything is deleted; qualify cold start,
   incoming send and steer, handle change, idle and exit on each runtime. "Only the channel is local" holds
   only where that map says so.
2. Service: Streamable HTTP endpoint, header identity, the one tool set. Rewrite the tool descriptions in
   the same pass, and hold `tools/list` at its new size with a ratchet test, as the skills are.
   **Slice 2 design (2026-10-27).**
   - *Endpoint:* `<service>/mcp/http`, FastMCP's Streamable HTTP in the same Starlette mount as `/mcp/sse`,
     **stateless with JSON responses**: no session lives in the service, so a rebuild or restart costs a
     client nothing (a stateful session would 404 every connected agent after each deploy). The API-key
     middleware already guards `/mcp`.
   - *Identity:* the `X-Aify-Agent-Id` request header, read per call from the request in the tool's MCP
     context. A tool that acts as the caller refuses a call without one; nothing falls back to an argument.
     Nothing on this host uses `/mcp/sse` (read 2026-10-27: no comms client config names it), so the
     Python tools change to header identity outright.
   - *Parity:* reply fixtures `{tool, args, caller, routes, text}`, recorded once from today's JS handlers
     in service mode. Both suites run every fixture: Python must produce `text`, and so must JS while
     Codex keeps it. Local-mode branches are not ported.
   - *Order:* the endpoint and identity first, then the tools group by group, then the descriptions and the
     `tools/list` ratchet.
   - *Caller adaptation (review of 4fa01c08):* the header replaces exactly the JS arguments a case names
     in `callerArgs`: `from` on send, channel create/join/leave/send/delete, unsend, unshare, share, spawn,
     compact, run_interrupt, interrupt; `agentId` on status, describe, inbox. Targets, members and filters
     stay arguments: channel_join `agentId` (the member to add), search `agentId`, contracts `agentId` and
     `fromAgent` (renamed from `from` in both copies: FastMCP cannot take an argument named `from`).
     Local context the JS read has a named replacement: the pid binding behind comms_agents' `(you)` is
     the header; the machine id behind a record without `machineId` prints `?`.
   - *Where the copies were raised, not matched:* the JS was brought up to the Python's containment where
     the Python had it (run summary and error fenced, event bodies on one clipped line, run and dashboard
     subjects quoted, files capped at 200), and both print channel times in UTC.
   - *Status 2026-10-27:* every tool but comms_register is ported and held by 136 cases over 33 tools,
     schemas compared. The agent-facing list is the comms tools only (the container and service tools came
     off MCP), and comms_register changes the header caller's role and name only. tools/list is 34 tools in 18,580 UTF-8 bytes
     against the JS tools' 24,533, held by `test_the_tool_list_is_held_at_its_size.py`. The published input
     schemas are 5,507 bytes smaller than pydantic writes them (titles, `anyOf` with null); the rest is
     wording that changed no decision. An optional argument is published without null, as the JS publishes
     it: the service still accepts an explicit null, which means the same as leaving it out, and the same
     test holds that every folded argument is optional with a null default.
   **Slice 3 design (2026-10-27, proposed).** The Claude channel (`claude-channel.js`) becomes Claude's only
   local comms process, so it takes what slice 1's map gives the tool bridge for Claude: auto-registration
   with runtime, session and config capture and the pid binding file; the adapter's session-handle beat;
   resident-lost at exit. It already holds delivery, the liveness beat and the runtime marker.
   - *Local tools, file transfer only:* `comms_share_file` (a local file by path, any type) and
     `comms_save_file` (an artifact saved to a local path). Distinct names, because a channel tool named
     `comms_share` would sit beside the service's under another server prefix, and two tools of one name
     cost context and invite the wrong pick. Text share and read stay with the service.
   - *comms_register* (revised after review, 2026-10-27): a registration is a full refresh of runtime,
     session, config and capabilities, and a header caller has none of them. A thin POST /agents turned a
     native resident `generic` with no handle (reproduced by review). The service tool now changes role and
     name only (`PATCH /agents/{id}/profile`), and an unregistered caller is told its launcher registers it.
     Either order with the channel's start-up registration is then safe, and no thin record is written.
   - *Duties carried from `server.js`, each inside the producer gate (`runChannel`, `claude-channel.js`), so
     an inactive copy registers nothing and tears nothing down:* the `AIFY_BRIDGE_DISABLED` refusal (82-94);
     start-up registration through `auto-registration.mjs`, with its retry and same-session, tombstone and
     managed-ownership guards; the binding file and its owner-matched removal (`binding-file.js`); stdin EOF
     and parent-death shutdown (`bridge-main.mjs` 28-58); resident-lost on SIGINT/SIGTERM/SIGHUP, once and
     bounded to 1.5 s (283-333). Not carried: managed PTY and session pools, the tool registry.
   - *Two ids, one per role, both from one process: today's live pair, moved, not merged.* The OWNER id is
     per process (`BRIDGE_INSTANCE_ID`): registration, `runtimeState.bridgeInstanceId`, the binding file,
     the handle PATCH and resident-lost. The service's resident-lost and the binding-file removal act only on
     a matching owner id, so an old channel exiting after its successor registered changes nothing. The
     DELIVERY id stays `channelBridgeId(agentId)`, kind `channel-sidecar`: beat and claims. The service is
     built around that row: a resident registration never supersedes a `channel-sidecar` row
     (`api_core/bridge_registration.py`), and a superseded sidecar heals itself on its next claim
     (`dispatch_claim.py`). One merged id would put the registration under both rules.
   - *Rollout:* the channel takes these duties only on a launch whose comms tools come over HTTP, which the
     slice 4 launcher says with `AIFY_COMMS_MCP=http`. A launch still running `server.js` keeps it doing
     them, so no agent is registered twice under two owner ids. Slice 5 deletes the condition.
   - *Cost:* reusing `auto-registration.mjs` rather than a second copy of its payload adds 6 MB to the
     channel (76 to 82 MB RSS on import, three runs). Measured against the 40 MB line at the switch.
   - *Cutover census:* `.claude-plugin/.mcp.json` still starts `server.js` for the plugin route.
   - *Qualify on a real Claude:* Claude's documentation supports tools beside `claude/channel`; still
     observe the channel's tools listed on both routes (plugin and development), and the channel near its
     measured idle size.
   - *Where the entry lives* (per launch or machine-wide) is the operator's call, asked 2026-10-27.
