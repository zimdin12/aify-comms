# S2c: the other nine C8 owners (2026-10-19)

Status-switch plan S2, its remaining half. Only the status word is measured today (S1, S2a, S2b, Q3). C8 needs all
ten decisions measured in the same evaluation, on the same rows, with a nonzero denominator each.

## The one new thing: `commsView`, pure

Nine of the ten end-state answers are C6's view: `status`, `holdsDelivery` (strict and P-1), `runOccupied`,
`deliverable`, and the delivery turn's open and `runId`. Today only the word's candidate exists
(`partial_status_shadow.candidate_word`). S2c builds `commsView(binding_rows, messaging) -> View` as one pure function
in its own module. The shadow calls it now, and S4 calls the same function in the gates, so nothing here is built to be
thrown away.

- **Inputs:** the env record(s) for the agent, from the same `Binding` the word shadow reads; and the messaging facts
  comms already holds: the definition flags (D8), the active run and its usability (`hasActiveRun`), queued runs, and
  the delivery turn.
- **The delivery turn during the shadow** is read from the run half of today's `agent_turn_state` row: `runId`,
  touched and started. C6's merge rules make it the same row, so no new table is needed before S4. The record-driven
  updates (touched on an advance, closed on a turn-end) are computed in the view from the record. They are not written
  anywhere.

## Isolation, the one property every site must keep

The candidate never changes today's answer. Each site computes today's answer first, then calls the shadow inside a
`try`. A shadow that raises counts `unavailable:<reason>` and the site returns today's answer. One test per site
proves it: a candidate forced to raise leaves the gate's decision and its side effects identical.

## Slices, each one review

1. `commsView` (pure), plus the busy owner at `_turn_busy_holds_delivery`. Busy is the delivery decision, so it goes
   first.
2. The four busy consumers: queue, claim, reminder skip, stranded guard.
3. Worker readiness, live counts, running-run promotion.
4. B6 in aify-env: publish its build and `turn.ageMs`, with the receiver and wrapper schema copies in the same
   rollout. The comms and wrapper suites run with `AIFY_ENV_REPO` set to the candidate. Then the ceiling owner, and the
   windows carry the real env version.
5. The unseen-class controls (C8's list), as deterministic tests through `commsView`.

Witness per slice: one constructible history per owner where today and the view agree, and one where they differ for a
named reason, both through the real call site.

## What would prove this wrong

- A decision site whose inputs are not all readable in the same evaluation, for example a gate that reads a row
  after it writes one. That owner then needs its own capture point, and this plan gets a row.
- A measurable latency added to the claim path. The env side comes from the in-memory mirror. The messaging facts are
  DB rows, so each slice reuses the rows its site already read, and names and measures any query it adds in its
  review.
