# v0.6.3 — a real console in aify-env, and the menus around it

Operator, 2026-09-08: *"in web dashboard i see hermes and claude code terminal well. i would like to
see it in aify-env also when console is shown (only then)... we need good, fast and stable solution,
not something buggy or laggy or performance hog."*

## The finding, and it is smaller than it looked

**The browser renders agent TUIs correctly because it runs a VT emulator.** `index.html:13-19` loads
`@xterm/xterm@5.5.0` from `vendor/xterm.js`. aify-env's pane has no emulator — `pane-buffer.mjs` is a
LINE BUFFER, and a coding agent does not print lines, it paints a picture with `ESC[row;colH`, `ESC[K`
and `ESC[A`-`G`. `isPainting()` detects that addressing and shows `live TUI — this pane cannot draw
it` rather than shredded text in the wrong order. It is refusing on purpose.

**So the gap is a renderer, not a transport.** Three things measured 2026-09-08 rather than recalled:

| question | answer | evidence |
|---|---|---|
| Who owns the PTY? | aify-env | `node-pty` required at `aify-env/lib/runner.mjs:83` |
| Does aify-wrapper own one? | **No** | zero matches in `aify-wrapper/lib/`; every "pty" hit there is the word "em*pty*". It is four `.sh.in` launcher scripts that set env and exec a runtime |
| Where does the pane's data come from? | aify-env's OWN daemon | `output-follower.mjs:84` builds the URL `{endpoint}/processes/{id}/output`, endpoint = `http://127.0.0.1:8802` |

**This retires the operator's "we need to send that terminal to both aify-comms and to aify-env".**
It already goes to both. aify-env owns the bytes FIRST — it holds the PTY — and streams a copy to
aify-comms, which stores the raw log and keeps a live pyte screen for the web client. aify-env's pane
is reading its own local copy over loopback today. Nothing needs to be sent anywhere new.

**And it retires my own earlier recommendation.** I proposed the pane fetch aify-comms' pyte-rendered
snapshot. That is a network round-trip per repaint, for bytes the process already holds in memory —
laggy by construction, which is the thing the operator ruled out by name. Rendering locally is both
the faster and the architecturally correct option, and I had it backwards.

## The design

**`@xterm/headless@5.5.0`, fed the local stream, only while the pane is shown.**

- **The same emulator that already works.** `@xterm/headless` is xterm.js without the DOM ("a headless
  terminal component that runs in Node.js"), and **5.5.0 is published** — the exact parser version the
  dashboard pins. Every escape the fleet emits is one this code already renders correctly on the
  operator's screen today. A hand-written emulator would rediscover `terminal_snapshot.py`'s scar
  tissue from scratch: `strip_private_sgr` exists because *"pyte, which implements none of them,
  corrupts the screen with two of the four the fleet emits"*, plus alt-screen balancing and width
  inference. That is a year of collisions with these specific agents.
- **An OPTIONAL dependency, like node-pty.** `aify-env/package.json` has NO hard dependencies —
  `node-pty` is `optionalDependencies` on purpose, and the view degrades to "terminals UNAVAILABLE"
  without it. The console degrades the same way: absent emulator, today's honest notice.
- **Only while shown, which is now enforceable.** `919f531` gave the pane a `paneHidden` flag and
  `pane()` returns null when it is set. That flag is the gate: no emulator constructed, no byte
  parsed, no follower running while the console is hidden. The operator asked for exactly this ("when
  console is shown (only then)") and the mechanism landed before the request.

### PROVEN BEFORE WRITING ANY OF IT, 2026-09-08, Node v22.20.0

The design rests on one assumption -- that this emulator advances its buffer from a chunk stream with
no DOM and no render loop. A scratch install of `@xterm/headless@5.5.0` was driven with painter
output. Results, each one a thing that would have killed the design:

| probe | result |
|---|---|
| Out-of-order absolute painting (`ESC[3;5H` written BEFORE `ESC[1;1H`) | reconstructed in the right places |
| Erase-in-line (`ESC[K`) overwriting a previous row | correct |
| **An escape split across THREE chunks** (`ESC` / `[2;` / `4HLANDED`) | reassembled correctly |
| Carriage-return spinner (a `Working.` line rewritten twice by CR) | one line, final state |
| Colour recoverable from cells for B5 | `getFgColor() === 2`, `isFgPalette() === true` |
| **Active handles after `dispose()`** | **`[]`, and the process exits on its own** |

That last row is the one that matters: **no render loop, no timers, nothing to leak.** Construction
and disposal per show is therefore cheap and complete, which is what makes "only while the console is
shown" a real gate rather than an intention.

**It is CommonJS**, so an ESM codebase imports the default and destructures -- `import headless from
"@xterm/headless"; const { Terminal } = headless;`. A named import throws at load. Worth knowing
before B2, because the optional-import wrapper has to survive both absence AND this shape.

**One claim in the first draft of this plan was sloppy and is corrected here.** I wrote that the probe
split an escape across chunks; it had split TEXT across chunks, which proves much less. The escape
split is its own row above because a real byte stream will break a sequence at a buffer boundary, and
an emulator that mishandled it would produce garbage exactly under load.

### Why this cannot be a performance hog, as budgets to measure rather than adjectives

- **One emulator, for the SELECTED process only.** Constructed on show, disposed on hide and on
  selection change. Not one per process.
- **Sized to the pane**, not to the terminal — a 40x20 grid, resized when the layout changes.
- **Parse is O(bytes); render is O(rows x cols).** At pane size that is ~800 cells per frame.
- **No re-render when the screen did not change** — the frame differ already refuses identical output.
- **Bounded by the same 2s refresh** the whole view runs on.

## The work, in loop-sized blocks

Each block: written, mutation-proven, five suites with their OWN exit statuses, committed and pushed
before the next. Counts updated in all three CLAUDE.md sites.

**B1 — `lib/screen-render.mjs`, pure, no dependency.** Takes an xterm buffer-like object and returns
the lines a pane draws. Written against a FAKE buffer so it is testable with no emulator installed,
which is also what makes B2's absence survivable. Proof: a positive control that real agent bytes
produce readable text, and a negative control that it can report an empty screen.

**B2 — the emulator behind an optional import.** `lib/screen-emulator.mjs`: constructs
`@xterm/headless`, feeds it chunks, exposes `lines({rows, cols})`, disposes. Absent module resolves to
null and every caller falls back to today's notice. Proof: the suite passes with the package
UNINSTALLED — that is the control proving the optional path is real rather than decoration.

**B3 — wire it into the pane.** `pane-buffer.mjs` keeps its line buffer for non-painting processes (a
plain log needs no emulator and must not get slower). When `isPainting()` and an emulator exists, draw
the screen instead of the notice. Proof: the notice still appears with no emulator; the screen appears
with one; the plain-log path is byte-identical to today.

**B4 — lifecycle and budget.** Construct on show, dispose on hide / switch / exit, resize on layout
change. Proof: hiding the pane disposes the emulator and stops the follower; switching agents does not
leak the previous screen into the next — the "superseded mount" defect the dashboard already has a
test for, reproduced here before it can happen.

**B5 — colour.** Text-first is the ship that answers the stated need ("see what the agent is doing");
SGR read from the buffer's cells is a separate block so B3 can land and be used tonight. Proof: a
coloured run survives the round trip and an uncoloured one gains no escapes.

**B6 — the menus.** A select-an-agent submenu (attach / stop / restart) and a spawn flow reading
available agents through the aify-comms plugin. **Two operator decisions are needed before this
block** — see below. `keys.mjs` is two modes plus a picker; menus need a real modal layer rather than
flags bolted onto it, or that file stops being trustworthy.

**B7 — the end-of-version pass**, which the operator wants at every version:
- docs and skills read against the code, not against intention;
- **dashboard settings audited by TRACING FROM CODE** — for each setting: is it still read, does the
  reader still do what the label says, is it stale. A setting whose reader was deleted looks identical
  to one that works;
- the three-suite counts, and the two the history omits;
- dev review last, on the whole diff.

## Blocking on the operator (B6 only — B1..B5 and B7 need nothing)

1. **Does stop confirm?** It kills a live worker mid-turn.
2. **What is "start available agent"?** Spawning a NEW managed worker, or re-attaching one aify-comms
   knows about but is not currently running?

## What is NOT in this plan, and why

**The "dashboard console corruption" item is narrowed, not folded in.** The operator says hermes and
claude-code terminals render *well* in the web dashboard, which contradicts the general claim I was
carrying. The specific artifact they reported earlier ("that empty character cache or something") is a
narrower defect and needs its own repro before anyone designs for it. Carrying it as a general
statement would have justified rewriting a transport that is working.
