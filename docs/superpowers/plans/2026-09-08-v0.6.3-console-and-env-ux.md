# v0.6.3 — a real console in aify-env, and the menus around it

Operator, 2026-09-08: *"in web dashboard i see hermes and claude code terminal well. i would like to
see it in aify-env also when console is shown (only then)... we need good, fast and stable solution,
not something buggy or laggy or performance hog."*

## The finding, and it is smaller than it looked

**The browser renders agent TUIs correctly because it runs a VT emulator.** `index.html:13-19` loads
`@xterm/xterm@5.5.0` from `vendor/xterm.js`. aify-env's pane has no emulator — `pane-buffer.mjs` is a
LINE BUFFER, and a coding agent does not print lines, it paints a picture with `ESC[row;colH`, `ESC[K`
and `ESC[A`-`G`. `isPainting()` detects that addressing and shows `live TUI — this pane cannot draw
it` rather than shredded text in the wrong order. It is refusing on purpose.

**So the gap is a renderer, not a transport.** Three things measured 2026-09-08 rather than recalled:

| question | answer | evidence |
|---|---|---|
| Who owns the PTY? | aify-env | `node-pty` required at `aify-env/lib/runner.mjs:83` |
| Does aify-wrapper own one? | **No** | zero matches in `aify-wrapper/lib/`; every "pty" hit there is the word "em*pty*". It is four `.sh.in` launcher scripts that set env and exec a runtime |
| Where does the pane's data come from? | aify-env's OWN daemon | `output-follower.mjs:84` builds the URL `{endpoint}/processes/{id}/output`, endpoint = `http://127.0.0.1:8802` |

**This retires the operator's "we need to send that terminal to both aify-comms and to aify-env".**
It already goes to both. aify-env owns the bytes FIRST — it holds the PTY — and streams a copy to
aify-comms, which stores the raw log and keeps a live pyte screen for the web client. aify-env's pane
is reading its own local copy over loopback today. Nothing needs to be sent anywhere new.

**And it retires my own earlier recommendation.** I proposed the pane fetch aify-comms' pyte-rendered
snapshot. That is a network round-trip per repaint, for bytes the process already holds in memory —
laggy by construction, which is the thing the operator ruled out by name. Rendering locally is both
the faster and the architecturally correct option, and I had it backwards.

## The design

**`@xterm/headless@5.5.0`, fed the local stream, only while the pane is shown.**

- **The same emulator that already works.** `@xterm/headless` is xterm.js without the DOM ("a headless
  terminal component that runs in Node.js"), and **5.5.0 is published** — the exact parser version the
  dashboard pins. Every escape the fleet emits is one this code already renders correctly on the
  operator's screen today. A hand-written emulator would rediscover `terminal_snapshot.py`'s scar
  tissue from scratch: `strip_private_sgr` exists because *"pyte, which implements none of them,
  corrupts the screen with two of the four the fleet emits"*, plus alt-screen balancing and width
  inference. That is a year of collisions with these specific agents.
- **An OPTIONAL dependency, like node-pty.** `aify-env/package.json` has NO hard dependencies —
  `node-pty` is `optionalDependencies` on purpose, and the view degrades to "terminals UNAVAILABLE"
  without it. The console degrades the same way: absent emulator, today's honest notice.
- **Only while shown, which is a flag that EXISTS and a gate that does NOT yet.** `919f531` gave the
  pane a `paneHidden` flag and `pane()` returns null when it is set. **It said "no follower running
  while the console is hidden" before that was true**: review reported it and I measured it -- with
  the pane hidden, `pane()` returned `null` while `syncProcesses` still opened a follower and set
  `watchedId`, and every arrow key opened and closed one. **Closed in `41f4032`**: the follower is
  derived from visibility as well as selection, so a hidden pane holds no connection and no buffer.
  What is still NOT held is the emulator half -- nothing constructs or parses yet, so there is
  nothing to gate, and B2/B3 must arrive already gated rather than gaining it later. And drawability
  remains the wider rule (`fed1aea`): `paneHidden` says what this session INTENDS, while the
  compositor decides what is drawn, so input is gated on a reported viewport too.

### PROVEN BEFORE WRITING ANY OF IT, 2026-09-08, Node v22.20.0

The design rests on one assumption -- that this emulator advances its buffer from a chunk stream with
no DOM and no render loop. A scratch install of `@xterm/headless@5.5.0` was driven with painter
output. Results, each one a thing that would have killed the design:

| probe | result |
|---|---|
| Out-of-order absolute painting (`ESC[3;5H` written BEFORE `ESC[1;1H`) | reconstructed in the right places |
| Erase-in-line (`ESC[K`) overwriting a previous row | correct |
| **An escape split across THREE chunks** (`ESC` / `[2;` / `4HLANDED`) | reassembled correctly |
| Carriage-return spinner (a `Working.` line rewritten twice by CR) | one line, final state |
| Colour recoverable from cells for B5 | `getFgColor() === 2`, `isFgPalette() === true` |
| **Active handles after `dispose()`** | **`[]`, and the process exits on its own** |

**THE INFERENCE I DREW FROM THE LAST ROW WAS WRONG, and amendment 4 below retires it.** I wrote
"no render loop, no timers, nothing to leak ... cheap and complete". The probe measured active
HANDLES after `dispose()`; it did not measure QUEUED WORK, and those are different nouns. A write
callback DOES fire after `dispose()` (measured), and review observed a parser timeout too. Eventual
process exit proves neither timer absence nor stale-callback cancellation. What the row still
supports is narrower and worth keeping: **no render loop is required to advance the buffer.** That is
all.

**It is CommonJS**, so an ESM codebase imports the default and destructures -- `import headless from
"@xterm/headless"; const { Terminal } = headless;`. A named import throws at load. Worth knowing
before B2, because the optional-import wrapper has to survive both absence AND this shape.

**One claim in the first draft of this plan was sloppy and is corrected here.** I wrote that the probe
split an escape across chunks; it had split TEXT across chunks, which proves much less. The escape
split is its own row above because a real byte stream will break a sequence at a buffer boundary, and
an emulator that mishandled it would produce garbage exactly under load.

### Why this cannot be a performance hog, as budgets to measure rather than adjectives

- **One emulator, for the SELECTED process only.** Constructed on show, disposed on hide and on
  selection change. Not one per process. Disposal must include a generation check, because a queued
  callback outlives it (amendment 4).
- **Sized to the PRODUCER, and the pane crops.** ~~Sized to the pane~~ was wrong and amendment 1
  killed it with a measurement: a narrow emulator wraps overflow onto the next row and shows a
  different screen, not a smaller one.
- **Parse is O(bytes); render is O(rows x cols)** at the PRODUCER's grid, so a 132x40 agent is ~5,300
  cells per frame rather than the ~800 this line claimed when it assumed a pane-sized terminal.
- **No re-render when the screen did not change** — the frame differ already refuses identical output.
- **The 2s refresh bounds REDRAW ONLY.** It was written here as though it bounded everything; it does
  not bound parse, backlog or memory, and none of those has a number yet. Each needs its own budget
  and its own measurement before B3 can claim to be fast.

## REVIEW AMENDMENTS — comms-senior-dev, 2026-09-08, all four REPRODUCED here

Design review came back blocking on four points. I re-measured each against the real package rather
than accepting them, and **all four hold**. One of them kills the design above.

**1. GEOMETRY. The emulator runs at the PRODUCER's size, and the pane CROPS.** This retires "sized to
the pane" from the section above, which was mine and was wrong. The measurement is worse than the
objection: feeding identical bytes to an 80-column and a 40-column terminal does not merely clip
differently, it WRAPS. Row 1 overflows onto row 2 and collides with the text that belongs there --
at 40 columns, `row two` came back as `row twoxxxxxxxxxxxxxCOL61-ON`. **A narrow emulator does not
show less of the screen; it shows a different and wrong one.** Consequences: the producer's geometry
has to be known and carried, a PTY resize needs ONE owner and has to be ordered against output, and
the pane's own width stops being an input to the emulator entirely.

**2. "CONSTRUCT ON SHOW" NEEDS A SEED, NOT A SUFFIX.** Starting an emulator when the pane opens and
feeding it only what arrives from then on cannot recover earlier positioned text, SGR state, alt-screen
and mode history, or geometry changes. Review's witness lost text and style on remount. So showing the
pane means replaying a complete seed and then joining live, deduplicated and contiguous -- the same
contract the console-handoff item has been carrying. "Do not wait until `isPainting()` to start
consuming the history you will need" is the sharp version, and it constrains B3 and B4 together.

**3. SAME VERSION IS NOT PARITY: the browser runs Unicode 11, headless defaults to Unicode 6.**
Measured: `term.unicode.activeVersion === "6"` on a default headless terminal, while `index.html`
loads `@xterm/addon-unicode11`. Emoji then measure 1 cell here and 2 there, so the two surfaces
disagree about where every character after one sits. The addon has to be loaded and activated
headless too -- which weakens "the same parser, so they agree by construction" to "the same parser
CONFIGURED THE SAME WAY", and that is a thing to assert in a test rather than assume.

**4. A WRITE CALLBACK FIRES AFTER `dispose()`.** Measured true. `write()` is asynchronous and uses
zero-delay timers, so an immediate buffer read is stale and completion callbacks are mandatory --
and a queued one survives disposal. **That is the superseded-mount defect with a new door**: a late
callback writing into the pane after the operator switched agents. Generation or process checks on
every callback, plus upstream abort/unsubscribe, are required rather than tidy. My earlier probe
showed zero active handles after dispose and I read that as "nothing to leak"; it measured handles,
not queued work, and those are different nouns.

**5. TEXT-FIRST MUST HONOUR CONCEAL.** `translateToString` returns SGR-8 hidden content verbatim:
`ESC[8mSECRETVALUE` came back as plain `SECRETVALUE` in the row text. An agent conceals things for a
reason, and a pane that prints them is disclosing what the terminal was told to hide. The cell API
does expose it (`isInvisible()` returns a truthy flag), so rows must be built from CELLS rather than
from `translateToString`. **Ordinary colour can wait; semantic visibility cannot.** This moves from
B5 into B2, where the rows are read.

**Also accepted without needing a probe:** no public `onWriteParsed` in headless 5.5.0, so dirtiness
comes from write completion plus resize/viewport rather than movement events (which miss erase-only
writes); `allowProposedApi: true` is required for buffer access; and a passive mirror must NOT forward
the emulator's `onData` replies, because device queries would then inject synthetic input into a live
agent's PTY. The 2s refresh bounds redraw and does NOT bound parse, backlog or memory, so those need
their own budget.

**What review did NOT concede, and I agree:** the previously reproduced snapshot/delta race stays a
distinct item from the operator's "renders well but lags sometimes", and neither justifies a broad
dashboard rewrite without attribution evidence.

## THE DEPLOYED DEFECT IS A CLIFF, NOT A SLOPE, 2026-09-09

**THE SHAPE OF THE RISK WAS UNSTATED, and it is the half that decides whether the margin
matters.** Two facts were established and neither answered it: the running build numbers frames
per POST, and on this fleet nothing coalesces -- zero wire gaps across every window. So does a
slightly busier console degrade gently, or fall off? (How CLOSE the fleet runs to coalescing is
a separate question and an unmeasured one: the arrival-interval margin that used to answer it
here is withdrawn, for the reason given in the hop-four section.)

**DRIVEN RATHER THAN REASONED**, on both modules in one run, with the browser's own rule applied
to the sequences the broadcasts carry. `scripts/measure-coalescing-severity.py`, 12 flushes per
row:

| batch | DEPLOYED step | recoveries | REPO step | recoveries |
|---|---|---|---|---|
| 1 | 1 | 0/11 | 1 | 0/11 |
| 2 | 2 | **11/11** | 1 | 0/11 |
| 3 | 3 | **11/11** | 1 | 0/11 |
| 4 | 4 | **11/11** | 1 | 0/11 |
| 8 | 8 | **11/11** | 1 | 0/11 |
| 16 | 16 | **11/11** | 1 | 0/11 |

**THE DEPLOYED STEP EQUALS THE BATCH SIZE, so from a batch of TWO onward every frame after the
first is a gap.** There is no gentle region: a console goes from zero recoveries to recovering
on EVERY frame the moment any two posts share one flush window. The repo's queue advances by one
at every batch size and never recovers, which is the paired half of the same run rather than a
second run described alongside.

**SO THE TWO MEASUREMENTS COMPOSE INTO THE ACTUAL STATEMENT, and a third does not exist.**
Severity: total, immediately, at the first coalesced flush. Exposure: zero wire gaps across ~50
minutes and >19,000 frames. DISTANCE TO THE EDGE: **unmeasured** -- the arrival-interval margin
that once filled this sentence is withdrawn, because receiver arrival spacing cannot bound post
spacing. So the fleet is not suffering this today, the consequence if it crosses is total rather
than gradual, and how near it runs is not something anything here has measured. That is still a
better argument for deploying than "there is a defect", and it is also why "sometimes" is a
plausible shape for what was reported -- a cliff crossed occasionally reads as intermittent lag,
which is a consistency and not evidence.

**BATCH SIZE, NOT POST RATE, AND THE REASON IS THIS MACHINE.** Pacing posts at sub-millisecond
intervals would measure the TIMER: Windows has a ~15ms floor, which this plan's own neighbours
were caught by once already (a test that waited 80ms for ticks needing 90). Asking for 0.5ms and
getting 15 measures nothing about the queue. Batch size is what the flush logic keys on, and the
mapping is stated rather than smuggled: a batch of k means k posts landed inside one flush
window.

**BOTH CONTROLS ARE IN THE RUN.** The batch-of-one row is the positive control that the harness
reads the right field -- if a single post did not advance the sequence by exactly one, every
other row would be meaningless, and the script refuses rather than printing them. It is also the
control that the recovery counter can report ZERO, while the batch-of-two row shows it can report
non-zero, both in the same run. And the two modules are visibly distinct in the output rather
than assumed: one steps by the batch size and the other by one.

**WHAT IT IS NOT: a rate.** It says what happens PER COALESCED FLUSH, never how often a flush
coalesces. `measure-live-frame-gaps.mjs` is the instrument for that and has measured zero on this
fleet. Severity and exposure are different questions and neither substitutes for the other.

cheapest lever left on the "fast" half of the goal.

**WHAT THAT MEASUREMENT DOES NOT SAY is which branch it timed.** This terminal is attached and
producing, so it very likely HAS a live screen and these are live-branch costs through a real
HTTP round trip to a container -- against 6.6ms for the same branch in-process. The uncached
property holds for whichever branch ran, because a cache would have shown itself on either.
Naming the branch would need the geometry discriminator this section already refuses to use on a
console the operator may be watching.

the replay renders FROM; the snapshot is what the response CARRIES. The fixture's own snapshot
is **3,269 characters** -- inside the real range, not an order of magnitude from it -- so the
comparison established nothing.

case, and the 51ms replay figure is correspondingly more relevant rather than less. That is the
opposite of what this paragraph claimed, and the error was mine: I compared a rendered screen

**AND 64KB IS NOT THE RESYNC WORST CASE**, which is what the row above said until review checked it.

## WHAT A RECOVERY REPAINT COSTS IN THE BROWSER, 2026-09-09

**THE FIGURE THIS BLOCK NEVER PRODUCED FOR A PATH IT CHANGED.** `5d6fbabe` fixed a sequence
counting POSTS where its only reader counts FRAMES, and the consequence was written down as "a
drop costs a full recovery: an HTTP refetch, a `term.reset()`, and a whole-screen repaint". That
sentence sat in this plan for a day with no number on any of its three parts' browser half. A
recovery is not a write: both existing phases of the paint probe APPEND to a live screen, so
neither had ever timed a reset. (What that defect explains is a MECHANISM; whether it is what
the operator saw is the attribution, and that is NOT ESTABLISHED -- see the table below.)

**MEASURED, 132x40, 20 recoveries per arm, timed from the `reset()` call** -- because the reset
is part of what a recovery pays, and timing the write alone would report a cost the console
never incurs:

| arm | offered B | parse p50 | repaint p50 | repaint minus parse |
|---|---|---|---|---|
| webgl 1 KB | 1,055 | 0.40 ms | 7.50 ms | 7.10 ms |
| dom 1 KB | 1,053 | 0.30 | 7.65 | 7.35 |
| webgl 16 KB | 16,431 | 0.40 | 7.50 | 7.10 |
| dom 16 KB | 16,429 | 0.40 | 7.50 | 7.10 |
| webgl 64 KB | 65,631 | 0.95 | 7.55 | 6.60 |
| dom 64 KB | 65,629 | 0.75 | 7.50 | 6.75 |

**A RECOVERY REPAINT IS ABOUT ONE FRAME, AND THE RESET'S OWN COST IS NOT MEASURED HERE.** Every
arm lands at 6.7 to 7.6ms, close to what the PACED phase reports for an ordinary full-screen
paint (7.6-7.8ms), and the payload size does not move it -- the same renderer-bound behaviour
the paced phase established.

**"THE RESET IS FREE" WAS A CLAIM THIS INSTRUMENT CANNOT MAKE, and it stood here until review
said so.** Both published spans START at the reset, so their difference removes the reset rather
than isolating it; and a small contrast between two medians is not a zero cost. Nothing in this
probe measures what `term.reset()` costs on its own, and no version of it did.

**WHAT THE OTHER HALF OF A RECOVERY COSTS IS NOT KNOWN IN THE SAME UNITS**, and this paragraph
claimed otherwise. It said the loop's cost "was not the repaint" because the refetch moved
**147,250 bytes** per resync before `43857ad7` cut it to a 6,442-byte snapshot -- but BYTES ARE
NOT AN ELAPSED-TIME DECOMPOSITION. A payload size and a paint duration cannot be compared, and
no measurement here puts the refetch in milliseconds on the path a browser takes.

What IS established: a recovery's repaint is about one frame at this geometry, and the refetch
shrank by a factor of twenty-three in bytes. Which of the two dominates the recovery's wall
clock is an open question, and it is the one to answer before anybody proposes optimising
either.

**THE FIRST VERSION OF THIS PHASE'S CONTROL COULD NOT FIRE**, and that is the fourth instrument
failure this block has recorded. It asked whether the SUSTAINED phase's marker survived the
reset -- and both markers are written at `ESC[40;1H`, so the repaint overwrites it either way.
Removing `term.reset()` from the phase entirely produced ZERO refusals. The control now keys on
a sentinel deliberately pushed into SCROLLBACK, which an append leaves in place and a reset
clears: with the reset removed it refuses all six arms and publishes nothing, and with the reset
restored every figure above publishes.

## THE LABEL ON THESE NUMBERS WAS WRONG, AND REVIEW CAUGHT IT — CORRECTED 2026-09-08

**I REPORTED THEM AS "PTY-TO-DELIVERY". THEY ARE NOT.** The collector timestamps its OWN receipt of
an aify-env SSE frame; it never reads the moment the PTY emitted anything. A clock it does not read
cannot appear in the noun. This is the second correction to this section and both were the same
mistake in different clothes: a number attached to a noun the instrument could not see.

**WHAT THE DIFFERENCE HONESTLY IS.** Both timestamps are observations made in one process:

| clock | what it actually records |
|---|---|
| A | this collector's receipt of an `aify-env /processes/:id/output` SSE `data` frame |
| B | this collector's receipt of an `aify-comms WS terminal_output` frame |

B minus A is the **EXTRA delay on the aify-comms WebSocket path, relative to reading aify-env's own
stream from the same process at the same moment**. The two paths share their origin -- aify-env holds
the PTY and feeds both -- so whatever happens upstream of that fork cancels, and what remains is the
service leg: ingest, store, push to a subscriber. That is a real and useful quantity. It is not the
age of a byte, and it bounds neither the PTY read nor the browser's paint.

**AND THE COUNTS ARE UTF-16 CODE UNITS, not bytes.** Both streams are decoded to strings before they
are compared. For ASCII the two agree and for anything else they do not, which is why the figures
below now say "units".

**THE COMPLAINT HAS A CANDIDATE MECHANISM NOW, AND IT IS IN THE BROWSER.**

The two server legs were measured and are fast. What had never been examined is the browser's own
RECOVERY path, and reading it produced a defect that was then reproduced against the real modules.

**THE GAP RECOVERY COULD LOOP.** `realtime-socket.mjs`:

```js
if (seq > entry.lastSeq + 1) { resyncActiveConsole().catch(() => {}); return; }
if (Number.isFinite(seq)) entry.lastSeq = seq;      // only on the PAINTING path
```

`lastSeq` advances only when a frame paints. So for the whole of an in-flight resync -- one HTTP
round trip -- every arriving frame still looks like a gap and is dropped. That much is survivable:
the snapshot carries what the server had.

**WHAT IS NOT SURVIVABLE IS WHAT COMES NEXT.** The snapshot's `outputSeq` is the sequence the buffer
had when the SERVER answered, while frames past it arrived during the fetch and were discarded. So
the very next live frame gaps AGAIN -- fetch, drop, gap, fetch -- and on a continuously producing
agent the console recovers in a circle, painting only snapshots and showing nothing in between.

**AND THE NEGATIVE CONTROL IS WHY THE OPERATOR'S WORD WAS "SOMETIMES".** When the snapshot is
already current -- a quiet terminal -- one pass ends it and the next frame paints normally. The loop
needs a busy terminal AND an initial gap. That is exactly the shape a bounded live observation misses.

Fixed in `815ea767`: frames are HELD during a recovery and replayed after the snapshot, in order,
skipping whatever the snapshot already covers. Bounded at 512, past which the console resumes from
the snapshot alone -- which is what it did before, so the fallback is never worse.

**PASSES IN TESTS, NOT PROVEN IN A BROWSER, and the distinction is the point.**
`the-console-does-not-stall-while-it-resyncs.test.mjs` drives the REAL socket and the REAL resync
with a stubbed fetch and a fake xterm. Nothing in it observes a browser painting. What it establishes
is that the bookkeeping PERMITTED the loop; whether the operator's lag WAS this loop needs a console
open on their screen, which is an action and therefore theirs.

**ONE NEARBY PATH WAS SUSPECTED AND REFUTED**, recorded because a refuted suspicion is worth as much
as a confirmed one. A status-only broadcast carries `"output": ""`, and the browser skips its whole
seq block when `output` is falsy -- which looked like the same bookkeeping hole. It is not: that
broadcast falls back to the row's CURRENT `output_seq` and does not increment it, so the next real
frame is still `lastSeq + 1`. `terminal_write_queue.py` already guards the adjacent case, from an
external review's Round 9, and its comment names this failure shape exactly.

## AND THEN THE ROOT WAS FOUND, 2026-09-08 — THE SEQUENCE COUNTED POSTS

The loop above is the AMPLIFIER. Asking what CAUSED the gaps rather than how the browser recovers
from them found the trigger, one tier down, on the server.

**`realtime-socket.mjs` reads the sequence as a count of FRAMES.** `seq > lastSeq + 1` means one was
dropped, and a drop costs a full recovery. **`terminal_write_queue.py` was counting POSTS**: `enqueue`
bumped it once per POST from the host, and the flush broadcast ONCE carrying the final value.

So a flush that coalesced three posts advanced the number by three and emitted one frame — a gap that
nothing dropped. **MEASURED against the real queue before the change: two flushes of two posts each
carried 2 then 4.**

**AND COALESCING IS WHAT HAPPENS WHEN THE AGENT IS BUSY**, which is when somebody is watching. That
is the mechanism behind *"our browser terminal kind of lags sometimes"*, and it explains the
"sometimes" without needing the loop at all: a quiet terminal posts one chunk per flush and never
gaps.

| | fixed by | what it was |
|---|---|---|
| trigger | `5d6fbabe` | every coalesced flush faked a gap |
| amplifier | `815ea767` | the recovery could loop, dropping everything that arrived during it |

Both were real and neither alone explains the behaviour: without the first the console recovers
constantly, without the second each recovery could fail to settle.

**TWO ENDS, ONE FIELD, DIFFERENT NOUNS** — the shape this project has been caught by three times, and
the reason its own rule is to prove BOTH ends of a field. The queue's own comment promised "ONE
ordered, gap-free terminal_output broadcast per flush", and that was true of the BROADCASTS. It was
never true of the NUMBERS they carry, and nothing compared the two readings.

**TWO EXISTING TESTS REQUIRED THE OLD BEHAVIOUR.** Both pinned a strictly-increasing-per-POST number,
and that property has NO CONSUMER: the value is returned to aify-env, which never reads it — zero
matches for `outputSeq` across its tree, and its only mentions of `output_seq` are comments about the
ARRIVAL ORDER the service assigns, which is unchanged. Retargeting them makes one field mean one
thing everywhere, which is the defect being fixed rather than a concession to it.

**SO THE ATTRIBUTION STANDS AT: NOTHING.** What exists is a reproduced server-side DEFECT with a
browser-side amplifier, both fixed, and neither confirmed against the operator's own screen.
Calling that a root CAUSE names a relationship to their report that nothing has established. That last step needs a console
open and a rebuilt container, which are actions and therefore theirs. PROVEN: the server now emits
consecutive numbers, and the browser's rule is satisfied by them. NOT PROVEN: that this was the lag
they saw.

## THE OTHER HALF OF "FAST" — THE FLUSH THE FULL BATCH ASKS FOR, ASKED ONCE PER POST

The seq fix answers "why does it recover so often". It does not answer "what does the transport cost
when an agent is loud", so that got its own measurement. THREE READINGS WERE NEEDED AND THE FIRST TWO
WERE WRONG, which is recorded here because the corrections are the evidence:

1. A "post every 1ms" arm reported 66 posts in a second. `asyncio.sleep(0.001)` waits a ~15.6ms
   Windows timer tick, so the busy arm was never busy. **The posts count is what exposed it** — the
   interval it was supposed to measure looked perfectly reasonable.
2. A genuinely busy arm then emitted a frame every 0.14ms against a documented 24ms bound. The
   explanation offered was asyncio's clock-resolution floor. **Measurement disproved it**:
   `loop._clock_resolution` is 1e-07 here and `call_later(4ms)` genuinely waits.
3. Counting the schedulers instead of reasoning about them found it in one run.

**NEITHER TIMER WAS FLUSHING.** Once a batch crosses `max_batch_chars`, `enqueue` calls
`_schedule_flush_locked`, which CANNOT flush inline — it holds `self._lock`, which `flush_terminal`
also takes — so it defers by a millisecond. Every post arriving inside that millisecond still saw a
batch over the cap and scheduled ANOTHER flush task. All but the first found the state already gone.

MEASURED against the real queue, flush tasks created per second of output:

| producer rate | flush tasks before | after | biggest frame (cap 16,384) |
|---|---|---|---|
| 100 KB/s | 65 | 65 | 3,456 -> 1,664 |
| 1 MB/s | 251 | 89 | 18,368 -> 17,536 |
| 8 MB/s | 56,465 | 284 | 31,680 -> 40,576 |

**THE 100 KB/s ROW IS THE CONTROL AND IT DOES NOT MOVE**: below the cap the timers do all the work
and nothing was ever wasted, so a fix that changed that row would be changing the wrong thing.

**WHY 56,465 TASKS A SECOND IS A REAL COST AND NOT A TIDINESS POINT.** This service is single-worker
by design — CLAUDE.md states it, `_LIVE_STATE_CACHE` depends on it — so those tasks are created on
the ONE event loop that also serves every dashboard poll, status read and message send. 8 MB/s is
what a verbose build log reaches, and the contention lands hardest exactly when an agent is busy,
which is when somebody is watching. That is the same "sometimes" the seq defect had.

**THE FRAMES GOT BIGGER AND FEWER.** At 8 MB/s the flush rate is 255 a second, a MEAN cadence of
3.9ms, and one 40 KB frame is what batching is for. The overshoot past the cap is inherent to the
deferred flush and is NOT fixed here: posts keep joining during the millisecond, and only an inline
flush would stop that, which the lock forbids. Arming once is the half that was actually a defect.

**I CLAIMED THAT WAS "NOT A LATENCY REGRESSION, IT IS INSIDE THE 24ms CONTRACT" AND THAT DOES NOT
FOLLOW.** Review (comms-senior-dev, on this commit alone) put it exactly right and I had not seen it:
a MEAN cadence is neither the maximum interval nor the age of the oldest held output, and even a
demonstrated 24ms maximum would not settle it, because the max timer only SCHEDULES a flush — the
write lock, the database write and the event loop all come after it. Holding the write lock for 60ms
produced ~69.90ms at the parent commit and ~74.31ms at this one, which demonstrates the LIMIT of the
inference rather than a regression between the two.

**SO THE CLAIM IS NARROWED TO WHAT WAS MEASURED**: scheduled flush tasks fell 56,465 → 284 at 8 MB/s
(99.5%, ~198.8x) and 251 → 89 at 1 MB/s (64.5%), the biggest frame grew 28.1%, and the mean cadence
is 3.9ms. **PER-OUTPUT LATENCY IS UNVERIFIED IN BOTH DIRECTIONS** — neither improved nor regressed,
because it was never measured. Settling it needs enqueue-to-commit and enqueue-to-broadcast latency
with a tail and a maximum, plus accounting for output still unflushed, under matched workloads.

**MUTATION-PROVEN**, three mutants, none survived: arming on every post (the pre-fix behaviour), a
flag set but never read, and a flag hung on the QUEUE instead of the batch. The third is the one
worth having — a permanent flag would leave every batch after the first waiting on a timer, and
nothing would have failed. The test asserts a SECOND batch arms too, for that reason.

**PROVEN**: the task count, at three rates, against the real queue with real timers and real
scheduling. **PASSES IN TESTS**: the arm-once behaviour. **NOT MEASURED**: any effect on the
operator's screen — this is server-side loop contention, and attributing a visible stall to it would
need the same rebuilt container and open console the seq fix is waiting on.

## AND THE RENDERER HALF OF "FAST", MEASURED THE SAME WAY — aify-env, 2026-09-08

The operator's goal names two things and the transport work above only answered one. So the same
question was put to the renderer: what does a frame cost, and how often does the operator get one.

**THE PANE UPDATES AT 0.5 FRAMES A SECOND.** `dashboard.mjs` redraws on a `setInterval` of
`AIFY_TUI_REFRESH_MS || 2000` and on keypresses. Every `draw()` call site is one of those two;
arriving terminal output notifies nothing, and the follower is constructed with no callback to notify
with. The bytes ARE streaming in — `output-follower.mjs` reads `response.body` with no polling — so
nothing is lost. Only the display is stale.

**AND THE OBVIOUS LEVER WAS MEASURABLY WRONG.** Lowering `AIFY_TUI_REFRESH_MS` speeds up the WHOLE
frame, and a frame cost 21.4ms at 40 processes — 21% of a core at 100ms. That is the "performance
hog" the operator ruled out by name, so the cadence could not be touched until the frame was cheap.

**THREE READINGS, AND THE FIRST TWO INSTRUMENTS WERE BROKEN.** Recorded because the corrections are
the evidence:

1. A `.pathname` on a `file:` URL gives `/C:/...` on Windows, so the registry read failed into an
