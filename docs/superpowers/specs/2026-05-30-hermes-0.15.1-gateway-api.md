# hermes 0.15.1 tui_gateway session API — reference + native forge/bind decision

Status: RECON / spec. Drives the next implementation phase (retargeting
`mcp/stdio/controllers/hermes-resident-controller.js`). Read-only study of the
installed 0.15.1 gateway; no gateway code was modified.

Source studied (hermes 0.15.1, read-only):

- `…/hermes-agent/tui_gateway/server.py` — RPC method registry + handlers + event routing
- `…/hermes-agent/tui_gateway/transport.py` — `Transport` protocol, `bind_transport`, `WSTransport`/`StdioTransport`/`TeeTransport`
- `…/hermes-agent/tui_gateway/ws.py` — WebSocket entrypoint (`handle_ws`), per-connection transport
- `…/hermes-agent/ui-tui/src/app/useSessionLifecycle.ts` — canonical TUI client sequence
- `…/hermes-agent/ui-tui/src/app/createGatewayEventHandler.ts` — forge path + client-side event demux

---

## TL;DR (for the next phase)

- **DECISION: Option A.** Retarget aify's controller to the **native** gateway
  API and **delete** the `aify.session.bind_transport` patch entirely. The
  installer's `patch_hermes_gateway_visible_bind` should be removed, not re-ported.
- **Single-client vs multi-client:** the gateway is **multi-client at the
  transport layer but per-session-single-owner.** Each WS connection has its own
  `WSTransport`; a session permanently belongs to whichever transport was bound
  when it was *created/resumed*. `session.activate` does **not** re-own events —
  it is a pure client-side redraw. Therefore aify **cannot** steal events for the
  operator's TUI-created session, but it **can** create/own its **own** session
  on its **own** WS and receive that session's events natively, concurrently with
  the operator's TUI, with **no displacement** of the TUI connection.
- **Method discovery:** **none exists.** No `rpc.discover` / `system.listMethods`
  / methods registry RPC. Unknown methods return JSON-RPC `-32601
  "unknown method: <name>"`. Capability detection must be a probe or version string.

## Step 1 — Method reference

All handlers are registered into a module-level dict `_methods` via the
`@method("name")` decorator (`server.py:438-443`, registry declared `:119`).
`handle_request` looks up `_methods.get(method)` and returns `-32601 "unknown
method: <method>"` when absent (`server.py:471-473`). `_ok` / `_err` envelopes:
`{"jsonrpc":"2.0","id":rid,"result":{…}}` / `{… ,"error":{"code","message"}}`
(`server.py:430-435`).

### `session.create` — server.py:2294
- params: `{ "cols": int = 80 }` (only key read; `:2298`).
- effect: mints a fresh in-memory session `sid = uuid4().hex[:8]` and
  `session_key = _new_session_key()`. **Stores `current_transport() or
  _stdio_transport` as the session's permanent event transport (`:2325`).**
  Agent build is deferred ~50ms (`:2337`), so the response returns before tools
  hydrate (`info.lazy = true`).
- result:
  ```json
  { "session_id": "<8hex>",
    "info": { "model": "...", "tools": {}, "skills": {}, "cwd": "...",
              "lazy": true, "profile_name": "..." } }
  ```

### `session.resume` — server.py:2447
- params: `{ "session_id": "<id-or-title>" (required), "cols": int = 80 }`.
  Resolves by id then by title (`:2455-2461`); `4006` if missing, `4007` if not found.
- effect: mints a NEW live `sid` (`:2462`) wrapping the stored conversation;
  rebuilds the agent and calls `_init_session(...)`. (`_init_session` also stores
  `current_transport() or _stdio_transport`, `:2083`.)
- result:
  ```json
  { "session_id": "<new 8hex>", "resumed": "<target id>",
    "message_count": int, "messages": [...], "info": { ... } }
  ```

### `session.active_list` — server.py:2568
- params: `{ "current_session_id": str = "" }` (used only to mark `current`).
- effect: read-only enumeration of in-memory live sessions in THIS gateway
  process (not the DB history browser that `session.list` is).
- result: `{ "sessions": [ row, ... ] }` where each row (`_session_live_item`,
  `:2530`) =
  ```json
  { "current": bool, "id": "<sid>", "last_active": float, "message_count": int,
    "model": str, "preview": str, "session_key": str, "started_at": float,
    "status": "idle|working|waiting|starting" }
  ```

### `session.activate` — server.py:2589
- params: `{ "session_id": "<sid>" (required) }`. `_sess_nowait` → `4xxx` if not
  a live session.
- **effect (CRUX): pure read. Docstring `:2591-2595`: "Attach the frontend to
  an already-live TUI session. This intentionally does not close the previously
  focused session; it merely returns enough state for Ink to redraw around
  another live session id."** It does NOT touch `session["transport"]`, does NOT
  bind the caller's transport, does NOT change event routing. It only bumps
  `last_active` and returns a state snapshot for the client to repaint.
- result:
  ```json
  { "info": {...}, "message_count": int, "messages": [...], "running": bool,
    "session_id": "<sid>", "session_key": str, "started_at": float,
    "status": "idle|working|waiting|starting", "inflight": {...}? }
  ```

### `session.status` — server.py:2745
- params: `{ "session_id": "<sid>" (required) }`.
- result: `{ "output": "<multi-line human-readable status text>" }` (Session ID,
  Path, Title, Model/provider, Created, Last Activity, Tokens, Agent Running).
  Note: text blob, not structured fields.

### `prompt.submit` — server.py:3338
- params: `{ "session_id": "<sid>" (required), "text": str }`.
- effect: rejects with `4009 "session busy"` if `running` (`:3345`); else sets
  `running=true`, starts an inflight turn, ensures the agent is built, and runs
  the turn on a daemon thread. Agent output streams as `event` frames
  (`message.*`, `status.update`, etc.) routed to the **session's stored
  transport** (see Step 2).
- result (immediate ack): `{ "status": "streaming" }`.

### `session.steer` — server.py:3301
- params: `{ "session_id": "<sid>" (required), "text": str (required) }`.
- effect: injects `text` into the next tool result of an in-flight turn without
  interrupting (`AIAgent.steer()`). `4002` if no text, `4010` if agent lacks
  steer.
- result: `{ "status": "queued" | "rejected", "text": str }`.

### `bind_transport(t)` — transport.py:90 (imported server.py:24, called server.py:490)
- `transport.py:77-97`: the active transport is a **`contextvars.ContextVar`**
  (`_current_transport`). `bind_transport(t)` = `_current_transport.set(t)`
  returning a reset token; `current_transport()` reads it; `reset_transport(tok)`
  restores it.
- `server.py:477-515` (`dispatch(req, transport)`): for every inbound RPC,
  `t = transport or _stdio_transport; token = bind_transport(t)` (`:489-490`),
  runs the handler (copying the context onto the pool for long handlers so the
  worker sees the same bound transport, `:500-511`), then `reset_transport` in
  `finally`. So **the bound transport is per-request and equals the WS connection
  that sent the request** (`ws.py:163` passes the connection's `WSTransport`).
- It is **NOT** a per-session subscription API. A WS client cannot call
  `bind_transport` to "scope itself to session X's events." Transport binding is
  an internal request-scoped mechanism. Event delivery to a session is decided by
  `write_json` (next section), keyed on the transport captured **at create/resume
  time**, not on who is currently bound.

## Step 2 — Canonical bind sequence + the single-client answer

### How events actually route (`write_json`, server.py:365-383)
```python
def write_json(obj):
    if obj.get("method") == "event":
        sid = ((obj.get("params") or {}).get("session_id")) or ""
        if sid and (t := (_sessions.get(sid) or {}).get("transport")) is not None:
            return t.write(obj)          # ← event → the session's STORED transport
    return (current_transport() or _stdio_transport).write(obj)  # responses → request transport
```
`_emit(event, sid, payload)` (`:386-390`) always tags events with `session_id`,
so **every async agent event for a session is written to the transport that was
stored on that session when it was created/resumed** — independent of which
connection is "current" or which connection called `session.activate`.

### Per-connection transports (`ws.py`)
`handle_ws` (`ws.py:116-178`) accepts each WS, builds a **per-connection**
`WSTransport(ws, loop)` (`:120`), and dispatches every request with
`server.dispatch(req, transport)` (`:163`). On disconnect it detaches itself from
any sessions it owned, reverting them to stdio (`:171-173`). Multiple WS clients
therefore coexist, each with an independent transport.

### The TUI proves multiplex-by-ownership + client-side demux
- The single Ink TUI creates ALL its sessions on its ONE WS
  (`useSessionLifecycle.ts:170` `session.create`; resume path likewise), so every
  session's stored transport is the TUI's connection.
- `session.activate` (`useSessionLifecycle.ts:251-279`) is purely client UI:
  `resetSession()` + repaint from the returned snapshot + `writeActiveSessionFile`.
  No transport change server-side.
- Inbound events are demultiplexed **by the client**:
  `createGatewayEventHandler.ts:284`
  ```ts
  if (ev.session_id && sid && ev.session_id !== sid && !ev.type.startsWith('gateway.')) return
  ```
  i.e. the gateway *delivers all of a connection's owned sessions' events to that
  connection*, and the client drops the ones not currently focused.

### Definitive answer to the crux
- **A second WS client does NOT displace or close the TUI's connection.**
  `session.activate` "intentionally does not close the previously focused
  session" (`server.py:2593`) and never reassigns `session["transport"]`. There
  is no server path where activating, or a new WS connecting, tears down another
  WS. (`ws.py` only detaches on that same socket's own disconnect.)
- **But a second WS client also CANNOT subscribe to the events of a session that
  another connection created.** Events hard-route to the session's *stored*
  transport (`server.py:380`). `session.activate {session_id}` from aify's WS
  returns the snapshot but the live stream keeps flowing to the TUI's transport,
  never to aify's. So "activate then events flow to me" is FALSE for a
  foreign-owned session.

**=> The only way for aify's WS to receive a session's live events on 0.15.1 is
to be the connection that CREATED (or resumed) that session.** aify must own its
own session, not piggy-back the operator's TUI session.

### Canonical sequence for aify on 0.15.1
1. Open aify's own WS to `/api/ws` (separate from the operator's TUI). Receive
   `gateway.ready`.
2. `session.create { cols }` (or `session.resume { session_id }`) on THAT socket.
   → the session's transport is now aify's WS; all its events route to aify
   natively. Capture the returned `session_id`.
3. `prompt.submit { session_id, text }` to dispatch; if `4009 busy`, fall back to
   `session.steer { session_id, text }`.
4. Consume streamed `event` frames on aify's WS (filter by `session_id` exactly
   like the TUI does).
5. Optional: the operator's TUI can `session.active_list` → see aify's session
   and `session.activate {session_id}` to *view* its transcript snapshot
   (read-only redraw); the live stream still lands on aify, but the TUI can poll
   `session.activate`/`session.history` to refresh. (Operator visibility of an
   aify-owned session is a follow-up UX question, not a transport blocker.)

`bind_transport` plays **no role** in this sequence from the client side — it is
internal request plumbing, automatically handled by `dispatch(req, transport)`.

## Step 3 — Method discovery

**No runtime method-enumeration RPC exists.** The registry `_methods`
(`server.py:119`) is populated by `@method` but is never exposed; there is no
`rpc.discover`, `system.listMethods`, `system.methods`, `methods.list`, or
`commands.catalog`-style introspection of RPC methods. Unknown methods return:
```json
{ "jsonrpc":"2.0", "id":rid, "error": { "code": -32601, "message": "unknown method: <name>" } }
```
(`server.py:471-473`).

**Capability detection plan for aify:** probe. e.g. issue `session.active_list`
(harmless, read-only) or `session.activate` with a sentinel id and inspect the
error: `-32601` (or a message containing `"unknown method"`) ⇒ pre-0.15.1 gateway
(use legacy path); a normal result or a domain error like `4007 "session not
found"` ⇒ native API present. A pinned hermes version string can be a secondary
signal but the `-32601` probe is authoritative. The legacy custom method
`aify.session.bind_transport` likewise will return `-32601` on a stock 0.15.1
gateway, which doubles as a "patch absent" signal.

## Step 4 — THE DECISION

**Option A — retarget to the native API; drop the patch entirely. CHOSEN.**

### Why the evidence forces A
1. **The patch's premise is dead.** The old patch + controller try to bind aify's
   bridge transport onto the operator's *TUI-created* visible session
   (`hermes-resident-controller.js:6-9`). On 0.15.1 a session's event transport is
   immutably the connection that created it (`server.py:380`, `:2325`, `:2083`);
   `session.activate` explicitly refuses to retarget it (`:2593`). Even a perfect
   re-port of `aify.session.bind_transport` would be fighting `write_json`'s
   session→stored-transport routing — to redirect a TUI-owned session's events to
   aify's socket you would have to mutate `session["transport"]`, which **steals**
   the stream from the operator's TUI (the very displacement we must avoid).
   So the patch can't deliver a *non-displacing* per-session subscription on the
   operator's session. Option B fails its own bar.
2. **Native methods already give aify a clean, non-displacing event stream** — by
   having aify own its own session: `session.create`/`resume` on aify's WS →
   events route to aify automatically; `prompt.submit` to dispatch; `session.steer`
   for mid-turn; `session.active_list`/`session.activate` for visibility. No
   patch, no `TeeTransport` injection, no text-anchor fragility across hermes
   upgrades.
3. **The patch is already silently no-opping on 0.15.1** (text anchors moved), so
   nothing today depends on it working. Removing
   `patch_hermes_gateway_visible_bind` from `install.sh` deletes a maintenance
   liability rather than removing live function.

### Consequence for the next phase
- Delete `patch_hermes_gateway_visible_bind` from `install.sh` (and any callers).
- Rewrite `hermes-resident-controller.js` to: open its own WS, `session.create`
  (or resume a designated session) to OWN it, then `prompt.submit` →
  `session.steer` on busy, consuming events filtered by `session_id`. Remove the
  `aify.session.bind_transport` call.
- Capability gate via the `-32601` probe (Step 3) so the controller can detect a
  too-old gateway and fail with a clear message instead of silently mis-binding.
- Open follow-up: decide whether/how the operator's TUI should surface
  aify-owned sessions (via `session.active_list` + periodic `session.activate`
  snapshot), since aify-owned sessions won't live-stream into the TUI. This is a
  visibility/UX item, not a dispatch blocker.

### Caveat to carry forward
Native dispatch makes aify-managed hermes sessions **aify-owned**, not
**operator-TUI-owned**. If the product requirement is specifically "the message
must appear in the operator's existing `hermes chat --tui` window in real time,"
that is architecturally unavailable on 0.15.1 without displacing the TUI's
transport — and should be treated as a separate decision rather than a reason to
re-port the patch.
