# aify-comms v0.2 plan

Backlog opened 2026-07-26 from the deep review of the v0.1 release series
(`6b3985c..7086006`, 125 files / ~4.2k insertions). Everything here was found by tracing
that series; anything **service-breaking was fixed in v0.1 instead** and is listed at the
bottom for context.

Ground rules carried from v0.1:
- Single-worker uvicorn is a hard constraint (`_LIVE_STATE_CACHE`, `_LIVE_SCREENS` are
  process-global). Nothing in here may assume otherwise.
- `bash scripts/stamp.sh` **before** `docker compose up -d --build` — the stamp is COPY'd in.
- Bridge changes need `install.sh` **and** a wrapper relaunch. `aify-doctor` proves it.
- Skill mirrors `.claude/skills/` and `.agents/skills/` stay byte-identical.

## A. Operator decisions (behaviour changed in v0.1 — confirm or revert)

### A1. Compaction dialog now spends usage limits by design
`mcp/stdio/claude-console-prompts.js` — the compaction-recommendation dialog used to
auto-confirm the highlighted **"Resume from summary (recommended)"**. It now navigates to
**"Resume full session as-is"** (`compaction-resume-full-session`, `[DOWN, ENTER]`).

The code it replaced argued the opposite explicitly: *"the one option that burns the usage
limits the dialog is warning about."* Preserving agent context is a defensible reason to
flip it, but across a fleet this deliberately consumes Claude Max quota faster, and this repo
already tracks per-source quota (see `usage-quota-sources-2026-06-26`).

Second-order: a dialog rendering **only** option 1 now returns `null` and stalls, where it
previously auto-confirmed. That re-opens the 2026-07-02 incident class ("managed agents
stalled at /compact while managers waited"). The real PTY fixture does render option 2, and
the matcher re-runs on later frames, so a progressive repaint recovers — but a genuinely
one-option render hangs.

- [ ] Decide: keep context-preserving, or revert to summary, or make it a setting.
- [ ] If kept: add a bounded fallback so a one-option dialog confirms rather than stalling
      forever, and surface the choice in the quota/usage screen so the cost is visible.

### A2. Managed codex auto-approves every command and file change
`mcp/stdio/runtimes-rpc.js` → `managedCodexServerRequest` answers
`item/commandExecution/requestApproval` and `item/fileChange/requestApproval` with
`{decision: "acceptForSession"}`, and `item/permissions/requestApproval` by echoing back
whatever `params.permissions` asked for with `scope: "session"`.

For an autonomous managed worker this is *necessary* — there is no operator to answer the
prompt, and without it the run deadlocks. It is also the same posture as
`HERMES_YOLO_MODE=1`. But it is currently implicit and unbounded (session-scoped grant of
arbitrary requested permissions).

CORRECTED 2026-07-26 (review): an earlier draft here claimed the handler was "wired only into
`codex-session.js`, never the resident path — which is correct today". That is FALSE. It is wired
in **three** places: `codex-session.js:202` and `controllers/codex-legacy-controller.js:218` and
`:228`. So the blast radius is wider than stated and the "never the resident path" reassurance was
never verified. Establishing which of those three can serve a resident/operator-owned session is
part of this item, not a settled fact.

- [ ] Make it explicit: a named setting/env with a documented default, so "managed codex is
      YOLO" is a stated property rather than an emergent one.
- [ ] Add a test pinning that the resident/WebSocket codex path does **not** get this handler.
- [ ] Fold into the standing "security fail-open defaults" operator decision from the
      2026-06-28 deep audit rather than deciding it in isolation.

## B. Verification gaps (aify-doctor can still say "fine" when it isn't)

### B1. No Windows coverage for "is the running bridge the installed bridge?"
`bridge-running` and `agent-identity` both `skip` with *"process inspection is Linux-only"*.
The primary dev host is Windows, so on it **nothing** verifies that a live wrapper is
executing post-`install.sh` code — the exact failure this repo has been bitten by repeatedly
(CLAUDE.md: "every deploy path in this repo fails silently").

Better than porting `/proc` scraping: have each bridge report its own build stamp on
`POST /agents/{id}/heartbeat`, store it, and let doctor compare **reported** stamp vs
installed stamp. Platform-independent, and it proves the running code rather than inferring
it from process start time.

- [ ] Bridge sends `bridgeBuild` (the `.aify-version` stamp it loaded at boot) on heartbeat.
- [ ] Server persists it on `bridge_instances` / `environments`.
- [ ] `aify-doctor` adds `bridge-code-current`: names any live bridge whose reported stamp
      != installed stamp, with "relaunch these wrappers" as the fix.
- [ ] Retire the Linux-only `bridge-running` check once this lands.

### B2. Doctor has no self-test
The `env-bridge` false green (fixed in v0.1) survived because no test exercised the check
against a payload of stale rows. `doctor.js` has essentially no unit coverage.

- [ ] Extract the pure predicates (`envIsOnline`, stamp comparison, usage classification)
      and unit-test them against captured `/environments` and `/version` payloads —
      including the all-offline payload that produced the false green.

## C. Correctness / consistency nits (real, low blast radius)

### C1. Live-screen grid is clamped tighter than the PTY
`service/terminal_snapshot.py:_clamp_grid` caps at **500×200**; the resize path clamps at
**2000×1000** (`api_v2.resize_terminal`, `mcp/stdio/terminal-runtime.js`). A console wider
than 500 columns gets a server-rendered snapshot at the wrong width, which is precisely the
"woven rows" garbling the snapshot exists to prevent.

- [ ] Align the two clamps (or clamp the resize down to what the renderer can represent) and
      state the single max in one place.

### C2. `handled_at` gets two timestamp formats
`service/db.py:_reconcile_terminal_controls` writes
`datetime.now(timezone.utc).isoformat().replace("+00:00","Z")` → sub-second precision, while
`api_v2._now()` writes `%Y-%m-%dT%H:%M:%SZ`. Safe **today** because the only comparison is
`datetime(handled_at) < datetime('now', ?)` (format-tolerant), but this repo has already been
bitten six times by lexical timestamp comparison (`bughunt-round2-2026-07-03`). A single
future `handled_at >= ?` would sort `...00.123456Z` before `...00Z`.

- [ ] Use `_now()`-equivalent formatting in `db.py` so every stored timestamp is one shape.
- [ ] Consider a test asserting no column mixes formats.

### C3. `_is_turn_busy_fresh` is production-dead
After v0.1 the delivery gates no longer call it; only `service/tests/` reference it (plus
`_turn_busy_state`, which the reminder loop still uses for its run-id).

- [ ] Either delete `_is_turn_busy_fresh` and fold its one assertion into `_turn_busy_state`
      coverage, or make the reminder loop use it so the shared "busy" definition is real.

### C4. Pre-existing queued runs migrate as non-steerable
`queue_if_busy` / `steer_if_busy` were added with `DEFAULT 0`, so runs queued **before** the
migration read as `steer_if_busy=0` — the claim gate treats them as explicit non-steer and
holds them while the target is mid-turn. Transient — it drains as the backlog clears.

CORRECTED 2026-07-26 (review): an earlier draft claimed this "self-heals within 30 min worst case".
Wrong. The anti-strand ceiling only fires once `turn_updated_at` STOPS advancing, and the bridge
detectors KEEP-FRESH re-stamp turn-start for as long as real work runs — so for a genuinely busy
agent such a run waits for the turn to actually end, which can be hours. 30 minutes bounds only an
ABANDONED flag. That is the correct behaviour (a legacy run must not be injected mid-turn), but the
bound is "until turn-end", not "within 30 min".

- [ ] No code change needed; note it in DECISIONS.md so it is not re-diagnosed as a bug.

## OPEN REVIEWER FINDINGS on `7b1ca31` — v0.1 is REVISE, not deployable

Independent review reproduced these on `ea54c96`. Only the reminder one is fixed (reverted — my
change had made it worse). The other four are UNFIXED and each is verified below, so the next
session starts from evidence rather than re-deriving.

### R1. Retention still destructive-by-default, and the prune has a race — UNFIXED
Two separate problems the reviewer bundled:
* **Default.** `DEFAULT_SETTINGS["session_history_retention_days"]` was set to `0` (opt-in) in this
  session — but any DB that already stored `3` from the earlier commit keeps pruning. A default
  change does not un-set a persisted setting. Needs an explicit migration/one-time reset, or the
  reviewer's reading stays correct in practice.
* **Race.** `_prune_session_history` does `SELECT ids` then `DELETE ... WHERE id IN (ids)` with NO
  re-check. A session that becomes live between the two statements is deleted anyway, and
  `terminal_sessions.session_id` is `ON DELETE CASCADE`, so that takes a LIVE console with it. The
  superseded-spawn reaper solves exactly this with a correlated `EXISTS` re-verify inside the
  UPDATE; this DELETE must do the same.

### R2. Stop worker does not stop non-virtual terminals, and hides the session it just ended — UNFIXED
`/agents/{id}/stop-worker` tears down DB state and the *virtual* RPC terminal; its own docstring
says bridge-side resources (the `claude-aify` wrapper PTY) are left to the bridge's next reconcile.
So the drawer button reports success while the real process keeps running. Worse in combination
with this session's `/sessions` change: the stop moves the session to a terminal status, which the
default list now hides — so the operator loses sight of the thing they just acted on. Fixing the
button without fixing that interaction would be misleading.

### R3. Doctor accepts `degraded` but spawning rejects it; malformed/future `lastSeen` false-greens — UNFIXED
* Consistency: doctor now counts `degraded` as connected, but the spawn path prefers/requires
  `online` (`api_v2.py:15239-15240` ordering, and the env-count at `:21906` keys on `status='online'`).
  Doctor can therefore go green while managed spawns cannot actually run — the same false-green
  class, just relocated. Decide ONE definition of "usable for spawn" and have both read it.
* `envIsOnline` returns `true` when `lastSeen` is unparseable, and a FUTURE `lastSeen` makes
  `Date.now() - seen` negative, so it always passes the staleness bound. Both green a dead bridge.

### R4. Future `turn_updated_at` strands delivery; drawer channel-selection race — UNFIXED
* `_turn_busy_holds_delivery` computes `(now - seen) <= CEILING`. A FUTURE timestamp yields a
  negative age, which always satisfies the bound — so a clock-skewed or bad write strands delivery
  permanently, the exact failure the ceiling was added to prevent. I closed the missing-timestamp
  hole this session and missed the future-timestamp one; same one-line predicate.
* `syncInspectorToSelection` fires after `open()`'s `await loadConversation(...)`, so two rapid
  selections can settle the drawer against the earlier one.

### C6. Finished runs can stay at `status='delivered'` — OPEN, evidence captured 2026-07-26
A run that has both a reply (`result_message_id`) and a `finished_at` can still carry
`status='delivered'` forever. Live counts at the time of writing:

```
require_reply=1  delivered=3   all with a reply AND finished_at (one finished 6s after request)
require_reply=0  delivered=10  of which 6 have no reply attached
```

Harmless to delivery — every consumer gates on `result_message_id`, not on `status`, so these are
correctly skipped by both the reminder loop and the stranded-reply closer. But any UI, analytics
query or agent reading `status` sees outstanding work that will never resolve. Same class as the
three "state that lies" defects fixed in v0.1 (doctor's row count, the Start-gate blocklist, the
Sessions history dump).

**Deliberately NOT fixed in v0.1.** The prerequisite is a question I have not answered: is
`delivered` a legitimate TERMINAL state for some delivery paths, or is every finished run meant to
reach `completed`? That decides whether the fix is "advance the status" or "stop treating delivered
as open", and getting it backwards would corrupt run bookkeeping fleet-wide. Trace before editing.

- [ ] Establish which delivery paths legitimately end at `delivered`.
- [ ] Then either advance finished runs to `completed`, or document `delivered`+`finished_at` as
      terminal and fix the readers instead.

### C7. WITHDRAWN — "reply contracts older than 24h are abandoned"
Recorded because it was asserted to the operator and is wrong; a future reader should not
re-derive it. The claim was that `recent_only=True` (24h) left old contracts unreminded and
leaking. It does not: the three long-lived `delivered` contracts all have replies attached and
`finished_at` set — they were answered within seconds. Nothing leaked, and the reminder window
needs no change. The real defect in that area is C6 above.

### C5. Unhandled server→client RPC now returns an error instead of silence
`runtimes-rpc.js` answers any `{id, method}` frame with `-32601` when no `onRequest` handler
is set. Today the only WebSocket clients are short-lived read-only inspectors
(`runtimes-codex.js` "marker inspector" / "register bridge") that never submit prompts, so
they receive no approval requests — no impact. But if a WS client is ever used for delivery,
codex approvals would be auto-**denied** rather than ignored.

- [ ] When any WS client gains prompt submission, give it an explicit `onRequest`. Add a test
      that a delivery-capable client never falls through to `-32601`.

## D. Product / UX improvements

### D1. Chat: agent↔agent traffic is now behind an identity choice
`chat.js` tightened the DM filter to strict pairwise
(`from===peer && to===viewer || from===viewer && to===peer`) and added an `all` read-only
identity. Watching a whole team's cross-talk now requires explicitly picking `all` — as
`dashboard` you see only your own DMs. This is a better model, but the affordance is one
option in a dropdown.

- [ ] Make `all` discoverable (label it "All traffic (read-only)", or default the dashboard
      identity to it since `dashboard` rarely holds the interesting conversations).

### D2. Fleet-wide "deaf agent" surfacing
The v0.1 strand was invisible: the dashboard showed the agent idle while its queued work
could never be claimed. The ceiling now bounds it, but the *symptom* still has no display.

- [ ] Surface "has queued work but is not claiming" as an attention-strip row, with the
      reason (`turn_busy latched`, `no steer capability`, `bridge offline`).
- [ ] Same for the reverse: a run `delivered` with `requireReply` and no reply past N minutes.

### D3. Reconcile observability
`_run_dispatch_reconcile_once` returns a rich counter dict that nothing displays. When the
fleet misbehaves, those counters are the fastest diagnosis available.

- [ ] Expose the last N reconcile results on an ops/debug panel (or `GET /reconcile/last`).

## E. Engineering hygiene

### E1. `api_v2.py` is ~22k lines
It is the single largest correctness risk left in the repo — every reviewer (human and agent)
reasons worse about it, and the 500-line guidance in CLAUDE.md is violated by ~44x. Splitting
it is a v0.2-scale project, not a drive-by.

- [ ] Carve out by seam, lowest-risk first, one commit per seam with the suite green between:
      terminal/console endpoints → dispatch/claim → status/derive → messages/channels.
- [ ] Keep `_LIVE_STATE_CACHE` ownership in exactly one module and import it, never duplicate.

### E2. Test-suite portability
The installer contract test was red on Windows for the whole v0.1 series (fixed), which means
"the suite is green" was not a claim anyone could make on the primary dev host.

- [ ] Sweep the suite for other host-shaped assumptions (absolute paths handed to `bash`,
      `/tmp`, POSIX-only tools) and add a note that the suite must be green on Windows too.
