# aify-comms v0.2 plan

Backlog opened 2026-07-26 from the deep review of the v0.1 release series
(`6b3985c..7086006`, 125 files / ~4.2k insertions). Everything here was found by tracing
that series; anything **service-breaking was fixed in v0.1 instead** and is listed at the
bottom for context.

Ground rules carried from v0.1:
- Single-worker uvicorn is a hard constraint (`_LIVE_STATE_CACHE`, `_LIVE_SCREENS` are
  process-global). Nothing in here may assume otherwise.
- `bash scripts/stamp.sh` **before** `docker compose up -d --build` — the stamp is COPY'd in.
- Bridge changes need `install.sh` **and** a wrapper relaunch. `aify-doctor` proves it.
- Skill mirrors `.claude/skills/` and `.agents/skills/` stay byte-identical.

## A. Operator decisions (behaviour changed in v0.1 — confirm or revert)

### A1. Compaction dialog — policy DECIDED, stall NOT fixed (attempt reverted)
**Operator decision: context-preserving is the DEFAULT.** "Resume full session as-is" is what the
matcher navigates to whenever the dialog offers it. That works and is tested.

**The stall is still open, and my fix for it was REVERTED as unsafe.** I added a fallback that
pressed Enter whenever "Resume full session" was absent from the tail. A reviewer caught that this
is exactly the hazard THIS FILE already documents: the menu "renders progressively — Resume from
summary paints before Resume full session", and mid-render "it must NOT auto-press Enter and
compact the session away". So on a partial repaint the fallback would select summary and SILENTLY
LOSE the context the operator explicitly chose to preserve — strictly worse than the stall, because
a stall is recoverable and lost context is not.

### A1b. Curing the stall needs the STATEFUL caller — OPEN, and STAYS in v0.2 on purpose
`matchConsolePrompt` is a pure function of one terminal frame and cannot distinguish "still
painting" from "only one option exists". No single-frame heuristic can. The state exists one layer
up: `TerminalProcessManager` already tracks per-terminal `answeredPrompt`, so it can require the
SAME unanswerable compaction dialog across a wall-clock dwell before confirming the highlighted
option.

**Recommended (2026-07-26) to stay out of v0.1, on RISK ASYMMETRY rather than effort.** v0.1 exists
so there is a safe revert point, and this is the one item where the cure's failure mode is worse
than the disease's:
  * the stall is VISIBLE and RECOVERABLE — the operator can type into the console and unstick it;
  * a wrong dwell presses Enter on a progressively-painted menu, selects "Resume from summary", and
    SILENTLY LOSES context the operator explicitly chose to preserve. Unrecoverable, fleet-wide, and
    it is the exact hazard that got the last attempt reverted.

Also note the mechanism is not the obvious one: a counter in `_handleOutput` CANNOT work, because a
stalled dialog emits no further output, so the counter never advances past 1. It needs a wall-clock
timer that re-reads the current tail and re-confirms ownership before acting — new machinery in the
highest-consequence path in the repo.

- [ ] Implement the dwell in terminal-runtime.js, not in the matcher. Wall-clock, not poll-count.
- [ ] Keep the matcher declining; it must stay safe on a single frame.
- [ ] Cheap v0.1-shaped MITIGATION if the stall bites again before the dwell lands: surface it
      instead of curing it. A new pure predicate ("compaction dialog owns the screen AND is
      unanswerable") reported as a status reason injects ZERO keystrokes and turns a silent wedge
      into something the operator can see and fix. Today such an agent reads idle.

### A2. Managed codex auto-approves every command and file change
`mcp/stdio/runtimes-rpc.js` → `managedCodexServerRequest` answers
`item/commandExecution/requestApproval` and `item/fileChange/requestApproval` with
`{decision: "acceptForSession"}`, and `item/permissions/requestApproval` by echoing back
whatever `params.permissions` asked for with `scope: "session"`.

For an autonomous managed worker this is *necessary* — there is no operator to answer the
prompt, and without it the run deadlocks. It is also the same posture as
`HERMES_YOLO_MODE=1`. But it is currently implicit and unbounded (session-scoped grant of
arbitrary requested permissions).

CORRECTED 2026-07-26 (review): an earlier draft here claimed the handler was "wired only into
`codex-session.js`, never the resident path — which is correct today". That is FALSE. It is wired
in **three** places: `codex-session.js:202` and `controllers/codex-legacy-controller.js:218` and
`:228`. So the blast radius is wider than stated and the "never the resident path" reassurance was
never verified. Establishing which of those three can serve a resident/operator-owned session is
part of this item, not a settled fact.

- [ ] Make it explicit: a named setting/env with a documented default, so "managed codex is
      YOLO" is a stated property rather than an emergent one.
- [ ] Add a test pinning that the resident/WebSocket codex path does **not** get this handler.
- [ ] Fold into the standing "security fail-open defaults" operator decision from the
      2026-06-28 deep audit rather than deciding it in isolation.

## B. Verification gaps (aify-doctor can still say "fine" when it isn't)

### B1. No Windows coverage for "is the running bridge the installed bridge?"
`bridge-running` and `agent-identity` both `skip` with *"process inspection is Linux-only"*.
The primary dev host is Windows, so on it **nothing** verifies that a live wrapper is
executing post-`install.sh` code — the exact failure this repo has been bitten by repeatedly
(CLAUDE.md: "every deploy path in this repo fails silently").

Better than porting `/proc` scraping: have each bridge report its own build stamp on
`POST /agents/{id}/heartbeat`, store it, and let doctor compare **reported** stamp vs
installed stamp. Platform-independent, and it proves the running code rather than inferring
it from process start time.

- [ ] Bridge sends `bridgeBuild` (the `.aify-version` stamp it loaded at boot) on heartbeat.
- [ ] Server persists it on `bridge_instances` / `environments`.
- [ ] `aify-doctor` adds `bridge-code-current`: names any live bridge whose reported stamp
      != installed stamp, with "relaunch these wrappers" as the fix.
- [ ] Retire the Linux-only `bridge-running` check once this lands.

### B2. Doctor has no self-test — DONE for the env predicates (v0.1)
The `env-bridge` false green survived because no test exercised the check against a payload of stale
rows, and the reason no test existed was structural: `doctor.js` runs every check at import and ends
in `process.exit()`, so it cannot be imported.

Fixed by moving the pure env predicates to `mcp/stdio/doctor-predicates.js` (behaviour-identical;
doctor.js imports them) and adding `tests/doctor-env-predicates.test.js` — 13 tests covering the
all-offline payload that produced the "2 connected" lie, `degraded`, future/undatable `lastSeen`,
the exact staleness boundary, and naive-timestamp parsing. Verified by running `aify-doctor` against
the live service, not just by the suite.

**That verification earned its keep immediately.** The first cut made the clock injectable as
`envIsOnline(env, now = Date.now())`, but doctor calls `list.filter(envIsOnline)` and
`Array.prototype.filter` passes **(element, index, array)** — so `now` bound to the array index, the
age went hugely negative, the `age >= 0` guard rejected it, and a bridge that had beaten 68 seconds
earlier read as NOT connected. A false RED, introduced by the very change meant to make the
false-green class testable. The clock is now injectable only via `envIsOnlineAt`; `envIsOnline`
stays arity-1 and a test asserts both `envIsOnline.length === 1` and correct behaviour at a non-zero
index. General lesson, worth more than the fix: **widening a predicate's arity is a breaking change
when a caller passes it as a callback.**

- [ ] Still un-extracted and untested: the build-stamp comparison and the usage classification.
      Same treatment, lower stakes — neither has produced a false report.

## C. Correctness / consistency nits (real, low blast radius)

### C1. Terminal grid max — FIXED
`terminal_snapshot.py` now owns ONE ceiling (`TERMINAL_MAX_COLS/ROWS = 500x200`) because the
renderer is the binding constraint (a pyte screen allocates cols*rows cells), and the resize
endpoint imports it instead of carrying its own `2000x1000`. They disagreed, so a console wider
than 500 columns was rendered at the WRONG WIDTH — the woven-rows garbling the server-rendered
snapshot exists to prevent.

### C2. Timestamp format — FIXED
`db.py` now writes `%Y-%m-%dT%H:%M:%SZ` like every other writer, instead of `isoformat()` with
sub-second precision. Was safe only because the single comparison is `datetime(handled_at)`; one
future `handled_at >= ?` would have sorted `...:00.123456Z` before `...:00Z`. This repo has been
bitten six times by exactly that.

### C3. `_is_turn_busy_fresh` is production-dead
After v0.1 the delivery gates no longer call it; only `service/tests/` reference it (plus
`_turn_busy_state`, which the reminder loop still uses for its run-id).

- [ ] Either delete `_is_turn_busy_fresh` and fold its one assertion into `_turn_busy_state`
      coverage, or make the reminder loop use it so the shared "busy" definition is real.

### C4. Pre-existing queued runs migrate as non-steerable
`queue_if_busy` / `steer_if_busy` were added with `DEFAULT 0`, so runs queued **before** the
migration read as `steer_if_busy=0` — the claim gate treats them as explicit non-steer and
holds them while the target is mid-turn. Transient — it drains as the backlog clears.

CORRECTED 2026-07-26 (review): an earlier draft claimed this "self-heals within 30 min worst case".
Wrong. The anti-strand ceiling only fires once `turn_updated_at` STOPS advancing, and the bridge
detectors KEEP-FRESH re-stamp turn-start for as long as real work runs — so for a genuinely busy
agent such a run waits for the turn to actually end, which can be hours. 30 minutes bounds only an
ABANDONED flag. That is the correct behaviour (a legacy run must not be injected mid-turn), but the
bound is "until turn-end", not "within 30 min".

- [ ] No code change needed; note it in DECISIONS.md so it is not re-diagnosed as a bug.

## OPEN REVIEWER FINDINGS on `7b1ca31` — v0.1 is REVISE, not deployable

(removed outright), R3a and R4a. STILL OPEN: R2, R3b, R4b — each verified below so the next

### R1. Retention — FIXED by REMOVAL
The whole `_prune_session_history` sweep is gone: the function, its reconcile wiring, both
settings keys, the safety-floor constant, the dashboard rows and its tests. Deleted rather than
repaired, for two reasons the reviewer's findings make decisive:
  * a `DEFAULT_SETTINGS` change to `0` does NOT un-set a persisted `3`, so any DB that stored the
    earlier value kept pruning — the reviewer's "still destructive by default" was correct in
    practice, and a default is not a migration;
  * the sweep did `SELECT ids` then `DELETE ... WHERE id IN (ids)` with no re-check, against an
    `ON DELETE CASCADE` foreign key — so a session that went live between the two statements would
    be deleted along with its LIVE console.
Automatic history deletion was never what fixed the Sessions list (hiding cleanly-finished rows
from `GET /sessions` did that), so there is nothing to preserve. v0.2 can reintroduce it with the
correlated `EXISTS` re-verify the superseded-spawn reaper already uses, plus a real migration.

### R2a. Stop worker did not stop the real PTY — FIXED (+ follow-up correction)
`stop_agent_worker` only enqueued a bridge-side stop for `runtime_state.virtualTerminalId` (Pi's
synthesized RPC terminal), so every wrapper-backed runtime kept running while the button reported
success. It now stops every LIVE non-`vterm_%` terminal for the agent via the same
`_append_terminal_control(action="stop")` the virtual path used.

CORRECTED after review: the first cut marked those rows `'stopped'` immediately. The stop is only
QUEUED — the host has not acknowledged it — so that asserted a process death that had not happened,
the same "state that lies" class this release exists to remove. Now `'stopping'`, matching the
shared session-control path (`api_v2.py:12407`); a wedged `'stopping'` row is caught by the
`STUCK_STOPPING_GRACE_SECONDS` reaper.

**CORRECTED AGAIN after review (`35cc646`) — the `'stopping'` write was a REGRESSION until now.**
`_reconcile_ended_terminal_controls` fails pending controls whose terminal is
`NOT IN ('starting','attached','running','active','idle')`, and `'stopping'` is not in that set. The
sweep runs on a timer while the bridge polls every ~3s, so whenever the sweep won the race it
CANCELLED the very stop meant to kill the process — the PTY survived a "successful" Stop worker and
900s later the stuck-stopping reaper wrote `'stopped'` over it. Worse than the state lie it replaced,
because the process lived. Not hypothetical: the live DB holds 158 controls failed with exactly
`terminal is not active`, so the sweep demonstrably fires against real traffic.

Fixed by exempting `action='stop'` from that sweep, in BOTH the outer query and
`_fail_pending_terminal_controls` (a terminal with an input AND a stop outstanding is still selected
on account of the input, and the helper would otherwise take the stop down as collateral). The
exemption is deliberately not "add 'stopping' to the active set": the PRE-EXISTING virtual path marks
`'stopped'` and queues its stop in the same transaction, so it had the identical exposure. Killing a
process is idempotent and stays desirable on a dead-looking row — server.js keeps an orphan-pid
fallback for exactly that. Everything non-stop still fails fast, pinned by tests.

SELF-REVIEW FIND (same round): the rule is implemented **twice** — `api_v2._reconcile_ended_terminal_controls`
and `db._reconcile_terminal_controls`, same predicate, same error string. The first fix landed in
`api_v2` only and therefore **changed nothing**, because the `db.py` copy still cancelled the stop.
Both now carry the exemption and the test drives both paths. Recorded as an invariant in
DECISIONS.md. This is the third time this round that a defect lived in the contract around a change
rather than in the change — the suite was green throughout.

**STILL OPEN from the same review — Start can spawn a replacement before host acknowledgement.**
`stop_agent_worker` writes the session `'ended'`, and the Start allowlist keys on session status, so
Start is permitted while the wrapper PTY may still be alive → two workers for one agent. Real, but
**pre-existing** (the session was written `'ended'` before this change too) and NOT fixed here on
purpose: the obvious fix is to block Start while a live/`stopping` terminal exists for the agent, and
a too-strict Start gate is precisely what made the whole ef- team permanently unstartable in v0.1
(fixed in `f291161` by replacing a blocklist with an allowlist). Any gate added here must be provably
self-clearing — bounded by the `STUCK_STOPPING_GRACE_SECONDS` reaper, never by a status that can wedge.
- [ ] Gate Start on a live-terminal check with an explicit time bound, plus a test that a wedged
      `'stopping'` row cannot make an agent unstartable.

**The sibling VIRTUAL-terminal write stays `'stopped'` — deliberately, and I was wrong to call it a
defect.** I told the operator it was "a two-line fix I'm not making right now", which implied the
change was correct and merely risky. Reading it says otherwise, so recording the evidence here to
stop a future reviewer (or me) from "fixing" it:
  * `vterm_%` rows are excluded from EVERY liveness query in the file — `:658`, `:2385`, `:3178`,
    `:3322`, `:4490`, `:11127`, `:13898`, `:14486`, `:19049`. Nothing derives liveness from one.
  * `runtime_state.virtualTerminalId` is popped in the SAME transaction, so after the call nothing

So `'stopping'` would buy accuracy for no reader and cost a 15-minute phantom console. The

### R2c. `_current_agent_session_row` returned DEAD sessions — FIXED in v0.1
Filed here as a docstring/WHERE mismatch. Tracing the ORDER BY before editing showed it was a real
shadowing defect, which is why it moved into v0.1 rather than staying a nit.

The `WHERE` excluded only `('ended','completed','cancelled')` while the docstring already claimed
the full complement of `LIVE_SESSION_STATUSES`, so `stopped`/`failed`/`lost` passed. On its own that
would be harmless — the callers test membership downstream. The damage came from the ORDER BY:

```sql
ORDER BY CASE WHEN status IN ('running','recovering','restarting','cli-takeover') THEN 0 ELSE 1 END,
         last_seen DESC, started_at DESC
```

The CASE promotes only FOUR statuses, so the live statuses `attached` / `active` / `idle` /
`starting` sit in the SAME tier-1 bucket as the dead ones and **lose the `last_seen DESC` tiebreak
to a fresher corpse**. The picker then answered "this agent's CURRENT session" with a dead row.
Reaches five callers:
  * `_has_live_worker_for` (`:4716`) → `live_session=False` for an agent with a LIVE console, i.e. a
    status lie, and worker-liveness also gates deliverability;
  * both idle-reply closers (`:5661` pi, `:5719` claude) read `terminal_id` off the dead row, so
    they inspect the wrong terminal and never auto-close their run;
  * the terminal-close requeue path (`:5568`) compares `current_terminal_id == terminal_id` and
    silently skips the requeue on the mismatch.

Same shadowing class as `c2f0e38` (the dashboard `find()` bug). Fixed by making the WHERE the
documented complement, via a new `ENDED_AGENT_SESSION_STATUSES` — a set of its own rather than
reusing `_SESSION_DELETE_ALLOWED_STATUSES` (a deletion allowlist, whose reuse as a filter already
broke `comms_restart` / `comms_compact` once) or `_TERMINAL_DEAD_STATUSES` (a different table).
The ORDER BY is deliberately UNTOUCHED — its comment says the ordering is kept stable "to avoid
reordering which session a relaunch picks", and the WHERE alone closes the defect. All five callers
traced first: each degrades safely to `None`, and the transitional `restarting` / `cli-takeover`
statuses still resolve as current. Guarded by 7 tests, including the running-beats-attached priority
tiebreak and the newest-live-wins ordering, so the parts that must not move are pinned.

### C6. Finished runs can stay at `status='delivered'` — OPEN, evidence captured 2026-07-26
A run that has both a reply (`result_message_id`) and a `finished_at` can still carry

require_reply=0  delivered=10  of which 6 have no reply attached

Harmless to delivery — every consumer gates on `result_message_id`, not on `status`, so these are

`delivered` a legitimate TERMINAL state for some delivery paths, or is every finished run meant to

- [ ] Establish which delivery paths legitimately end at `delivered`.
- [ ] Then either advance finished runs to `completed`, or document `delivered`+`finished_at` as

### C8. NEW — `comms_console_input` reports success on input the TUI never acts on
Reported 2026-07-26 by an operator's sc-manager: five "stalls" where a managed claude sat at an idle
`❯` prompt with an unsubmitted draft while status read `online`. Console tail was the only arbiter.
`comms_console_input` with `enter: true` "worked twice, then silently stopped submitting".

**Confirmed against the live DB (read-only).** Every `comms_console_input` control sc-manager issued
reached `status='completed'` with `handled_at` set — the bridge wrote the bytes — and the draft did
not submit:

```
00:51:44  text ending <CR>   completed   (×2, to sc-claude and sc-designer)
00:56:27  bare <CR>          completed   (×2)
01:50:25  bare <CR>          completed   (×1)
```

So the tool returns ok, the control says completed, and nothing happened. That is the same
"state that lies" class as the v0.1 fixes — the difference is this one lies to an AGENT, which then
burns critical-path time re-trying a lever that cannot work. ~15 min of idle in this instance.

**Two hypotheses RULED OUT by evidence, so nobody re-derives them:**
  * *Not comms_send.* With `insert_messages_via_console=false` (the live setting) `comms_send` never
    types into a PTY — `api_v2.py:16266-16281` spawns the PTY only as the HOST for the channel
    sidecar and says so. The data agrees: exactly TWO `text` input controls exist in the whole
    table, both sc-manager's own `console_input`, none from `message_send`. Work delivery went over
    the channel as designed. A comms_send failure would look like an unclaimed queued run, not text
    at a prompt.
  * *Not stuck bracketed paste.* Zero `\x1b[200~` / `\x1b[201~` sequences have ever been written
    (`body LIKE '%[200~%'` → 0). The `bracketed_paste=True` builder is only reachable from the
    console-delivery path, which is gated off.
  * *Not the mouse-event injection below.* The failures were at 00:51-01:50; the mouse controls fall
    in 21:00-22:00 and 02:00. No temporal overlap.

**Leading hypothesis, NOT yet confirmed:** claude's composer is in multi-line mode, where Enter
inserts a newline instead of submitting — which would make each retried bare `\r` add an invisible
blank line and leave a draft that looks *identical*, exactly as reported. That is claude-TUI
behaviour this repo cannot verify from the outside.
**DONE in v0.1 — the HONESTY half.** `POST /agents/{id}/console/input` now returns
`queued: true` + `submitted: None` + a note, and the MCP tool's success text says "Input QUEUED …
This is NOT confirmation", with the description warning that repeated Enter has been measured to do
nothing. That is the part that cost the 15 minutes: sc-manager read "Input sent to X's console" as
confirmation.

CORRECTED after review (`35cc646`): a first cut also returned `consoleBytesBefore` so the caller
could diff the tail. **A tail diff cannot prove submission** — a managed claude repaints its spinner
and footer continuously, so the output changes whether or not the keystroke was consumed. That was a
misleading affordance dressed as evidence; removed rather than documented. Nothing this endpoint
returns can confirm a submit, and it now says so.

- [ ] DISCRIMINATING TEST before any mechanism fix: capture the console tail immediately before and
      after a single bare `\r` on a stuck draft, and read it by EYE (not by byte count). A newline
      appearing ⇒ multi-line composer, and the fix is to send the runtime's real submit sequence.
      Note `_sendAnswer` already sends keys as a delayed SEQUENCE to dodge Ink state-batching — a
      discipline this path skips. But do NOT reach for write-splitting first: the observed evidence
      CONTRADICTS it, because three bare-`\r` writes with nothing else in them also failed, and a
      lone CR cannot lose to state batching.

`runtimes-rpc.js` answers any `{id, method}` frame with `-32601` when no `onRequest` handler
is set. Today the only WebSocket clients are short-lived read-only inspectors
(`runtimes-codex.js` "marker inspector" / "register bridge") that never submit prompts, so
they receive no approval requests — no impact. But if a WS client is ever used for delivery,
codex approvals would be auto-**denied** rather than ignored.

- [ ] When any WS client gains prompt submission, give it an explicit `onRequest`. Add a test
      that a delivery-capable client never falls through to `-32601`.

## D. Product / UX improvements

### D1. Chat: agent↔agent traffic is now behind an identity choice
`chat.js` tightened the DM filter to strict pairwise
(`from===peer && to===viewer || from===viewer && to===peer`) and added an `all` read-only
identity. Watching a whole team's cross-talk now requires explicitly picking `all` — as
`dashboard` you see only your own DMs. This is a better model, but the affordance is one
option in a dropdown.

- [ ] Make `all` discoverable (label it "All traffic (read-only)", or default the dashboard
      identity to it since `dashboard` rarely holds the interesting conversations).

### D2. Fleet-wide "deaf agent" surfacing
The v0.1 strand was invisible: the dashboard showed the agent idle while its queued work
could never be claimed. The ceiling now bounds it, but the *symptom* still has no display.

- [ ] Surface "has queued work but is not claiming" as an attention-strip row, with the
      reason (`turn_busy latched`, `no steer capability`, `bridge offline`).
- [ ] Same for the reverse: a run `delivered` with `requireReply` and no reply past N minutes.

### D3. Reconcile observability
`_run_dispatch_reconcile_once` returns a rich counter dict that nothing displays. When the
fleet misbehaves, those counters are the fastest diagnosis available.

- [ ] Expose the last N reconcile results on an ops/debug panel (or `GET /reconcile/last`).

reasons worse about it, and the 500-line guidance in CLAUDE.md is violated by ~44x. Splitting
