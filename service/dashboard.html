Environments

Environments are connected host bridges. They claim spawn requests and run managed Sessions for agent identities in allowed workspaces.

Spawn Agent

Spawn starts a fresh session — prior context is NOT resumed. Re-spawning an existing agent ID replaces its backing with a new session (no native handle until its first run completes). To keep an agent's existing work/context, use Compact / Continue on its session instead of re-spawning.

What is this?

This is the aify-comms control plane: a dashboard for connected Windows, WSL, Linux, Docker, and remote bridges. Use it to spawn managed agents into chosen workspaces, chat with them, inspect runs, stop/restart sessions, and keep old manual CLI bindings visible only when they matter.

Dashboard / MCP service (:8800) | | chat, runs, sessions, artifacts, agent identity v Environment bridge: aify-comms | | claims managed work for one host/WSL/Windows environment v Runtime adapter: Claude Code / Codex / OpenCode / Pi | v Agent session in a specific workspace

Managed Mode

Default path. Run aify-comms as the host bridge, spawn agents from the dashboard, and let the dashboard own lifecycle, restart, compact, and recovery.

Resident Mode

Use claude-aify, codex-aify, omp-aify / pi-aify, or explicit OpenCode registration when a terminal you opened should temporarily own the live session.

Debug Path

Runs, Sessions, and API details are for operational triage. Daily communication should stay in Chat.

Core Concepts

  • Chat: conversation history and composer. Use Viewing as to read and send from a specific identity, such as manager. Read/unread and delete actions are scoped to the selected identity or selected conversation.
  • Channel: shared room inside Chat. Use it for group broadcasts and team history. It is not a separate top-level workflow.
  • Agent: persistent identity. Managed agents are dashboard-spawned and recoverable. Manual/resident CLI bindings are human-open compatibility sessions.
  • Session: concrete runtime backing record for an agent: environment, workspace, process/session handle, resume capability, and lifecycle state.
  • Run: execution/delivery audit record attached to a message. Use it when you need events, interrupt/steer, failure state, or handoff tracking.
  • Work contract: computed obligation from a message/run. It shows who owes a reply, whether the owner is queued/working/overdue/answered, and whether old inbox bookkeeping needs repair.
  • Artifact: shared file or text blob. Chat can upload a file and insert its reference; the Artifacts page lists and deletes stored artifacts.

Run Managed Mode

Managed mode is the normal team workflow. Run an environment bridge in every execution environment you want the dashboard to use, then spawn agents from Environments or the Sessions header.

cd /path/to/workspace-or-workspace-parent
aify-comms

On native Windows PowerShell/cmd, run aify-comms.cmd. The service URL defaults to http://192.168.100.10:8800. The current directory is always an allowed workspace root; extra root arguments are optional safety boundaries. The actual project folder is selected per spawned agent in Environments → Spawn Agent.

Rule of thumb: run one aify-comms bridge per host/WSL/runtime environment you want the dashboard to control. Keep it open while managed agents are working. Closing it makes those managed agents offline until the bridge returns or you assign them to another environment.

Run Resident Mode

Resident mode is for a real terminal session you want to watch or drive directly. Start the runtime through the wrapper and bind it to an agent ID. The wrapper auto-registers that live owner; if you omit --aify-agent, register manually from inside the session.

Claude Code Resident

cd /path/to/project
claude-aify --aify-agent manager --aify-role manager -auto

Codex Resident

cd /path/to/project
codex-aify --aify-agent coder --aify-role coder -auto

Use resident mode when you want the visible CLI to own the session. Use managed mode when you want the dashboard to start, stop, restart, and compact the agent without keeping a terminal open.

Managed, Resident, Session

Managed Agent

Dashboard-spawned agent. It has an environment, workspace, runtime, spawn spec, saved handle, and recovery metadata. This is the default managed mode.

Resident CLI

A terminal session you opened yourself through claude-aify, codex-aify, or omp-aify / pi-aify. It can receive live wakeups. If the live bridge is still polling, dashboard Stop asks it to terminate the host CLI/app process; otherwise Stop only disables wake in the control plane.

Session

The concrete runtime backing for an agent: Claude session ID, Codex thread ID, OpenCode/Pi handle, process state, workspace, and environment.

Move Between Dashboard And CLI

Managed dashboard control -> copy/open resume command with --aify-agent -> wrapper auto-registers resident owner -> do direct terminal work -> close CLI -> resident lease expires -> dashboard sends resume through managed backing

Managed → Resident CLI

  1. Open Sessions for the agent.
  2. Run the shown resume command. It includes --aify-agent so the wrapper auto-registers the live owner.
  3. If the managed run is still active, takeover waits until that turn finishes.
  4. Use manual comms_register(...) only when the wrapper was launched without --aify-agent or when you are binding a new ID.

Resident CLI → Managed

  1. Open Sessions, then Identity Directory.
  2. Use Edit or the identity row's Actions → Adopt env.
  3. Assign an online environment, runtime, and workspace.
  4. Close the CLI, or use Stop wake / session Stop to ask the live resident bridge to terminate the host process. Future dashboard sends return to managed backing after the lease expires.
  5. Reopen with --aify-agent to make the visible CLI the resident owner again.

Adoption creates managed backing for future dashboard work. Ownership changes only between turns: active managed work defers resident takeover, and stale resident leases can return to managed mode without inventing a new native handle. Set handle repairs a known saved Claude session ID, Codex thread ID, OpenCode session ID, or Pi handle without creating a fresh context. Recreate is the explicit reset that leaves the old native session behind and starts a fresh Claude session ID or Codex thread ID; use it only when you accept losing native chat context.

Codex CLI note: for resident live wakeups, start Codex through codex-aify. The wrapper exposes its app-server to the MCP bridge and can auto-register with --aify-agent.

Pi CLI note: for resident live wakeups, start Oh My Pi through omp-aify or pi-aify. Resume a known Pi session when you need resident dispatch to target the same native session handle.

Claude CLI note: resident wakeups require claude-aify. The resume command may include --dangerously-skip-permissions; --permanently-skip-permissions is not a Claude Code option.

Compact

Open Sessions and use Compact. Handoff is the reliable path today: it opens an editable continuation form with agent ID, role, environment, runtime, workspace, and a generated packet. It defaults to the same agent ID and queues a fresh managed-warm backing. The packet includes the last selected number of direct messages involving the source agent plus channel posts authored by it. Internal is reserved for native runtime compaction when an adapter exposes a verified API; current managed adapters do not.

Restart restores dashboard control with the saved spawn spec and saved native handle. If the handle is locked or cannot be resumed, the run fails loudly instead of pretending context was retained. Set handle is for operator repair when you know the correct native ID. Pause for CLI is an explicit dashboard-delivery pause for cases where you want terminal ownership to win. Recreate is the explicit reset: it leaves the old native session behind and starts fresh. The bridge should not silently clear native memory or invent blank replacement sessions on lock errors. Dashboard work may start a managed PTY for terminal-capable runtimes; Claude Code uses that PTY as its claude-aify backing, submits dashboard turns into the interactive prompt, and no longer uses managed claude -p dispatch.

Daily Use

Live send: messages still fail instead of being stored when the target is offline, stale, stopped, or lacks a live wake path. If the target is busy and steer-capable, normal sends steer into the active run between tool calls. If the target is busy but cannot steer, normal sends queue or merge for the next turn.

Dashboard composer: Send is the normal teamwork path. It starts idle agents, steers busy steer-capable agents, and uses next-turn queue/merge as the fallback. Queue forces the explicit next-turn path.

Work Loop: requests, reviews, and errors are tracked reply contracts by default. Routine info messages are notes unless they explicitly require a reply. Reminder messages are nudges, not new obligations; by default they repeat until the original work is answered or operator-closed. Use Close or Close Selected when an operator has reviewed stale/audit-only contracts.

Console vs messaging (current model): the Console is a live interactive PTY surface. Click into it to drive the CLI directly with normal terminal keys, paste, selection, and copy. Messaging an agent stays in Messenger mode and creates tracked run/message contracts. Native-managed runtimes use their managed/steer adapters; managed Claude Code and Hermes may start or reuse a bridge-owned PTY, but those inputs are still tracked as Messenger work rather than hidden human console typing. Blocked console input is never silently swallowed.

Status semantics: working means a genuinely active run/turn — either a claimed/running dispatch run or the bridge reporting it is mid-turn (turn-busy heartbeat). Managed Claude PTY turns stay working until the reply closes the run; if Claude visibly returns to an idle prompt after output without sending an explicit chat reply, reconcile closes that turn as completed-without-reply so it becomes Work Loop audit debt, not live work. If the active terminal output clearly asks for operator input or a decision, the agent becomes blocked instead of working. An attached but quiet console, delivered resident-channel marker, or merely-queued work is active (reachable, idle), not working. While a working agent's terminal is receiving output, its yellow dot briefly pulses orange as a live-output hint. A best-effort ⌛ badge flags an agent/console whose output looks like it is waiting for input (heuristic, not guaranteed).

Images: paste (Ctrl+V) an image into the Messenger composer — it uploads as a shared artifact and a viewable dashboard link is added to your message; the agent opens it via that link or fetches the artifact.

Spawn/respawn: spawning starts a fresh session — prior context is not resumed. Re-spawning an existing agent replaces its backing (no native handle until its first run completes). To preserve an agent's context use Compact/Continue, not re-spawn.

Bridge changes need a host bridge restart: runtime/console/status fixes that live in the host aify-comms bridge (interactive console, accurate turn-busy status, runtime advertisement) only take effect after you restart that bridge — a container rebuild alone does not apply them.

Peek mode: turn it on in Chat when you want to watch a conversation without automatically marking incoming messages read. Mark read acknowledges a direct message or the selected channel for the selected Viewing as identity.

Agent communication:

  • Keep each message scoped to one ask, result, blocker, or status update.
  • Treat every message as a small contract: owner, expected action or answer, evidence/result, and whether a reply or follow-up wake is owed.
  • Dashboard-managed delivered runs answer the current message in final plain text. Logs, tool output, and run summaries are telemetry, not the team-visible answer.
  • If more work must happen after the current turn, send the next owner a message or self-schedule before finishing.
  • Resident/live CLI sessions use comms_send(type="response", inReplyTo=...) for inbox replies.
  • Channels are for bounded shared context: answer when named, responsible, asked a question, or holding useful evidence.

Dashboard Settings

Settings cover appearance, runtime policy, Work Loop reminders, and maintenance. Recent due reply reminders are sent by the periodic service loop; busy or blocked turns are deferred so reminders do not inject text into an agent that is already handling work, and a due reminder is retried when that agent returns idle. Reminder notices do not create new reply debt. Reminders can also be previewed or sent manually from Work Loop. The Runtime tab controls global managed runtime model and effort policy; normal spawn and identity-edit forms do not tune model/effort per agent. Oh My Pi uses its own defaults unless Runtime settings or runtime config supplies model/effort.

Tools

  • Messaging: comms_register, comms_envs, comms_spawn, comms_compact, comms_agents, comms_status, comms_agent_info, comms_send (normal teamwork; live-gated), comms_inbox, comms_unsend, comms_search, comms_contracts. comms_listen remains only as deprecated compatibility/debug long-polling.
  • Advanced run control: comms_dispatch (debug/strict run tracking), comms_run_status, comms_run_interrupt. Normal users and agents should send messages, not dispatches.
  • Channels: comms_channel_create, comms_channel_join (+ invite/rejoin others), comms_channel_send (live-gated), comms_channel_read, comms_channel_list. In the dashboard, channels live inside Chat; leaving/removing a member stops future fan-out for that identity but keeps channel history.
  • File sharing: comms_share (text + binary), comms_read, comms_files
  • Management: comms_clear, comms_dashboard

API Endpoints

Mostly useful for debugging integrations and tests; daily work should happen through Control, Chat, Work Loop, Environments, Sessions, Runs, and Artifacts.

  • GET /health — Health check
  • GET /mcp/sse — MCP SSE endpoint
  • GET/POST /api/v1/agents, DELETE /api/v1/agents/{id} — Identity records
  • POST /api/v1/agents/{id}/control — Stop, resume, or interrupt active work for an identity
  • PATCH /api/v1/agents/{id}/session-handle — Operator repair for the saved native resume handle
  • GET /api/v1/environments — Connected execution environments
  • POST /api/v1/environments/heartbeat — Environment bridge heartbeat
  • GET/POST /api/v1/spawn-requests — Dashboard spawn queue
  • POST /api/v1/spawn-requests/claim — Bridge claim next spawn for an environment
  • GET /api/v1/sessions — Runtime session records
  • POST /api/v1/sessions/{id}/control — Stop, restart, recreate, or resume a managed session
  • PATCH /api/v1/agents/{id} — Update status + note
  • GET /api/v1/agents/{id}/last-read — Last message agent read
  • POST /api/v1/agents/{id}/heartbeat — Alive signal
  • POST /api/v1/messages/send — Send message (returns recipient status)
  • GET /api/v1/messages/inbox/{id} — Check inbox (supports mode=headers and messageId=...; replies include parent context)
  • POST /api/v1/messages/{id}/read — Mark one message read/unread for its recipient
  • DELETE /api/v1/messages/{id} — Unsend a message
  • POST /api/v1/messages/conversation/clear — Clear a direct chat between two identities
  • POST /api/v1/dispatch — Create a tracked delivery/run for triggerable resident sessions or managed identities
  • GET /api/v1/dispatch/runs/{id} — Inspect a run record, events, and controls
  • POST /api/v1/dispatch/runs/{id}/control — Request interrupt or steer for an active run
  • GET /api/v1/contracts — Computed work contracts over messages/runs
  • POST /api/v1/contracts/reminders/run — Send overdue reply reminders
  • GET /api/v1/dashboard/dispatches — Dispatch-focused dashboard view
  • GET/POST /api/v1/channels — Channels
  • POST /api/v1/channels/{name}/join — Join or invite agent
  • POST /api/v1/channels/{name}/send — Post to channel
  • GET/POST /api/v1/shared — Shared files (text + binary upload)
  • GET/PUT /api/v1/settings — Settings
